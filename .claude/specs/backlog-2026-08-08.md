## B-1. 🔴 `.env` ของเครื่อง dev ชี้ Supabase ตัวเดียวกับ prod — และ test เขียนลงไปจริง

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** (โผล่ระหว่าง Phase 39 ลำดับ 4)
**ความรุนแรง: ใหญ่กว่าอะไรก็ตามใน Phase 39**

### เจออะไร

`.env` ของเครื่อง dev ใช้ Supabase / Upstash **ชุดเดียวกับ production** (บันทึกไว้ก่อนหน้าแล้วว่าห้าม seed/migrate จาก local)

ด้านที่**จับได้แล้ว** ระหว่าง Phase 39 ลำดับ 4: ไม่รัน `prisma migrate dev` บนเครื่อง — เขียน migration SQL ด้วยมือแทน

**ด้านที่ยังไม่มีใครดู — และเป็นด้านที่อันตรายกว่า:**

`src/lib/__tests__/isolation/composite-fk.integration.test.ts`

- บรรทัด 23: `import "dotenv/config"` ⇒ อ่าน `.env` ของเครื่องเข้ามาทั้งไฟล์
- บรรทัด 29: `const RAW_URL = process.env.DIRECT_URL ?? process.env.TEST_DATABASE_URL ?? ""`
  ⚠️ **`DIRECT_URL` มาก่อน `TEST_DATABASE_URL`** — ตั้ง `TEST_DATABASE_URL` เฉย ๆ **ไม่ช่วย** ตราบใดที่ `DIRECT_URL` ยังอยู่ใน `.env`
- guard ที่มี (บรรทัด 49–74): `describe.skipIf(!DB_REACHABLE)` — skip เฉพาะเมื่อ **ไม่มี URL / URL เป็น localhost หรือ dummy / ต่อ DB ไม่ติด**
  ⇒ **URL ของ prod ที่ต่อติด = ไม่เข้าเงื่อนไข skip สักข้อ ⇒ test รันจริง**
- test **insert แถวจริง** ลงฐานข้อมูลนั้น

⇒ **ทุกครั้งที่รัน `npm test` บนเครื่อง dev มันเขียนลง production database**
มี cleanup ใน `afterAll` แต่ **ถ้ารันค้างกลางทาง (Ctrl-C, timeout, process ตาย) แถวตกค้าง**

### ทำไมสำคัญกว่าทุกอย่างใน Phase 39

prod นี้เป็น **portfolio สาธารณะที่มีคนเข้าจริง** (brief §1) ⇒ **แถวทดสอบที่ตกค้างคือของที่คนนอกเห็นได้**
Phase 39 ทั้งเฟสกำลังแก้เรื่อง "กลไกตายเงียบ" ซึ่งเสียหายเป็น *การมองไม่เห็น* — ส่วนข้อนี้เสียหายเป็น *ข้อมูลจริงบน prod เปื้อน* ซึ่งหนักกว่าและย้อนยากกว่า

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **แยก `.env.local` ให้ชี้ DB คนละตัว** — แก้ที่ต้นเหตุ ครอบทุก tool ไม่ใช่แค่ test นี้ · ต้องมี DB dev แยก (Supabase free project ที่สอง / Postgres ใน Docker)
2. **guard ให้ test รันเฉพาะเมื่อมี `TEST_DATABASE_URL`** — เล็กและเร็ว · แต่ต้อง**กลับลำดับ fallback** (`TEST_DATABASE_URL` ต้องมาก่อน และ **ห้าม fallback ไป `DIRECT_URL` เลย**) ไม่งั้นไม่ได้แก้อะไร
3. ผสมกัน: ทำข้อ 2 ทันทีเป็นตัวกันเลือดออก แล้วค่อยทำข้อ 1 เป็นทางแก้จริง

### สิ่งที่ต้องตรวจก่อนตัดสินใจ

- [ ] ตอนนี้มีแถวทดสอบตกค้างบน prod อยู่แล้วหรือยัง (เคยรัน `npm test` บนเครื่องนี้กี่ครั้ง)
- [ ] มี test ไฟล์อื่นที่ `import "dotenv/config"` แล้วแตะ DB จริงอีกไหม

## B-2. `prisma migrate deploy` ไม่ได้อยู่ใน pipeline ไหนเลย

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** · ดู **erratum §F** ที่บันทึกลำดับบังคับไว้แล้วสำหรับ Phase 39

ตรวจแล้วทั้งสองที่:

- `vercel.json` → `"buildCommand": "npm run build"` · `package.json` → `"build": "next build && npm run scan:bundle"` — **ไม่มี migrate**
- `.github/workflows/ci.yml` — lint / tsc / test / build / scan:bundle / audit — **ไม่มี migrate**

⇒ **deploy สำเร็จได้โดยที่ตารางยังไม่ถูกสร้าง** — รูปทรงเดียวกับ Phase 35 (RLS policy ไม่เคย apply แต่ทุก gate เขียว)

**ต่างจาก Phase 35 ตรงที่:** โค้ดที่ query ตารางที่ยังไม่มีจะ **พังเสียงดัง** (Prisma โยน) ไม่ใช่ตายเงียบ ⇒ อันตรายน้อยกว่า
**แต่ลำดับต้องถูกเขียนไว้ ไม่ใช่พึ่งความจำ** — ว่าจะทำเป็นขั้นตอนใน runbook ต่อไป หรือใส่เข้า pipeline จริง ยังไม่ตัดสิน
