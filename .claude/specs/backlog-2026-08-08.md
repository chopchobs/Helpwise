## B-1. 🔴 `.env` ของเครื่อง dev ชี้ Supabase ตัวเดียวกับ prod — และ test เขียนลงไปจริง

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** (โผล่ระหว่าง Phase 39 ลำดับ 4)
**ความรุนแรง: ใหญ่กว่าอะไรก็ตามใน Phase 39**

> 🔴 **อัปเดต 2026-08-09 — ไม่ใช่ความเสี่ยงเชิงทฤษฎีอีกต่อไป: ถูกกระตุ้นจริงแล้ว ภายใน 24 ชม. หลังบันทึก**
>
> เขียนไว้ **08-08** ว่าเป็นความเสี่ยง → **โดนจริง 08-09** อย่างน้อย **2 รอบในวันเดียว**
> โดยที่ **ไม่มีใครตั้งใจจะแตะ prod สักครั้ง** — ทั้งสองรอบเป็นการรันคำสั่งธรรมดาที่ทุกคนรันทุกวัน:
> 1. `npx vitest run` — **การรัน gate ตามปกติ** (`npm test` ก็เส้นทางเดียวกัน)
> 2. `npx vitest run <ไฟล์นั้น>` — คำสั่งวินิจฉัยตอนไล่หาจำนวนไฟล์เทสต์
>
> ⇒ **ยกระดับความเร่งด่วนตามหลักฐาน ไม่ใช่ตามความรู้สึก** — อัตราการเกิดจริงที่วัดได้คือ *ทุกครั้งที่รัน gate*
> ⇒ ✅ **verify แล้วว่าไม่มีเศษตกค้าง** (2026-08-09 · ตารางหลักฐาน 6 ตาราง อยู่ใน rehearsal runbook **C1e**)
> ⇒ ✅ **ไม่กระทบขั้น C1 ของ Phase 39** — เทสต์ insert/delete **แถวข้อมูล** ผ่าน `pg` เท่านั้น
>    **ไม่สร้างและไม่แก้ schema** ⇒ ไม่แตะ `_prisma_migrations` และไม่รบกวนหลักฐานของ migration gate

### เจออะไร

`.env` ของเครื่อง dev ใช้ Supabase / Upstash **ชุดเดียวกับ production** (บันทึกไว้ก่อนหน้าแล้วว่าห้าม seed/migrate จาก local)

ด้านที่**จับได้แล้ว** ระหว่าง Phase 39 ลำดับ 4: ไม่รัน `prisma migrate dev` บนเครื่อง — เขียน migration SQL ด้วยมือแทน

**ด้านที่ยังไม่มีใครดู — และเป็นด้านที่อันตรายกว่า:**

`src/lib/__tests__/isolation/composite-fk.integration.test.ts`

- บรรทัด 23: `import "dotenv/config"` ⇒ อ่าน `.env` ของเครื่องเข้ามาทั้งไฟล์
- บรรทัด 29: `const RAW_URL = process.env.DIRECT_URL ?? process.env.TEST_DATABASE_URL ?? ""`
  ⚠️ **`DIRECT_URL` มาก่อน `TEST_DATABASE_URL`** — ตั้ง `TEST_DATABASE_URL` เฉย ๆ **ไม่ช่วย** ตราบใดที่ `DIRECT_URL` ยังอยู่ใน `.env`
- guard ที่มี (บรรทัด 49–74): `describe.skipIf(!DB_REACHABLE)` — skip เฉพาะเมื่อ **ไม่มี URL / URL เป็น localhost หรือ dummy / ต่อ DB ไม่ติด**
  ⇒ **URL ของ prod ที่ต่อติด = ไม่เข้าเงื่อนไข skip สักข้อ ⇒ test รันจริง**
- test **insert แถวจริง** ลงฐานข้อมูลนั้น

- **ไฟล์นี้อยู่ใน `include` ของ `vitest.config.ts` ตามปกติ** (`src/**/__tests__/**/*.test.ts`)
  ⇒ **ไม่ต้องเจาะจงรันไฟล์นี้ก็โดน — การรัน gate ปกติก็รันมัน**

⇒ **ทุกครั้งที่รัน `npm test` บนเครื่อง dev มันเขียนลง production database**
มี cleanup ใน `afterAll` แต่ **ถ้ารันค้างกลางทาง (Ctrl-C, timeout, process ตาย) แถวตกค้าง**

🔴 **และที่แย่กว่านั้น: cleanup ล้มเงียบได้แม้ process รันจบสวย ๆ**
`afterAll` ทุกบรรทัด (145–151) ลงท้ายด้วย **`.catch(() => {})`** ⇒ ลบไม่สำเร็จก็ไม่มีใครรู้
และไฟล์จะยังรายงาน **ผ่าน 7/7** เหมือนเดิมทุกประการ
⇒ **"เทสต์ผ่าน" ไม่ใช่หลักฐานว่าเก็บกวาดสำเร็จ** — ต้อง query นับของจริงเท่านั้น (query พร้อมใช้อยู่ที่ runbook **C1e**)
⇒ นี่คือ fail-silent **รูปทรงเดียวกับที่ Phase 39 ทั้งเฟสสร้างมาแก้** แค่ไปอยู่ในไฟล์เทสต์แทนที่จะอยู่ใน production code

### ทำไมสำคัญกว่าทุกอย่างใน Phase 39

prod นี้เป็น **portfolio สาธารณะที่มีคนเข้าจริง** (brief §1) ⇒ **แถวทดสอบที่ตกค้างคือของที่คนนอกเห็นได้**
Phase 39 ทั้งเฟสกำลังแก้เรื่อง "กลไกตายเงียบ" ซึ่งเสียหายเป็น *การมองไม่เห็น* — ส่วนข้อนี้เสียหายเป็น *ข้อมูลจริงบน prod เปื้อน* ซึ่งหนักกว่าและย้อนยากกว่า

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **แยก `.env.local` ให้ชี้ DB คนละตัว** — แก้ที่ต้นเหตุ ครอบทุก tool ไม่ใช่แค่ test นี้ · ต้องมี DB dev แยก (Supabase free project ที่สอง / Postgres ใน Docker)
2. **guard ให้ test รันเฉพาะเมื่อมี `TEST_DATABASE_URL`** — เล็กและเร็ว · แต่ต้อง**กลับลำดับ fallback** (`TEST_DATABASE_URL` ต้องมาก่อน และ **ห้าม fallback ไป `DIRECT_URL` เลย**) ไม่งั้นไม่ได้แก้อะไร
3. ผสมกัน: ทำข้อ 2 ทันทีเป็นตัวกันเลือดออก แล้วค่อยทำข้อ 1 เป็นทางแก้จริง

4. **กัน integration test ออกจาก `include` ของ gate** (แยก `vitest.config.integration.ts` / เปลี่ยนนามสกุล)
   — ทำให้ `npm test` เลิกแตะ prod ทันทีโดยไม่ต้องมี DB ใหม่
   ⚠️ **ห้ามทำใน Phase 39** (ตัดสิน 2026-08-09) · แลกมาด้วยการที่ **composite-FK isolation test หลุดออกจาก gate**

## B-2. `prisma migrate deploy` ไม่ได้อยู่ใน pipeline ไหนเลย

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** · ดู **erratum §F** ที่บันทึกลำดับบังคับไว้แล้วสำหรับ Phase 39

ตรวจแล้วทั้งสองที่:

- `vercel.json` → `"buildCommand": "npm run build"` · `package.json` → `"build": "next build && npm run scan:bundle"` — **ไม่มี migrate**
- `.github/workflows/ci.yml` — lint / tsc / test / build / scan:bundle / audit — **ไม่มี migrate**

⇒ **deploy สำเร็จได้โดยที่ตารางยังไม่ถูกสร้าง** — รูปทรงเดียวกับ Phase 35 (RLS policy ไม่เคย apply แต่ทุก gate เขียว)

**ต่างจาก Phase 35 ตรงที่:** โค้ดที่ query ตารางที่ยังไม่มีจะ **พังเสียงดัง** (Prisma โยน) ไม่ใช่ตายเงียบ ⇒ อันตรายน้อยกว่า
**แต่ลำดับต้องถูกเขียนไว้ ไม่ใช่พึ่งความจำ** — ว่าจะทำเป็นขั้นตอนใน runbook ต่อไป หรือใส่เข้า pipeline จริง ยังไม่ตัดสิน

## B-3. 🔴 `ReadinessState` / heartbeat ไม่มี scope ของ environment

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-09** (โผล่ระหว่าง review ของ Phase 39) · **เจ้าของ: Phase 40**
**อ้างอิง:** erratum **§G ข้อ 9** · rehearsal runbook **C0-a กรณี 1**

### เจออะไร

`writeSnapshot()` upsert แถว `ReadinessState` id `"singleton"` — **แถวเดียวทั้งระบบ ไม่มีคอลัมน์ใดแยกว่าใครเขียน**
`recordHeartbeat("readiness-probe")` ก็เป็นแถว global เช่นกัน

⇒ ถ้า `DATABASE_URL` ใช้ค่าร่วมทุก scope **deployment ของ Preview เขียนสถานะทับแถวที่ endpoint สาธารณะของ
production เสิร์ฟให้ external pinger อ่าน** — Preview ที่ถูกจงใจทำให้พัง (ขั้น D ของการซ้อม) จะเขียน `FAIL` ลงไปตรง ๆ

### ทำไมยังไม่ระเบิดตอนนี้

verify 2026-08-09: route ยังไม่อยู่บน `main` · `schedule:` ของ GitHub Actions รันเฉพาะ default branch
⇒ **ยังไม่มีใครอ่านหรือเขียนแถวนี้บน prod เลย ⇒ blast radius = 0 จนกว่าจะ merge**
⚠️ ⇒ **หลัง merge ข้อนี้มีผลทันที** — §F มีข้อบังคับชั่วคราวคุมไว้แล้ว (ห้ามเชื่อค่าจนกว่า cron รอบแรกจะเขียนทับ)
แต่นั่นคือ**พลาสเตอร์เชิงกระบวนการ ไม่ใช่ทางแก้**

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **ใส่ `environment` เข้าไปใน key ของแถว** (`singleton:production` / `singleton:preview` จาก `VERCEL_ENV`)
   — เล็กที่สุด · แต่ทำให้ "แถวเดียวทั้งระบบ" ที่ v2 §3 ข้อ 7 ตั้งใจไว้ไม่จริงอีกต่อไป ต้องแก้ดีไซน์ให้ตรง
2. **ให้ Preview ใช้ DB คนละตัว** — แก้ที่ต้นเหตุและได้ผลพลอยได้กับ B-1 · แต่เป็นงานโครงสร้างที่ใหญ่กว่ามาก
3. **ห้าม non-production deployment เขียน snapshot เลย** (guard ที่ `writeSnapshot()`)
   — ตรงประเด็นที่สุดสำหรับความปลอดภัย · แต่ทำให้ **ซ้อมบน Preview พิสูจน์ write path ไม่ได้อีก** ⇒ ต้องชั่งกับคุณค่าของลำดับ 7

## B-4. เฝ้าว่าโหมด Deployment Protection ของ Vercel เปลี่ยนไปแล้ว

**สถานะ:** ยังไม่ทำ **โดยตั้งใจ** · **บันทึก 2026-08-09** · **ตัดสินใน Phase 40**
**อ้างอิง:** erratum **§G ข้อ 5 + ข้อ 7**

### เจออะไร

P2 ทั้งลูปแขวนอยู่กับค่า `ssoProtection.deploymentType = "all_except_custom_domains"` (อ่านค่าตรงแล้ว 2026-08-09)
ถ้ามีใครสลับไปโหมดที่ครอบทุก deployment ⇒ cron (ลำดับ 5) และ pinger (ลำดับ 6) โดน `302` ⇒ **P2 หยุดทั้งลูป**
กฎ `INCONCLUSIVE` กันไม่ให้ถูกอ่านเป็น PASS ได้ **แต่ไม่มีอะไรเฝ้าตัว setting เอง**

### ทางแก้ที่ยืนยันแล้วว่าทำได้ (แต่ยังไม่ทำ)

assert `ssoProtection.deploymentType` ผ่าน Vercel API ในลำดับ 5 — ค่าอ่านได้จริง เขียนเป็น check ได้ตรง ๆ

**ราคาที่ต้องจ่าย — เหตุผลที่เลื่อน:**
- ต้องเพิ่ม **`VERCEL_API_TOKEN`** อีกหนึ่ง secret (อีกหนึ่งอย่างที่หมดอายุเงียบได้)
- **ผู้เฝ้าไปกองใน GitHub มากขึ้น** ⇒ อยู่ **failure domain เดียวกับลำดับ 5** ⇒ GitHub เงียบ = เงียบพร้อมกัน
  ขัดหลักการเดียวกับ §H-5 ที่ทั้งเฟสยึด

⇒ ควรตัดสินพร้อมคำถามที่ใหญ่กว่าใน Phase 40: **ชั้นที่เฝ้า "setting ของ provider" ควรอยู่ที่ไหน**
