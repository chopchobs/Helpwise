## B-2. `prisma migrate deploy` ไม่ได้อยู่ใน pipeline ไหนเลย

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** · ดู **erratum §F** ที่บันทึกลำดับบังคับไว้แล้วสำหรับ Phase 39

ตรวจแล้วทั้งสองที่:

- `vercel.json` → `"buildCommand": "npm run build"` · `package.json` → `"build": "next build && npm run scan:bundle"` — **ไม่มี migrate**
- `.github/workflows/ci.yml` — lint / tsc / test / build / scan:bundle / audit — **ไม่มี migrate**

⇒ **deploy สำเร็จได้โดยที่ตารางยังไม่ถูกสร้าง** — รูปทรงเดียวกับ Phase 35 (RLS policy ไม่เคย apply แต่ทุก gate เขียว)

**ต่างจาก Phase 35 ตรงที่:** โค้ดที่ query ตารางที่ยังไม่มีจะ **พังเสียงดัง** (Prisma โยน) ไม่ใช่ตายเงียบ ⇒ อันตรายน้อยกว่า
**แต่ลำดับต้องถูกเขียนไว้ ไม่ใช่พึ่งความจำ** — ว่าจะทำเป็นขั้นตอนใน runbook ต่อไป หรือใส่เข้า pipeline จริง ยังไม่ตัดสิน

## B-3. 🔴 `ReadinessState` / heartbeat ไม่มี scope ของ environment

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-09** (โผล่ระหว่าง review ของ Phase 39) · **เจ้าของ: Phase 40**

`writeSnapshot()` upsert แถว `ReadinessState` id `"singleton"` — **แถวเดียวทั้งระบบ ไม่มีคอลัมน์ใดแยกว่าใครเขียน**

⇒ ถ้า `DATABASE_URL` ใช้ค่าร่วมทุก scope **deployment ของ Preview เขียนสถานะทับแถวที่ endpoint สาธารณะของ
production เสิร์ฟให้ external pinger อ่าน** — Preview ที่ถูกจงใจทำให้พัง (ขั้น D ของการซ้อม) จะเขียน `FAIL` ลงไปตรง ๆ

### ทำไมยังไม่ระเบิดตอนนี้

verify 2026-08-09: route ยังไม่อยู่บน `main` · `schedule:` ของ GitHub Actions รันเฉพาะ default branch
⇒ **ยังไม่มีใครอ่านหรือเขียนแถวนี้บน prod เลย ⇒ blast radius = 0 จนกว่าจะ merge**
⚠️ ⇒ **หลัง merge ข้อนี้มีผลทันที** — §F มีข้อบังคับชั่วคราวคุมไว้แล้ว (ห้ามเชื่อค่าจนกว่า cron รอบแรกจะเขียนทับ)

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **ใส่ `environment` เข้าไปใน key ของแถว** (`singleton:production` / `singleton:preview` จาก `VERCEL_ENV`)
   — เล็กที่สุด · แต่ทำให้ "แถวเดียวทั้งระบบ" ที่ v2 §3 ข้อ 7 ตั้งใจไว้ไม่จริงอีกต่อไป ต้องแก้ดีไซน์ให้ตรง
2. **ให้ Preview ใช้ DB คนละตัว** — แก้ที่ต้นเหตุและได้ผลพลอยได้กับ B-1 · แต่เป็นงานโครงสร้างที่ใหญ่กว่ามาก
3. **ห้าม non-production deployment เขียน snapshot เลย** (guard ที่ `writeSnapshot()`)
   — ตรงประเด็นที่สุดสำหรับความปลอดภัย · แต่ทำให้ **ซ้อมบน Preview พิสูจน์ write path ไม่ได้อีก** ⇒ ต้องชั่งกับคุณค่าของลำดับ 7

⇒ ระหว่างที่ B-1 ยังไม่ถูกแก้ **การแก้ชื่อ 1 บรรทัดมีราคาเท่ากับการแตะ production database**
⇒ เก็บไว้ทำรวมกับรอบที่ต้องรัน gate อยู่แล้ว **หลัง B-1 ปิด**

### ขอบเขตของงาน (เล็กและชัด)

- **rename อย่างเดียว ไม่แตะโครงสร้าง ไม่แตะตรรกะสถานะ** — `"probe"` → `"heartbeat_read"` ใน `STAGE_FAILURE`
- ต้องแก้ตามอีก 3 ที่: test ที่ assert `components.probe` · ตาราง E2 ของ rehearsal runbook · ตาราง stage ใน §H-8
- ⛔ **ไม่ใช่การแยก component key ให้ละเอียดขึ้น** — ตัดสินแล้ว 2026-08-09 ว่า**ไม่แยก** เพราะจะได้ความแม่นยำ
  เพิ่มขึ้น **ศูนย์** (มีผู้ต้องสงสัยรายเดียวอยู่แล้ว) แต่ต้องเพิ่ม try/catch เข้าไปใน `runLiveProbe()`
  = สร้าง swallow site ใหม่ในไฟล์ที่ §F ห้ามมี swallow site ที่สุด

> 📌 **เหตุผลที่ข้อนี้ต้องอยู่ในไฟล์นี้ ไม่ใช่ค้างในบทสนทนา:** ข้อเสนอนี้เกิดในแชตแล้วเกือบหายไปกับ context

## B-6. 🔴 เครื่อง dev ไม่มี `QSTASH_URL` — ยังอยู่ในสภาพ incident เดิม และซ้อนทับกับ B-1

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-09** (โผล่ตอนหาแหล่งกู้ค่าให้ขั้น D0 ของ rehearsal runbook)

### เจออะไร

ตรวจ `.env` ของเครื่อง dev 2026-08-09 — มี `QSTASH_TARGET_BASE_URL` · `QSTASH_TOKEN` ·
`QSTASH_CURRENT_SIGNING_KEY` · `QSTASH_NEXT_SIGNING_KEY` แต่ **ไม่มี `QSTASH_URL`**

⇒ โค้ดที่รันบนเครื่องนี้ **fallback ไป EU default (`https://qstash.upstash.io`)**
⇒ **เครื่อง dev ยังอยู่ในสภาพเดียวกับ incident Phase 38 เป๊ะ ๆ** — ทั้งที่ prod แก้ไปตั้งแต่ 2026-08-06

### ทำไมสำคัญกว่าที่ดู — **ซ้อนทับกับ B-1**

รวมสองข้อเข้าด้วยกัน สภาพจริงของเครื่อง dev คือ:

> 🔴 **production database (B-1) + QStash ที่ชี้ผิด region (ข้อนี้)**

⇒ งานที่รันบนเครื่องนี้แล้ว publish คิว **จะเขียน DB ของ prod แต่ยิงคิวไปปลายทางที่ไม่มีอะไรอยู่**
⇒ เป็นการผลิต**สถานะครึ่ง ๆ กลาง ๆ บน production** ที่ยากจะสืบย้อนกว่าอย่างใดอย่างหนึ่งเดี่ยว ๆ
· และ **ไม่มีอะไรจับ** เพราะ P2 ที่สร้างมาเพื่อจับเรื่องนี้ยังไม่ merge

### ผลข้างเคียงที่กระทบ Phase 39 ตอนนี้

**`.env` ใช้เป็นแหล่งกู้ค่าไม่ได้** ⇒ เมื่อรวมกับ **§G ข้อ 10** (Sensitive ⇒ อ่านค่าจาก Vercel ไม่ได้)
⇒ **แหล่งเดียวที่เหลือของค่านี้คือ incident §8.1** ซึ่งเป็น**ไฟล์ markdown ในรีโป**
⇒ เขียนกำกับไว้ในรันบุ๊กขั้น D0 แล้ว (ไม่ใช่ให้ไปค้นตอนฉุกเฉิน)

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **เติม `QSTASH_URL` ลง `.env` ของเครื่อง** — เล็กที่สุด แต่ทำให้เครื่อง dev ยิงคิวจริงเข้า prod QStash ได้
   ⇒ **ต้องตัดสินพร้อม B-1** ว่าเครื่อง dev ควรต่อของ prod ตัวไหนได้บ้าง — ไม่ใช่แก้ทีละตัวแปร
2. **ให้โค้ด fail-loud เมื่อไม่ได้ตั้ง `QSTASH_URL`** แทนที่จะ fallback ไป EU เงียบ ๆ
   — ปิดคลาสของ incident เดิมที่ต้นเหตุ · แต่แตะ `src/lib/queue.ts` ⇒ **ไม่ใช่งานของ Phase 39**
3. บันทึกไว้เฉย ๆ แล้วรอ B-1 — ถูกที่สุด แต่สภาพ "prod DB + EU QStash" ยังอยู่ต่อไป

## B-7. ให้ `readiness-rehearsal.ts` บังคับกฎ `source === "live"` เอง

**สถานะ:** ยังไม่ทำ **โดยตั้งใจ** · **บันทึก 2026-08-09** · **เจ้าภาพ: Phase 40 (ทำรวมรอบเดียวกับ B-5)**
**อ้างอิง:** erratum **§G ข้อ 11** · **§H-10** · rehearsal runbook ข้อ 1 (*กฎที่ 0*)

### เจออะไร

`buildAuthorizedReport()` มี min-interval 300s — ชน lock ⇒ เสิร์ฟ snapshot เก่าพร้อม `components` ชุดเดิม
⇒ กด F3 ภายใน 5 นาทีหลัง E1 จะได้ `PROVEN` จากผลของ E1 ⇒ **อ่านว่า "ยังไม่คืนสภาพ" ทั้งที่คืนแล้ว**

กฎที่ปิดช่องนี้ (**`"source":"stored"` ⇒ `INCONCLUSIVE` เสมอ**) เขียนไว้ใน runbook แล้ว
แต่ **`evaluate()` ไม่เคยอ่าน `source`** ⇒ ตอนนี้พึ่งคนอ่านล้วน

> ⚠️ **นี่คือรูปทรงที่ทั้ง Phase 39 สร้างมาเพื่อกำจัด** — กฎที่ไม่มีอะไรบังคับ คือกฎที่จะตายเงียบ
> ⇒ ข้อนี้ไม่ใช่ "ของแต่ง" แต่เป็นการทำให้กฎที่มีอยู่แล้วมีฟันจริง

### ขอบเขตของงาน (เล็กและชัด)

- `probePreview()` อ่าน `data.source` จาก body ที่ parse แล้ว
- `evaluate()` เพิ่มเงื่อนไขก่อนทุกเงื่อนไขอื่น: `source !== "live"` ⇒ `INCONCLUSIVE`
  พร้อม hint *"ชน min-interval — เว้น > 5 นาทีแล้วกดใหม่ · redeploy ไม่ล้าง lock (อยู่บน Redis)"*
- ⛔ **ห้ามแตะตรรกะสถานะฝั่ง endpoint** — งานนี้อยู่ฝั่งผู้อ่านล้วน

### ทำไมยังไม่ทำ — **ราคา ไม่ใช่ความสำคัญ**

แก้สคริปต์ = รัน gate ซ้ำ = **เขียนลง prod (B-1)** ⇒ เหตุผลเดียวกับ **B-5** เป๊ะ
⇒ **ทำรวมรอบเดียวกันหลัง B-1 ปิด** · ระหว่างนี้ความผิดพลาดที่เกิดได้เป็น **false alarm ไม่ใช่ false pass**
