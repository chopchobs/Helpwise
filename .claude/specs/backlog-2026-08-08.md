### 🟢 workaround ที่ใช้ได้ทันที — **ไม่ใช่การแก้** *(ยืนยันด้วยการรันจริง 2026-08-09)*

```bash
DIRECT_URL= npm test
```

รัน gate ได้เต็ม โดย **ไม่แตะ prod เลย** — กลไกที่ทำให้ได้ผลนี้ (ยืนยันด้วยการรันจริง ไม่ใช่อ่านโค้ดอย่างเดียว):

1. **`dotenv` ไม่ override ตัวแปรที่ตั้งมาแล้วใน `process.env`** ⇒ `DIRECT_URL` ของ `.env` ไม่ถูกโหลดทับ
2. **`??` ไม่ fall through ที่ empty string** ⇒ `process.env.DIRECT_URL ?? process.env.TEST_DATABASE_URL ?? ""`
   คืน `""` (ไม่เด้งไปหา `TEST_DATABASE_URL`) ⇒ `RAW_URL = ""` ⇒ `DB_REACHABLE = false` ⇒ **skip ทั้ง suite**

> ⚠️ **ยังไม่ใช่ guard — อย่าอ่านว่าปิดจบแล้ว**
> workaround นี้ **ปลอดภัยเพราะคนพิมพ์ถูกทุกครั้ง** ไม่ใช่เพราะมีอะไรกันไว้
> · ลืมพิมพ์ prefix ครั้งเดียว = กลับไปเขียน prod เหมือนเดิม **โดยไม่มีสัญญาณอะไรเตือน**
> · เป็นความปลอดภัยชนิดเดียวกับที่ **§H-10** เพิ่งบันทึกว่าเป็นหนี้ (กฎที่พึ่งคนบังคับ)
>
> **การแก้จริงคือ guard ในโค้ด** — ปฏิเสธ host ของ prod เว้นแต่มี **opt-in ที่ชัดเจน**
> (เช่น ต้องตั้ง `ALLOW_PROD_DB_TEST=1` ถึงจะยอมรัน) ⇒ ค่าเริ่มต้นปลอดภัยโดยไม่ต้องพึ่งการพิมพ์
> ⇒ ทางแก้ข้อ 2 ในรายการด้านล่างคือรูปแบบนี้ · **workaround ใช้ระหว่างรอ ไม่ใช่แทน**
> ⇒ ✅ **verify แล้วว่าไม่มีเศษตกค้าง** (2026-08-09 · ตารางหลักฐาน 6 ตาราง อยู่ใน rehearsal runbook **C1e**)
> ⇒ ✅ **ไม่กระทบขั้น C1 ของ Phase 39** — เทสต์ insert/delete **แถวข้อมูล** ผ่าน `pg` เท่านั้น
>    **ไม่สร้างและไม่แก้ schema** ⇒ ไม่แตะ `_prisma_migrations` และไม่รบกวนหลักฐานของ migration gate

## B-2. `prisma migrate deploy` ไม่ได้อยู่ใน pipeline ไหนเลย

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-08** · ดู **erratum §F** ที่บันทึกลำดับบังคับไว้แล้วสำหรับ Phase 39

ตรวจแล้วทั้งสองที่:

- `vercel.json` → `"buildCommand": "npm run build"` · `package.json` → `"build": "next build && npm run scan:bundle"` — **ไม่มี migrate**
- `.github/workflows/ci.yml` — lint / tsc / test / build / scan:bundle / audit — **ไม่มี migrate**

⇒ **deploy สำเร็จได้โดยที่ตารางยังไม่ถูกสร้าง** — รูปทรงเดียวกับ Phase 35 (RLS policy ไม่เคย apply แต่ทุก gate เขียว)

**ต่างจาก Phase 35 ตรงที่:** โค้ดที่ query ตารางที่ยังไม่มีจะ **พังเสียงดัง** (Prisma โยน) ไม่ใช่ตายเงียบ ⇒ อันตรายน้อยกว่า
**แต่ลำดับต้องถูกเขียนไว้ ไม่ใช่พึ่งความจำ** — ว่าจะทำเป็นขั้นตอนใน runbook ต่อไป หรือใส่เข้า pipeline จริง ยังไม่ตัดสิน

## B-3. 🔴 `ReadinessState` / heartbeat ไม่มี scope ของ environment

**สถานะ:** ยังไม่แก้ · **บันทึก 2026-08-09** (โผล่ระหว่าง review ของ Phase 39) · **เจ้าของ: Phase 40**

### เจออะไร

`writeSnapshot()` upsert แถว `ReadinessState` id `"singleton"` — **แถวเดียวทั้งระบบ ไม่มีคอลัมน์ใดแยกว่าใครเขียน**
`recordHeartbeat("readiness-probe")` ก็เป็นแถว global เช่นกัน

⇒ ถ้า `DATABASE_URL` ใช้ค่าร่วมทุก scope **deployment ของ Preview เขียนสถานะทับแถวที่ endpoint สาธารณะของ
production เสิร์ฟให้ external pinger อ่าน** — Preview ที่ถูกจงใจทำให้พัง (ขั้น D ของการซ้อม) จะเขียน `FAIL` ลงไปตรง ๆ

### ทำไมยังไม่ระเบิดตอนนี้

verify 2026-08-09: route ยังไม่อยู่บน `main` · `schedule:` ของ GitHub Actions รันเฉพาะ default branch
⇒ **ยังไม่มีใครอ่านหรือเขียนแถวนี้บน prod เลย ⇒ blast radius = 0 จนกว่าจะ merge**
⚠️ ⇒ **หลัง merge ข้อนี้มีผลทันที** — §F มีข้อบังคับชั่วคราวคุมไว้แล้ว (ห้ามเชื่อค่าจนกว่า cron รอบแรกจะเขียนทับ)
แต่นั่นคือ**พลาสเตอร์เชิงกระบวนการ ไม่ใช่ทางแก้**

### ทางแก้ที่ควรพิจารณา (ยังไม่เลือก)

1. **ใส่ `environment` เข้าไปใน key ของแถว** (`singleton:production` / `singleton:preview` จาก `VERCEL_ENV`)
   — เล็กที่สุด · แต่ทำให้ "แถวเดียวทั้งระบบ" ที่ v2 §3 ข้อ 7 ตั้งใจไว้ไม่จริงอีกต่อไป ต้องแก้ดีไซน์ให้ตรง
2. **ให้ Preview ใช้ DB คนละตัว** — แก้ที่ต้นเหตุและได้ผลพลอยได้กับ B-1 · แต่เป็นงานโครงสร้างที่ใหญ่กว่ามาก
3. **ห้าม non-production deployment เขียน snapshot เลย** (guard ที่ `writeSnapshot()`)
   — ตรงประเด็นที่สุดสำหรับความปลอดภัย · แต่ทำให้ **ซ้อมบน Preview พิสูจน์ write path ไม่ได้อีก** ⇒ ต้องชั่งกับคุณค่าของลำดับ 7

## B-7. `readiness-rehearsal.ts` — **สคริปต์ไม่รู้ว่าตัวเองถูกเรียกในบริบทไหน** (3 อาการ รากเดียว)

> 🔑 **รากร่วมของทั้งสามอาการ:** สคริปต์ถูกเขียนขึ้นเพื่อตอบคำถามเดียว (*"ซ้อม reproduce ได้ไหม"*)
> แต่ของจริงถูกใช้ตอบ **สองคำถามที่ต้องการคำตอบตรงข้ามกัน**:
> · **E1 (rehearse):** `PROVEN` = สำเร็จ · `INVALID` = ต้องไปแก้ prerequisite
> · **F3 (restore):** `PROVEN` = **ล้มเหลว (ยังไม่คืนสภาพ)** · `INVALID`/อื่น ๆ = **สำเร็จ**
> ⇒ **เกณฑ์ ข้อความ และ exit code กลับด้านกันทั้งชุด** แต่สคริปต์ไม่มีทางรู้ว่ากำลังอยู่โหมดไหน
>
> **ทางแก้ที่ครอบทั้งสามอาการ:** รับ **โหมด** เป็น argument — `rehearse` (ค่าเริ่มต้น) | `restore`
> แล้วเปลี่ยน **เกณฑ์ตัดสิน + ข้อความ + exit code** ตามโหมด

### อาการที่ 1 — ไม่บังคับกฎ `source === "live"`

**สถานะ:** ยังไม่ทำ **โดยตั้งใจ** · **บันทึก 2026-08-09** · **เจ้าภาพ: Phase 40 (ทำรวมรอบเดียวกับ B-5)**
**อ้างอิง:** erratum **§G ข้อ 11** · **§H-10** · rehearsal runbook ข้อ 1 (*กฎที่ 0*)

### เจออะไร

`buildAuthorizedReport()` มี min-interval 300s — ชน lock ⇒ เสิร์ฟ snapshot เก่าพร้อม `components` ชุดเดิม
⇒ กด F3 ภายใน 5 นาทีหลัง E1 จะได้ `PROVEN` จากผลของ E1 ⇒ **อ่านว่า "ยังไม่คืนสภาพ" ทั้งที่คืนแล้ว**

กฎที่ปิดช่องนี้ (**`"source":"stored"` ⇒ `INCONCLUSIVE` เสมอ**) เขียนไว้ใน runbook แล้ว
แต่ **`evaluate()` ไม่เคยอ่าน `source`** ⇒ ตอนนี้พึ่งคนอ่านล้วน

> ⚠️ **นี่คือรูปทรงที่ทั้ง Phase 39 สร้างมาเพื่อกำจัด** — กฎที่ไม่มีอะไรบังคับ คือกฎที่จะตายเงียบ
> ⇒ ข้อนี้ไม่ใช่ "ของแต่ง" แต่เป็นการทำให้กฎที่มีอยู่แล้วมีฟันจริง

### อาการที่ 3 — ข้อความ + exit code ของ `INVALID` ผิดบริบทเมื่อถูกใช้ที่ F3

*(เพิ่ม 2026-08-09 หลังทำขั้น F จริง)*

`evaluate()` เคส `INVALID` พิมพ์ว่า *"ต้องแก้ prerequisite ให้ครบก่อนซ้อมใหม่"* และ `main()` ตั้ง
`process.exitCode = 1` พร้อมข้อความ *"⛔ ยังพิสูจน์ไม่ได้ — ห้ามถือว่าซ้อมผ่าน"*

**ถูกต้องสำหรับ E1 · ผิดสำหรับ F3 ทุกประการ** — ที่ F3 ผลนี้คือ **สิ่งที่ต้องการ**:

| | E1 (rehearse) | F3 (restore) |
| --- | --- | --- |
| `INVALID` แปลว่า | ❌ prerequisite ไม่ครบ ไปแก้ | ✅ **คืนสภาพสำเร็จ** (signature หายแล้ว) |
| exit code 1 สื่อว่า | ถูกต้อง — งานยังไม่ผ่าน | **ผิด** — งานผ่านแล้วแต่รายงานว่าล้มเหลว |

⚠️ **ราคาจริงของอาการนี้:** ที่ F3 คนต้องอ่านผลโดย **เพิกเฉยต่อข้อความที่สคริปต์พิมพ์ออกมา**
แล้วไปเทียบกับเกณฑ์ในรันบุ๊กแทน ⇒ **เครื่องมือกับเอกสารสั่งสวนทางกันตรงขั้นที่ผิดพลาดแล้วเสียหายที่สุด**
(F3 คือหลักฐานหลักของการคืนสภาพ — §G ข้อ 10)
· รอบนี้ไม่เสียหายเพราะ runbook เขียนเกณฑ์ไว้ชัด แต่**พึ่งคนอ่านที่เชื่อเอกสารมากกว่าเชื่อ output** — ไม่ยั่งยืน

### อาการที่ 2 — ข้อความปิดท้ายเป็นถ้อยคำของทาง B

`main()` ของ `scripts/readiness-rehearsal.ts` พิมพ์ปิดท้ายทุกครั้งว่า:

⇒ 🔴 **คนที่ทำตามข้อความนี้ตรง ๆ จะไปเปิดแถวที่ Production ใช้ ซึ่งเป็นสิ่งที่ทาง A ตั้งใจเลี่ยงทั้งหมด**
⇒ ข้อความแนะนำที่ชี้ไปยังการกระทำที่อันตรายกว่าที่จำเป็น — อันตรายกว่าข้อความที่แค่ล้าสมัยเฉย ๆ

### ขอบเขตของงาน (เล็กและชัด — ทำรอบเดียวปิดทั้งสามอาการ)

## B-11. ไม่มี test ค้ำ `if:` ของ job `dispatch` — คลาย filter = dispatch storm

**เพิ่ม 2026-08-10** (Dev เสนอตอนรีวิว §H-12) · **ยังไม่ทำ — อยู่นอกข้อกำหนด 5 ข้อของ §H-12**
**อ้างอิง:** `.github/workflows/readiness.yml` job `dispatch` · `src/lib/__tests__/readiness-workflow-guards.test.ts`

### ปัญหา

`readiness-workflow-guards.test.ts` ค้ำ concurrency · loop · permission · ผู้ตรวจ≠ผู้ถูกตรวจ ครบแล้ว
แต่ **ไม่ค้ำตัวกรอง `if:` ของ job `dispatch`** ซึ่งตอนนี้เป็น:

```
github.event_name == 'deployment_status' &&
github.event.deployment_status.state == 'success' &&
github.event.deployment_status.environment == 'Production'
```

⇒ ถ้ามีคนคลาย `state == 'success'` หรือ `environment == 'Production'` ออก
**preview deploy ทุกใบจะสั่ง `workflow_dispatch`** (Vercel ยิง `deployment_status` ทุกสถานะ รวม pending/error
และยิงจาก preview ด้วย — ดูคอมเมนต์เหนือ `if:` ในไฟล์) ⇒ **dispatch storm**

### ทำไมมันแย่กว่าที่ดู

- run ที่ถูก dispatch ทุกใบ **ยิง probe จริงไปที่โดเมน production** (เป้าหมายมาจาก `secrets.PROD_BASE_URL`
  ไม่ใช่จาก input) ⇒ storm ไม่ได้แค่เปลือง quota แต่**กระแทก min-interval + เขียน `ReadinessState` รัว**
- `concurrency: readiness` ของ job `check` จะเข้าคิวยาว ⇒ cron รอบปกติถูกดันออกไป
- **CI ไม่มีทางจับ** — เป็น expression ใน YAML ที่ประเมินตอนรันเท่านั้น

### ทางแก้ที่เสนอ (ยังไม่อนุมัติ)

assert ว่า `if:` ของ job `dispatch` **มีครบทั้ง 3 เงื่อนไข** — แต่ ⚠️ ต้องระวังไม่ให้กลายเป็น
**การค้ำถ้อยคำ** (string match ตรง ๆ จะแดงทันทีที่มีคนจัดบรรทัดใหม่ ทั้งที่ความหมายไม่เปลี่ยน)
⇒ ทางที่น่าจะถูก: normalize whitespace แล้วเช็คว่ามี **ทั้งสาม predicate** อยู่ (ไม่ผูกกับลำดับ/การขึ้นบรรทัด)

**ประเมิน:** ผู้สมัครที่คุ้มที่สุดของรอบถัดไป — ความเสียหายสูง · ค้ำได้ด้วย test ที่มีอยู่แล้ว · ราคาต่ำ

### 🔄 อัปเดต 2026-08-10 — **สมมติฐานถูกวัดแล้วครั้งหนึ่ง แต่ backlog ยังคงอยู่**

deploy จริงหลัง merge §H-12: job `dispatch` **รัน** (ไม่ใช่ `skipped`)
⇒ ✅ **`state=='success'` และ `environment=='Production'` ตรงกับที่ Vercel ส่งจริง** — ยืนยันแล้ว

> 🔑 **แต่นี่คือ "วัดแล้วครั้งหนึ่ง" ไม่ใช่ "ปิดข้อนี้ได้"** — และเส้นแบ่งนี้สำคัญ:
> · สิ่งที่ได้มา: ลบความเสี่ยง *"สมมติฐานผิดตั้งแต่แรก"* ออกไปแล้ว
> · สิ่งที่**ยังไม่ได้**: **ไม่มีอะไรเฝ้าว่ามันจะเปลี่ยน** — Vercel เปลี่ยนชื่อ environment เมื่อไรก็ได้
>   แล้ว job จะถูกข้ามเงียบ ๆ โดยไม่มี error ให้เห็น
> ⇒ **รูปทรงเดียวกับ §G ข้อ 5 → ข้อ 7 เป๊ะ ๆ** (ค่า Deployment Protection ถูก verify แล้ว
>   แต่การ verify ครั้งเดียวกลับ*สร้าง*ข้อ 7 ขึ้นมา เพราะทั้งระบบไปแขวนกับค่าที่ไม่มีใครเฝ้า)

⇒ **ขอบเขตของ B-11 จึงกว้างกว่าที่เขียนไว้ตอนแรก** — มีสองชั้นที่ต่างกัน:

| --- | --- | --- |

   ⇒ **เขียนเจตนานั้นลงคอมเมนต์** ให้ชัด (ตอนนี้คอมเมนต์อธิบายแต่เกณฑ์อัตราส่วน)
