# Design Brief — Phase 39 (P2 + P3)
> สำหรับส่งให้ **Claude Design** · เขียน 2026-08-06 หลังปิด gate Phase 36 + 38
> เอกสารนี้ **self-contained** — ผู้อ่านไม่มี context ของโปรเจกต์มาก่อน

---

## 0. บทบาทที่ขอ

คุณคือ **สถาปนิกซอฟต์แวร์** ที่ถูกขอให้ออกแบบกลไก ไม่ใช่ให้เขียนโค้ด
ผลลัพธ์ที่ต้องการคือ **เอกสารออกแบบ** ที่ตอบคำถามใน § 6 ได้ครบ และผ่านเกณฑ์ § 8

⛔ อย่าเพิ่งเสนอโค้ด · อย่าเพิ่งเลือก library · อย่าข้ามไปที่ implementation
ถ้าข้อมูลไม่พอให้ **ถามกลับ** ก่อนออกแบบ

## 1. ระบบคืออะไร (ย่อ)

**Helpwise** — multi-tenant SaaS help desk (B2B) · Next.js 16 App Router + TypeScript ·
Prisma + PostgreSQL (Supabase) · deploy บน **Vercel** · แยก tenant ด้วยคอลัมน์ `tenantId`
และ subdomain `{slug}.gethelpwise.xyz`

**Infrastructure ภายนอกที่พึ่งพา:**

| บริการ | ใช้ทำอะไร |
| --- | --- |
| **Upstash QStash** | message queue — ส่ง outbound email · dispatch outbound webhooks · ขับ SLA sweep ตามรอบ |
| Upstash Redis | cache tenant lookup |
| Stripe | subscription + webhook |
| Postmark/SendGrid | outbound email provider |

**สภาพปัจจุบันของ production:** ไม่มีลูกค้าจริง มีแค่ 2 tenant สาธิต (`acme`, `globex`)
ที่เปิดให้คนทั่วไปเข้าดูได้ — เป็น portfolio ที่มีคนเปิดจริง
**ทีม = คนเดียว + AI · ไม่มี on-call · ไม่มีระบบ alerting ใด ๆ วันนี้**

## 2. เหตุการณ์ที่เป็นที่มาของงานนี้ (ข้อเท็จจริงล้วน)

### 2.1 อาการ

**ทุกอย่างที่ผ่าน message queue ตายสนิทบน production จนถึง 6 ส.ค. 2026 โดยไม่มีใครรู้** —
queue ถูกเพิ่มเข้าระบบเมื่อ **19 มิ.ย. 2026** และ **ไม่เคยส่ง message ออกไปได้สำเร็จแม้แต่ครั้งเดียว** (~7 สัปดาห์):

| feature | เข้าระบบเมื่อ | ผู้ใช้เห็นอะไร |
| --- | --- | --- |
| outbound email ตอบกลับลูกค้า | 19 มิ.ย. (พร้อม queue) | agent เห็นข้อความถูกบันทึกปกติ · **ลูกค้าไม่เคยได้รับเมล** |
| outbound webhooks | **23 ก.ค.** | API ตอบ `201` ปกติทุกครั้ง · delivery ค้าง `PENDING` ถาวร — **เกิดมาพังตั้งแต่วันแรก ไม่เคยทำงานเลยสักครั้ง** |
| SLA sweep | 19 มิ.ย. | **ไม่เคยมี QStash schedule ถูกสร้างเลยด้วยซ้ำ** — ไม่ใช่ "เคยทำงานแล้วพัง" แต่ **ไม่เคยเริ่มทำงาน** และไม่มี error path ให้เห็นเลย |

> 🔑 **ข้อสังเกตที่สำคัญกว่าจำนวนสัปดาห์:** 2 ใน 3 feature **ไม่เคยทำงานสำเร็จแม้แต่ครั้งเดียว**
> ผ่าน code review · ผ่าน test · ผ่าน gate ก่อน merge · deploy ขึ้น production · แล้ว**ไม่มีใครสังเกตเลย**
> ⇒ ปัญหาไม่ใช่ *"ของที่เคยทำงานแล้วพัง"* แต่คือ **ระบบไม่มีทางบอกได้ว่าของที่ deploy ไปแล้วเคยทำงานจริงหรือไม่**

### 2.2 สาเหตุ

โค้ดสร้าง QStash client ด้วย `new Client({ token })` โดยไม่ระบุ `baseUrl`
→ SDK ตกไปอ่าน `process.env.QSTASH_URL` → **ไม่มีตัวแปรนี้อยู่เลย** → ใช้ endpoint default (EU)
แต่บัญชี Upstash อยู่ **US East** → publish ถูกปฏิเสธตั้งแต่ต้นทางด้วย
`user (…) not found in this region (eu-central-1)`

→ ไม่มี message เข้า queue เลย → worker ไม่เคยถูกเรียก → ทุกอย่างที่ผ่าน queue ตายพร้อมกัน

**การแก้ = เพิ่ม env ตัวเดียว** `QSTASH_URL=https://qstash-us-east-1.upstash.io` แล้ว redeploy

### 2.3 🔴 ทำไมไม่มีใครรู้มา 6 สัปดาห์ — จุดที่สำคัญที่สุดของเอกสารนี้

**สภาพ ณ เวลาที่ระบบตายสนิท:**

| ตัวแปร | สถานะ |
| --- | --- |
| `QSTASH_TOKEN` | ✅ ตั้งครบ · **และ token ถูกต้อง ใช้งานได้จริง** |
| `QSTASH_CURRENT_SIGNING_KEY` / `NEXT` | ✅ ตั้งครบทั้งคู่ · **ถูกต้องทั้งคู่** |
| `QSTASH_TARGET_BASE_URL` | ✅ เป็น URL จริง ไม่ใช่ template |
| `QSTASH_URL` | ❌ **ไม่มีตัวแปรนี้ และไม่มีใครรู้ว่าต้องมี** |

> **gate ที่ตรวจว่า "ตัวแปรมีค่าไหม / สะกดถูกไหม / ไม่ว่างไหม" จะให้ PASS ทั้งหมด**
> ตัวแปรที่ผิดคือ **ตัวที่ไม่มีอยู่และไม่มีใครรู้ว่าต้องมี**
> ⇒ **การ enumerate ตัวแปรที่รู้จักแล้วเช็คว่ามีค่า ไม่มีทางจับเคสนี้ได้ ไม่ว่าจะเขียนดีแค่ไหน**

**และกลไกที่ทำให้เงียบ:** โค้ด `publish` **throw จริง** แต่ถูกกลืนโดยเจตนา
(`Promise.allSettled` + try/catch ครอบทั้งฟังก์ชัน) เพื่อไม่ให้ webhook ที่ล้มไปทำให้
การสร้าง ticket ล้มตาม — **fail-soft ที่ถูกต้องตามหลักการ แต่ทำให้ไม่มีสัญญาณเหลือถึงผู้ดูแลเลย**

### 2.4 ประวัติของบทเรียนนี้ — ไม่ใช่ครั้งแรก

| ครั้ง | เหตุการณ์ |
| --- | --- |
| Phase 35 | realtime presence ผ่านทุก gate ก่อน merge แต่ RLS policy ไม่เคย apply + `NEXT_PUBLIC_*` ไม่เคยตั้งบน Vercel → **feature ตาย 1 เดือน** |
| Phase 38 | `vercel.json buildCommand` override `package.json` → gate script ที่เขียนไว้ **ไม่เคยถูกเรียกในสาย build ของ production เลย** |
| **วันนี้** | env ครบทุกตัวที่รู้จัก แต่ระบบตายสนิท 6 สัปดาห์ |

**รากเดียวกันทั้งสามครั้ง: gate ตรวจ "เจตนา" ไม่ได้ตรวจ "ผล"**
โปรเจกต์แก้ไปแล้วบางส่วน (เปลี่ยน checklist เป็นตารางหลักฐานที่ต้องอ้างคำสั่ง + ผลจริงบน prod)
แต่ **ยังไม่มีกลไกอัตโนมัติ** — ทุกวันนี้ยังพึ่งคนไล่ตรวจด้วยมือทีละเฟส

## 3. ปัญหาที่แท้จริง (โจทย์ตัวจริง)

> **ระบบไม่สามารถแสดงได้ว่าตัวเองยังทำงานอยู่ — และเราตีความ "ไม่มี error" ว่า "ปกติ"**

เหตุการณ์วันนี้ทำให้เห็นว่า **อย่างน้อย 4 กลไกในระบบมีรูปแบบความล้มเหลวเดียวกัน**:

| # | กลไก | ล้มเหลวยังไง | มองเห็นได้ไหม |
| --- | --- | --- | --- |
| 1 | publish เข้า queue | ถูกปฏิเสธที่ต้นทาง (region ผิด / **โควตาหมด**) | ❌ กลืนโดย fail-soft |
| 2 | QStash quota | free = 1,000 msg/วัน · sweep พังต่อเนื่องที่ `*/5` = **1,152/วัน เกินโควตา** → ลากทุก feature ตายตาม | ❌ ไม่มีอะไรเฝ้า |
| 3 | SLA near-breach | polling ทุก 5 นาที จับหน้าต่างที่กว้างแค่ **3 นาที** (URGENT) → **ยิงราว 60% ของเคสแบบสุ่ม** | ❌ "เคยเตือน" ทำให้คนสรุปว่าปกติ |
| 4 | SLA sweep วนทุก tenant | ไม่มี per-tenant checkpoint → timeout กลางทาง = tenant ท้าย ๆ **ไม่มีวันถูก sweep** · retry เริ่มจาก tenant แรกใหม่เสมอ | ❌ เห็นทางเดียวคือ DLQ ที่ไม่มีใครเฝ้า |

**ทั้ง 4 ข้อคือปัญหาคลาสเดียวกัน ไม่ใช่ 4 บั๊กแยกกัน**
→ โจทย์ของ Phase 39 คือออกแบบ **คำตอบเชิงโครงสร้างต่อคลาสนี้** ไม่ใช่ปะทีละรู

## 4. ข้อเท็จจริงเชิงเทคนิคที่จำกัดทางเลือก (สำคัญมาก)

1. **Vercel env ที่ติดแท็ก `Sensitive` = write-only** — อ่านค่ากลับไม่ได้ทั้งใน UI และ CLI
   ⇒ **gate ที่ออกแบบให้อ่านค่า env มาเทียบ ทำไม่ได้บนแพลตฟอร์มนี้** เหลือทางเดียวคือ probe ที่ runtime
2. **`NEXT_PUBLIC_*` ถูก inline ตอน build** → ต้องตรวจที่ artifact ที่ deploy จริง · แก้ค่าแล้วต้อง redeploy
   ส่วน **server env อ่านตอน runtime** → ต้องตรวจที่ runtime · **ตรวจผิดชั้น = false PASS**
3. **Vercel ผูก env snapshot กับ deployment** → เปลี่ยน env แล้วต้อง redeploy ถึงจะมีผลกับตัวที่ live
4. **QStash log/DLQ retention = 3 วัน** → หลักฐานหายเอง · ต้องคัดออกมาเก็บทันทีที่เห็น
5. **`WebhookDelivery` ผูก `onDelete: Cascade` กับ `WebhookEndpoint`** → เก็บกวาด endpoint = ลบหลักฐานทิ้งพร้อมกัน
6. โปรเจกต์เป็น **multi-tenant** — ทุก query ต้องมี `tenantId` scope · ห้ามรับ `tenantId` จาก client
   แต่ **readiness เป็นเรื่องระดับระบบ ไม่ใช่ระดับ tenant** → ต้องออกแบบให้ไม่หลุดเข้า tenant pipeline
7. **prod ไม่มีลูกค้าจริง** — ความเสียหายต่อผู้ใช้วันนี้ = 0 · เกณฑ์ตัดสินคือ **"ต้นทุนของการปล่อยไว้"**
   ไม่ใช่ "มีคนเจ็บอยู่ตอนนี้"

## 5. สิ่งที่ขอให้ออกแบบ

### P2 — กลไกพิสูจน์ว่า server-side resource ใช้งานได้จริงบน production

ข้อเสนอตั้งต้นคือ `GET /api/health/readiness` **แต่ไม่ผูกมัดว่าต้องเป็นรูปนี้** —
ถ้ามีรูปที่ดีกว่า ให้เสนอพร้อมเหตุผล

**สิ่งที่ต้องจริงเสมอไม่ว่าจะออกแบบเป็นรูปไหน:**

- ต้อง **เรียก provider จริง** ไม่ใช่ตรวจการมีอยู่ของ env (§ 2.3 อธิบายว่าทำไม)
- ⛔ **ห้ามมี key ของ `NEXT_PUBLIC_*` อยู่ในนั้น** — server อ่าน runtime env ได้เสมอ → false PASS (§ 4 ข้อ 2)
- ต้องไม่ทำให้ secret หลุดออกทาง response

### P3 — observable fail-soft

fail-soft ที่ถูกต้องต่อผู้ใช้ **แต่ต้อง fail-loud ต่อผู้ดูแล**
ตัวอย่างที่เคยคิดไว้: ให้ UI ปล่อย marker ที่ smoke test assert ได้ว่า "ต่อจริง" ไม่ใช่แค่ "หน้าไม่พัง"
แต่หลักการต้องใช้ได้กับทุกกรณีใน § 3 ไม่ใช่แค่ UI

### และตอบให้ครอบคลุมทั้ง 4 ข้อใน § 3

ถ้าออกแบบแล้วครอบได้แค่ข้อ 1 ให้บอกตรง ๆ ว่าข้อไหนต้องแยกงาน และเพราะอะไร

## 6. คำถามออกแบบที่ต้องตอบให้ได้ (แก่นของงาน)

1. **ใครเรียก และเมื่อไหร่** — build-time · post-deploy · ตามรอบ · ตอนมีคนเข้าใช้
   แต่ละจังหวะตรวจคนละชั้นและจับคนละบั๊ก · ถ้าเลือกอย่างเดียวจะพลาดอะไร
2. **⚠️ probe ต้องไม่กินทรัพยากรที่มันปกป้อง** — probe QStash ที่ publish message จริง
   = **กินโควตา 1,000/วัน ที่กำลังจะเป็นสาเหตุตายรอบหน้า** จะแก้ปมนี้ยังไง
3. **⚠️ circular dependency** — ถ้าให้ QStash schedule เป็นตัวเรียก probe แล้ว QStash ตาย
   **probe ก็ไม่ถูกเรียก = เงียบเหมือนเดิม** ใครเฝ้าคนเฝ้า
4. **probe ล้มแล้วบอกใคร** — วันนี้ **ไม่มีคนเฝ้าอะไรเลย** (ไม่มี on-call ไม่มี alerting)
   "fail-loud" ที่ไม่มีหูฟังก็เท่ากับเงียบ · ช่องทางที่เป็นไปได้จริงกับทีมขนาดนี้คืออะไร
5. **แยก "ต่อไม่ได้" ออกจาก "ต่อได้แต่ใกล้หมดโควตา"** — ping สำเร็จตอนโควตาเหลือ 0.1%
   ก็ยัง PASS ทั้งที่กำลังจะตาย → **P2 ต้องตรวจ headroom ไม่ใช่แค่ connectivity**
6. **auth ของ endpoint** — เปิดสาธารณะ = เปิดเผยสภาพ infra ให้คนนอก ·
   auth ด้วย QStash signature = circular อีกชั้น · ใช้ secret ก็เพิ่ม env ที่ต้องดูแลอีกตัว
7. **ต้นทุนของ false alarm** — probe ที่เตือนบ่อยเกินจะถูกเมิน แล้วกลายเป็นเงียบอีกแบบ
   จะกัน alert fatigue ยังไงในเมื่อไม่มีคนเฝ้าประจำ
8. **เส้นแบ่งกับ observability สำเร็จรูป** — ทำไมไม่ใช้ Sentry / Better Stack / Checkly ไปเลย
   ถ้าจะใช้ ส่วนไหนยังต้องเขียนเอง · ถ้าไม่ใช้ เพราะอะไร (ตอบให้ชัด ไม่ใช่เลี่ยง)
9. **P2 ทำงานอย่างไรกับ multi-tenancy** — readiness เป็น global แต่ระบบทั้งระบบสร้างบนสมมติฐาน
   ว่าทุกอย่างมี `tenantId` (§ 4 ข้อ 6)
10. **จะรู้ได้ยังไงว่า P2 เองยังทำงานอยู่** — ถ้า P2 ตายเงียบ เรากลับไปจุดเริ่มต้นพอดี

## 7. ทางที่ลองแล้วและถูกปฏิเสธ (ห้ามเสนอซ้ำ)

| ทาง | ทำไมตกไป |
| --- | --- |
| ตรวจว่า env มีค่า / ไม่ว่าง / สะกดถูก | § 2.3 — ให้ PASS ทั้งที่ระบบตายสนิท |
| อ่านค่า env จาก Vercel มาเทียบ | § 4 ข้อ 1 — `Sensitive` = อ่านกลับไม่ได้ |
| ใช้ readiness endpoint ยืนยัน `NEXT_PUBLIC_*` | server อ่าน runtime env ได้เสมอ → false PASS |
| assert เฉพาะใน CI (`ci.yml`) | CI build ≠ artifact ที่ deploy จริง |
| ผูก gate ไว้ที่ `package.json` `build` อย่างเดียว | `vercel.json buildCommand` override ได้ (และ Vercel Dashboard override `vercel.json` ได้อีกชั้น) |
| เขียน "วิธีตรวจ" ลง docs แล้วถือว่าปิดงาน | **docs ไม่ใช่ gate** — Phase 38 พิสูจน์แล้วว่าคนไม่ทำตาม |
| escape hatch ที่เป็นคำแนะนำในเอกสาร ("แก้ไฟล์ชั่วคราวแล้ว revert") | คนลืม revert = เสีย gate ถาวรแบบเงียบ · **escape hatch ต้องเป็นกลไกในโค้ด** |
| assertion ที่มี fallback ฝังใน source | fail ไม่ได้เลย = แถวเขียวปลอม **ซึ่งแย่กว่าไม่มีแถว** (สร้างความมั่นใจปลอม) |

## 8. เกณฑ์ตัดสินว่าออกแบบนี้ใช้ได้

> ทดสอบด้วยเคสจริงที่เกิดขึ้นแล้ว ไม่ใช่เคสสมมติ

1. **เกณฑ์หลัก:** เอา P2 ที่ออกแบบไปรันกับสภาพใน § 2.3 (env ทุกตัวที่รู้จักครบและถูกต้อง
   แต่ `QSTASH_URL` ไม่มี และไม่มีใครรู้ว่าต้องมี) แล้วได้ **PASS** → **ออกแบบใหม่**
2. รันกับสภาพ "โควตาเหลือ 0.1%" แล้วได้ PASS → ยังไม่ครอบ § 6 ข้อ 5
3. ถ้า QStash ตายทั้งบริการ P2 ต้องยัง **ส่งเสียงถึงคนได้** → ถ้าเงียบ = ยังไม่ครอบ § 6 ข้อ 3
4. ต้องบอกได้ว่า **จะรู้ได้ยังไงว่า P2 เองยังไม่ตาย** (§ 6 ข้อ 10)
5. ทุกข้อเสนอต้องระบุ **ต้นทุน** (เวลาเขียน · เงิน · โควตา · ภาระดูแลต่อเนื่อง) —
   ทีมนี้คือคนเดียว + AI ไม่มี on-call **ข้อเสนอที่ดูแลไม่ไหวถือว่าไม่ผ่าน**

## 9. รูปแบบผลลัพธ์ที่ต้องการ

1. **สรุปแนวทาง 1 ย่อหน้า** — ตัดสินใจอะไร เพราะอะไร
2. **ทางเลือกอย่างน้อย 2 ทาง พร้อมข้อดี/ข้อเสีย/ต้นทุน** และบอกว่าเลือกทางไหน เพราะอะไร
   (เสนอทางเดียวโดยไม่เทียบ = ยังไม่ได้ออกแบบ)
3. **คำตอบต่อคำถามทั้ง 10 ข้อใน § 6** — ข้อไหนตอบไม่ได้ให้บอกตรง ๆ ว่าต้องรู้อะไรเพิ่ม
4. **ตารางว่าครอบข้อไหนใน § 3 บ้าง** — ข้อที่ไม่ครอบต้องบอกว่าแยกเป็นงานอะไร
5. **ลำดับงานที่ทำได้จริง** — อะไรทำก่อน · อะไรรอได้ · อะไรที่ต้องมีก่อนถึงเริ่มข้อถัดไป
6. **สิ่งที่ออกแบบนี้ยัง _ไม่_ ครอบ** — เขียนให้ชัด อย่าให้คนอ่านเข้าใจว่าปิดหมดแล้ว
   (บทเรียนของโปรเจกต์: เอกสารผิดได้ทั้งสองทิศ — "เขียนว่าผ่านทั้งที่ยังไม่ตรวจ"
   และ "เขียนว่ายังไม่ทำทั้งที่ทำไปแล้ว")
