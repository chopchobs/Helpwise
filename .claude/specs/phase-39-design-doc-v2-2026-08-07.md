## 0. ขอบเขต

เอกสารนี้ตอบ §5–§9 ของ design brief: ออกแบบ P2 (พิสูจน์ว่า server-side resource ใช้งานได้จริง) และ P3 (fail-soft ที่ observable) ให้ครอบ 4 กลไกใน §3 เท่าที่ทำได้ และระบุตรง ๆ ว่าข้อไหนต้องแยกงาน ไม่มีการเลือก library หรือ implementation — ทุกอย่างอยู่ในระดับกลไกและ data shape

## 1. สรุปแนวทาง

P2 ไม่ใช่ endpoint เดียวที่ตรวจ "ต่อได้ไหม" แต่เป็นกลไกสองชั้นที่แก้คนละปัญหา: **active probe** ที่เรียก provider จริงแบบ read-only (ไม่กินโควตาที่กำลังปกป้อง) เพื่อตอบ "ต่อได้ไหม และเหลือ headroom แค่ไหน" กับ **execution heartbeat** ที่บันทึกทุกครั้งที่กลไกภายใน (sweep, worker) รันจบสำเร็จจริง เพื่อตอบ "มันทำงานจริงหรือแค่ provider ยังไม่ตาย" — เพราะเคสวันนี้พิสูจน์แล้วว่า provider ปกติ (schedule ว่างเปล่าไม่ใช่ QStash พัง) ก็ยังทำให้ feature ไม่เคยรันได้ ทั้งสองชั้นถูกเรียกจาก **GitHub Actions** ซึ่งเป็นโครงสร้างเดียวที่อยู่นอก Vercel และนอก QStash พร้อมกัน แก้ปัญหา circular dependency ใน §6 ข้อ 3 โดยไม่ต้องเพิ่มบริการใหม่ ผลลัพธ์ถูกส่งเป็น alert เข้า Slack/Discord webhook — ช่องทางเดียวที่เหลืออยู่จริงสำหรับทีมขนาดนี้ตาม inventory ใน §1 ของ brief ต้นทุนรวมคือ $0/เดือน ใช้ของที่มีอยู่แล้วทั้งหมด (Postgres, GitHub Actions) บวก webhook ใหม่ 1 ตัว

## 2. ทางเลือก ≥ 2 ทาง

### ทางเลือก A — Active probe endpoint เดี่ยว

endpoint เดียว (`GET /api/ops/readiness`) ที่ยิง read-only call ไปหา provider จริงทุกครั้งที่ถูกเรียก (เช่น `GET /v2/schedules` ของ QStash, ping Redis) แล้วตอบสถานะสด ๆ ณ ขณะนั้น ถูกเรียกโดย GitHub Actions ตามรอบ

### ทางเลือก B — Execution heartbeat ล้วน (passive)

ไม่ probe provider เลย แทนที่ทุก worker/sweep เขียนแถว "รันสำเร็จล่าสุดเมื่อไหร่" ลง DB ทุกครั้งที่จบงานจริง แล้ว endpoint แค่อ่าน DB ว่าห่างจากรอบที่ควรรันกี่นาที เกิน threshold = FAIL ไม่มีการเรียก provider เพิ่มเลย ต้นทุน quota = 0 เป๊ะ

| แกน | A · Active probe | B · Heartbeat ล้วน |
| --- | --- | --- |
| จับเคส §2.3 (region ผิด แต่ env ครบ) | ✅ จับได้ตรง — เรียก provider จริงจึงเจอ error region ทันที แม้ไม่มี traffic เลย | ⚠️ จับได้ทางอ้อมเท่านั้น ต้องรอให้ worker/sweep พยายามรันจริงก่อนถึงจะไม่มี heartbeat ให้เห็น |
| กินโควตาที่ปกป้องอยู่ไหม (§6 ข้อ 2) | ไม่กิน ถ้าจำกัดเฉพาะ read-only call (list/GET) ซึ่งไม่นับใน publish quota — ต้องระวังไม่หลุดไปเรียก endpoint ที่ publish จริง | ไม่กินเลย เพราะไม่เรียก provider เพิ่มแม้แต่ครั้งเดียว |
| bootstrap gap | ไม่มี — probe ทำงานได้แม้ feature ยังไม่เคยรันสักครั้ง | 🔴 มี — "ไม่เคยมี heartbeat" ต้องถูก treat เป็น FAIL ตั้งแต่ต้น ไม่งั้นจะเหมือน §2.1 เป๊ะ (ไม่เคยเริ่ม = อ่านไม่ออกว่าผิดปกติ) |
| จับ §3 ข้อ 3–4 (near-breach / per-tenant sweep) | ❌ ไม่เห็น — provider (QStash) ปกติดีในสองเคสนี้ ปัญหาอยู่ใน logic ของแอปเอง | ✅ เห็นได้ ถ้าทำ heartbeat ระดับ (tenant, mechanism) ไม่ใช่แค่ระดับ mechanism |
| ต้นทุนสร้าง | ต่ำ — endpoint เดียว ไม่ต้องแก้ business code | สูงกว่า — ต้องแทรก instrumentation ในทุก call site ที่อยากเฝ้า |

**เลือก: hybrid ของทั้งสอง ไม่ใช่เลือกทางเดียว** — เหตุผลคือทั้งสองจับคนละคลาสของความล้มเหลวใน §3 พอดี: A จับ #1–#2 (ปัญหาที่ provider) B จับ #3–#4 (ปัญหาที่ logic ของแอปเอง แม้ provider ปกติ) ทางใดทางหนึ่งเดี่ยว ๆ ครอบได้แค่ครึ่งเดียวของ §3 การเลือกทางเดียวจะขัดกับ §5 ที่บังคับตอบให้ครอบทั้ง 4 ข้อหรือระบุชัดว่าข้อไหนต้องแยกงาน — ถ้าไม่ใช้ B เลย ข้อ 3–4 จะกลายเป็น "ไม่ครอบเลย" ทั้งที่ B ปิดช่องว่างนั้นได้ด้วยต้นทุนที่ยังอยู่ในเพดาน (ดู §7)

## 2.5 P3 — fail-soft ที่ observable (เพิ่มใน v2)

v1 มีแต่ heartbeat แล้วโยน event log ไปแถวท้ายของลำดับงาน ⇒ คนอ่านจะเข้าใจว่า Phase 39 ครอบ P3 ทั้งที่จริงครอบแค่ P2 · v2 แยก P3 เป็น 3 ชั้น: หลักการไม่ลด scope · ขอบเขตบังคับใช้แคบโดยตั้งใจ · กลไกกันตกหล่นที่บังคับได้จริง

### (ก) หลักการ — ประโยคเดียว ใช้กับทุก catch ในระบบ

ทุก catch block ที่กลืน error ต้องเขียน event ลงที่ที่ P2 อ่านได้ — fail-soft ต่อผู้ใช้ แต่ห้าม fail-silent ต่อ P2

หลักการนี้ไม่ลด scope — ใช้กับทุก catch ทั้งโปรเจกต์ สิ่งที่แคบคือ**ขอบเขตที่บังคับในเฟสนี้** ไม่ใช่ตัวหลักการ

### (ข) ขอบเขตบังคับใช้ใน Phase 39 — แคบโดยตั้งใจ และจะรู้ได้อย่างไรว่าครบ

บังคับเฉพาะ swallow site บนเส้นทางของ 4 กลไกใน §3 ของ brief เท่านั้น **แต่การระบุขอบเขตต้องไม่พึ่งการไล่ดูด้วยตา** — การตกหล่น 1 จุด = fail-silent 1 จุดที่ P2 มองไม่เห็น = รูเดิมที่ทำให้เกิดเคสนี้ ⇒ วิธีระบุต้องเป็นการ**กำหนดเป็นขอบเขตของไฟล์ (path scope) แล้วให้เครื่องตรวจเป็นคนไล่เองว่าในขอบเขตนั้นมี catch กี่จุด** ไม่ใช่คนนั่งนับเอง:

1. **นิยามขอบเขตจาก entry point ไม่ใช่จากการ grep** — 4 เส้นทางคือ: จุด publish เข้า queue · dispatch webhook · route `sla-sweep` · route `webhook-deliver` ⇒ ขอบเขต = **ทุกโมดูลที่เส้นทางเหล่านี้เรียกถึง** ไม่ใช่รายชื่อที่คนนึกออกได้
2. **ตั้งกฎเป็น default-on ไม่ใช่ opt-in** — กฎครอบไฟล์ในขอบเขตทั้งหมดโดยอัตโนมัติ การยกเว้นต้องเขียนไว้ทีละจุดอย่างชัดเจน ⇒ **ไฟล์ใหม่ที่เพิ่มเข้าเส้นทางนี้ถูกครอบโดยปริยาย** คนไม่ต้องจำว่าต้องเพิ่มชื่อเข้าลิสต์ (จุดตายของ allowlist คือต้องจำเติม)
3. **ความครบพิสูจน์ด้วย build ไม่ใช่ด้วยการนับ** — ถ้ามี catch ในขอบเขตที่ไม่เขียน event และไม่ rethrow → กฎใน (ค) ทำให้ CI แดง ⇒ จำนวนจุดที่ต้องแก้เป็นผลลัพธ์ของเครื่องมือ ไม่ใช่ตัวเลขที่เอกสารนี้เดา

**เอกสารนี้ไม่ระบุจำนวน swallow site** เพราะยังไม่ได้ตรวจทีละไฟล์ — สเกลของทั้งโปรเจกต์ตามที่รีวิวระบุ (`catch` 230 บรรทัด / 97 ไฟล์ ใน `src/lib` + `src/app`) ใช้อธิบายว่าทำไม (ข) ต้องแคบ และทำไมต้องมี (ค) — **ไม่ใช่เป้า และไม่ใช่ฐานของการประมาณต้นทุน** ต้นทุนจริงจะรู้หลังรันกฎครั้งแรกแล้วเห็นรายการจริง

### (ค) กันตกหล่นในอนาคต — ต้องเป็นกลไก ไม่ใช่เอกสาร

กลไกที่เสนอ: **static check ระดับ source ที่รันใน CI ของ GitHub Actions** — เจอ catch ในขอบเขตที่ไม่ rethrow และไม่เขียน event ⇒ **build แดง merge ไม่ได้** คนจึงเพิ่ม catch ที่กลืน error เข้ามาเงียบ ๆ ไม่ได้อีก

**ทำไมนี่ไม่ซ้ำกับ §7 ของ brief ที่ปฏิเสธ "assert เฉพาะใน CI":** ข้อที่ถูกปฏิเสธคือการเอา CI ไป assert *คุณสมบัติของ artifact/environment ที่ deploy จริง* ซึ่ง CI ไม่มีทางรู้ — แต่กฎนี้ assert **คุณสมบัติของ source เอง** ซึ่ง CI เป็นชั้นที่ถูกต้องที่สุด คำถาม "artifact ที่ deploy จริงเป็นตัวเดียวกันไหม" ไม่เกิดขึ้นเลย · ส่วนชั้น runtime มี P2 รับผิดชอบอยู่แล้ว — **สองชั้น ไม่มีชั้นไหนอ้างว่าทำหน้าที่ของอีกชั้น**

⚠️ ข้อจำกัดที่ต้องเขียนไว้: กฎนี้บังคับได้เฉพาะ**การมี event ถูกเขียน** ไม่ได้บังคับว่า event นั้น*มีความหมายที่ถูก* — กันแถวเขียวปลอมชั้นที่สองได้ด้วย P2 เท่านั้น (event ที่เขียนแล้วต้องมีคนอ่านจริง ไม่งั้นก็เป็น log ที่ไม่มีใครอ่านอีกแบบ)

## 2.6 ขอบเขต probe ที่เพิ่ม: Supabase realtime JWT (เพิ่มใน v2)

handoff Phase 38 ระบุว่า P2 ต้องปิด server env อีกชุด: `SUPABASE_REALTIME_JWT_PRIVATE_KEY` / `SUPABASE_REALTIME_JWT_KID` (ใช้จริงที่ `src/lib/realtime.ts:48,58`) อาการเมื่อขาด: `/api/realtime/token` คืน `500` แต่ client กลืน error → presence ตายเงียบ = failure class เดียวกับ §3

key ชุดนี้**ไม่เข้า pattern "เรียก provider จริง"** เพราะไม่มี endpoint ให้ ping ⇒ probe ที่ทำได้คือ **sign JWT ทิ้งแล้ว verify กลับในเครื่อง** (ไม่กินโควตา ไม่ต้องต่อเน็ต) · ⚠️ **ข้อจำกัดที่ต้องติดมากับแถวนี้เสมอ:** มันพิสูจน์แค่ *PEM parse ได้ + KID มีอยู่* **ไม่ได้พิสูจน์ว่า Supabase ยอมรับ token นั้นจริง** ถ้าไม่เขียนข้อจำกัดนี้ติดไว้ จะกลายเป็นแถวเขียวปลอมที่ §7 ของ brief ระบุไว้ว่าแย่กว่าไม่มีแถว · สิ่งที่พิสูจน์ได้จริงต้องเป็น runtime probe ชั้นถัดไป (เอา token ไปต่อ realtime จริงแล้วดูผล) — **นอกขอบเขต Phase 39** ต้องเขียนไว้ใน §8

เลือกอย่างเดียวพลาดอะไร: post-deploy อย่างเดียวพลาดความเสื่อมหลัง deploy (quota ค่อย ๆ หมด) ส่วน cron อย่างเดียวพลาดว่า "deploy ล่าสุดพังตั้งแต่วินาทีแรก" ช้าไปเท่าความถี่ cron — ทั้งสองจังหวะจำเป็นพร้อมกัน ไม่ใช่เลือกใดเลือกหนึ่ง

### 1ก. 🔴 ทำไม "step ต่อท้าย deploy" ของ v1 ใช้ไม่ได้ และใช้อะไรแทน

ตรวจจาก `.github/workflows/`: มี `ci.yml` ไฟล์เดียว trigger = `push: branches:[main]` + `pull_request` และ**ไม่มี workflow ไหนแตะ Vercel เลย** — deploy วิ่งผ่าน Vercel git integration ต่างหาก ⇒ push ขึ้น main ครั้งหนึ่ง GitHub Actions กับ Vercel build **วิ่งขนานกัน ไม่ใช่ต่อคิวกัน** ⇒ probe ที่ยิงตอนนั้นจะไปเจอ deployment เก่าที่ยังถือ alias อยู่ = **false PASS** และเป็นกับดัก "ตรวจผิดชั้น" ที่โปรเจกต์เตือนตัวเองไว้ ⇒ คำเคลมของ v1 ว่าจะจับ region mismatch "ภายในนาที" ใช้ไม่ได้ตามไปด้วย

ทางที่ใช้ได้ ต้องมีครบ 3 ชั้น:

1. **trigger ที่ถูก** — ใช้ `deployment_status` event ที่ Vercel integration ส่งเข้ามา แทนการต่อท้าย `push` (ยิงเมื่อ deployment เข้าสถานะสุดท้าย ไม่ใช่ตอนเริ่ม) · **ยังไม่พอ** เพราะ event บอกว่า deployment พร้อม ไม่ได้พิสูจน์ว่า production alias ชี้มาที่ตัวนี้แล้ว
2. **ยืนยัน identity ก่อนอ่านผล** — probe ต้องคืน identity ของ deployment ที่กำลังตอบอยู่ (commit sha / deployment id ที่ Vercel inject ให้ตอน build — *ชื่อตัวแปรจริงต้อง confirm กับเอกสาร Vercel ก่อน implement เอกสารนี้ไม่เดาชื่อ*) แล้ว workflow poll production alias จน identity ตรงกับ commit ที่เพิ่ง push ถึงจะถือว่าผล probe เป็นของ deploy รอบนี้
3. **timeout = สัญญาณ ไม่ใช่การข้าม** — poll ครบเวลาแล้ว identity ยังไม่ตรง ⇒ `FAIL` ที่ต้องแจ้ง (แปลว่า deployment ไม่ถูก promote) ห้าม fallback เป็น "ข้ามไปก่อน"

ต้นทุนเพิ่ม = $0 และ**ไม่ต้องใช้ Vercel API token ใหม่** เพราะ identity มาจาก response ของ probe เราเอง ไม่ต้องถาม Vercel

### 2. ไม่กินทรัพยากรที่ตัวเองปกป้อง

**ก. ต้นทุนของ probe เอง** — probe ต้องไม่ publish message จริงเด็ดขาด ใช้เฉพาะ read/list call (`GET /v2/schedules`, `/v2/queues`, `/v2/keys`) ซึ่งเป็นชนิดเดียวกับที่ incident ใช้วินิจฉัยแบบ read-only ใน §2.2–2.3 ของ phase-38 **แก้จาก v1:** ที่ v1 เขียนว่า "จึงยืนยันได้ว่าไม่กินโควตา" เป็นข้อสรุปที่**ไม่มีใครตรวจ** — หลักฐานที่มีบอกแค่ว่า call นั้นไม่ publish message ไม่ได้บอกว่าผู้ให้บริการไม่นับ และ free tier ไม่มี quota API ให้ตรวจย้อน ⇒ ถือเป็น **สมมติฐานที่ยังไม่ verify** และ budget แบบเคสแย่สุด (สมมติว่านับทุก call):

| รายการ | msg/วัน | % ของโควตา Free 1,000 |
| --- | --- | --- |
| probe cron ทุก 15 นาที | 96 | 9.6% |
| sla-sweep `*/5` ตามปกติ (phase-38 §10.3) | 288 | 28.8% |
| **รวม** | **384** | **38.4%** — ใต้ threshold DEGRADED (80%) |

ถ้าสมมติฐานผิดจริง ดีไซน์ไม่ตาย แต่ต้องขยับ 2 จุด: (1) ลดความถี่ cron 15 → 30 นาที (96 → 48/วัน) (2) ให้รอบปกติอ่านเฉพาะ heartbeat จาก DB (ชั้น B ไม่แตะ provider เลย) แล้วเหลือ live probe เฉพาะรอบ post-deploy กับรอบที่สถานะไม่ใช่ OK — ทั้งสองจุดเป็นการปรับค่า ไม่ใช่เปลี่ยนโครง

**ข. วัด headroom ยังไง — 🔴 v1 ผิด แก้ทั้งกลไก** v1 นับ publish ที่แอปเรียกเอง ซึ่ง**มองไม่เห็น retry ของ QStash**: เคส sweep พังต่อเนื่องที่ `*/5` แอปเรียกเอง 288/วัน แต่ retry default 3 ทำให้ของจริง **1,152/วัน** (phase-38 §10.3) ⇒ counter อ่านได้ 28.8% → OK ในนาทีที่ใช้จริง 115.2% = **false-PASS เต็มรูปแบบ** ตกเกณฑ์ §8 ข้อ 2 ของเอกสารเอง ⇒ ย้ายจุดนับไปที่ **inbound delivery attempt** เพราะ retry ของ QStash วิ่งเข้า endpoint ของเราเองทุกครั้ง จึงนับเห็นครบ (counter เป็นยอดสะสมรายวันตาม UTC เทียบกับเพดาน 1,000/วัน)

**ข-1. นับ ณ จุดไหน — เลือก: หลัง verify signature** (นับทันทีที่ signature ผ่าน *ก่อน* เข้า business logic ⇒ attempt ที่ route ตอบ `500` ก็ถูกนับไปแล้ว) เหตุผลที่ไม่เลือกนับก่อน verify ทั้งที่นับครบกว่า: จุดนั้นเปิดให้ใครก็ได้ POST เข้ามาดันตัวเลขทะลุ threshold → alert ปลอมรัว ๆ → alert fatigue ซึ่ง brief §6 ข้อ 7 เตือนไว้เอง — ความเสียหายนั้น**ทำลายระบบเตือนทั้งระบบ** ส่วนสิ่งที่เสียจากการนับหลัง verify ชดเชยได้ด้วยตัวนับตัวที่สอง (ข-2) **ตัวเลขของเคสจริง:** retry ของ QStash แนบ signature ที่ถูกต้องเสมอ ⇒ 1,152 attempt/วันผ่าน verify ทั้งหมด ⇒ counter อ่านได้ **1,152 = 115.2%** → เกิน 100% ⇒ **FAIL** (เพดานสองชั้น: DEGRADED ที่ 80% · FAIL ที่ 100%) — เคสที่ v1 ตอบ OK ตอนนี้ตอบ FAIL

**ข-2. ชดเชยด้านที่เสียไป** — attempt ที่ verify ไม่ผ่านยังกินโควตาจริงถ้ามาจาก QStash (เคส signing key ไม่ตรง = `401` ทุก attempt) ⇒ นับ "inbound ที่ verify ไม่ผ่าน" เป็น **counter ตัวที่สอง แยกกันคนละตัว** · ไม่เอาไปรวมในตัวเลขโควตา (กันการดันตัวเลขจากคนนอก) แต่ให้มีผลต่อสถานะของตัวเอง: ค่ามากกว่าศูนย์ต่อเนื่อง = **FAIL ทันที** เพราะความหมายมีแค่สองอย่างและต้องรู้ทั้งคู่ (signing key ไม่ตรง / มีคนยิงมั่วเข้า worker endpoint) และตลอดช่วงที่มันไม่เป็นศูนย์ ตัวเลขโควตาถูก mark ว่า "ต่ำกว่าความจริง" และ**ห้ามสถานะรวมเป็น OK**

**ข-3. เคสโควตาหมดจริง → QStash หยุด deliver → counter เงียบเหมือนดีขึ้น** ⇒ ดีไซน์นี้**ไม่อนุญาตให้ "counter ต่ำ" ผลิตสถานะ OK ได้เลย** · OK ต้องมาจากหลักฐานเชิงบวกเท่านั้น คือ heartbeat ของทุก mechanism ที่เฝ้าอยู่ต้องสดภายในหน้าต่างที่คาด (ชั้น B) ⇒ โควตาหมด: publish ถูกปฏิเสธ → ไม่มี delivery → heartbeat ของ sla-sweep และ webhook worker ค้างเก่า → **FAIL ภายในหน้าต่างเดียว** ไม่ว่า counter จะอ่านได้เท่าไร (นี่คือเหตุผลเชิงโครงสร้างที่ชั้น A อย่างเดียวไม่พอ)

### 3. Circular dependency — ใครเฝ้าคนเฝ้า

ตัวกำหนดจังหวะ (scheduler) ต้องไม่ใช่ QStash — ใช้ GitHub Actions ซึ่ง inventory ใน §1 ของ brief ยืนยันแล้วว่า "อยู่นอก Vercel และนอก QStash = ไม่ตายพร้อมกัน" ถ้า QStash ตายทั้งบริการ: probe (ทางเลือก A) จะได้ error จาก provider ตรง ๆ → GitHub Actions เห็น response ผิดปกติ (หรือ timeout) → alert ยิงเข้า Slack ได้ตามปกติ เพราะ GitHub Actions เองไม่ได้พึ่ง QStash ในการรันตามรอบ นี่คือคำตอบของเกณฑ์ §8 ข้อ 3 โดยตรง

### 4. Probe ล้มแล้วบอกใคร

ช่องทางเดียวที่ผ่านเกณฑ์ทั้งหมดของ brief เอง (ไม่ใช่อีเมล — circular ตาม §1 ของ brief, ไม่ใช่ on-call — ทีมไม่รับ): Slack/Discord incoming webhook ต้นทุนตามที่ inventory ระบุไว้แล้วคือ webhook 1 ตัว + env 1 ตัว ฟรี GitHub Actions step ที่ตรวจ FAIL แล้ว POST เข้า webhook นี้โดยตรง เสริมอีกชั้นแบบไม่มีต้นทุนเพิ่ม: ถ้า workflow เอง crash (ไม่ใช่ probe fail แต่ workflow รันไม่จบ) GitHub จะส่ง notification ของตัวเองไปหา repo collaborators โดยอัตโนมัติอยู่แล้ว — เป็น safety net ชั้นสุดท้ายที่ไม่ต้องตั้งอะไรเพิ่ม (ดูข้อ 10)

### 5. แยก "ต่อไม่ได้" ออกจาก "ต่อได้แต่ใกล้หมดโควตา"

สถานะต้องเป็น 3 ระดับ ไม่ใช่ boolean: **OK** (connect สำเร็จ + headroom เหนือ threshold) · **DEGRADED** (connect สำเร็จ แต่ self-metered counter เกิน threshold ที่ตั้งไว้ห่างจาก 0 พอสมควร เช่น ใช้ไปแล้วเกิน 80% ของโควตารู้จัก) · **FAIL** (connect ไม่สำเร็จเลย) การตั้ง threshold ให้ห่างจาก 100% พอสมควรทำให้เคส "เหลือ 0.1%" ตกอยู่ใน DEGRADED (หรือ FAIL ถ้าตั้งเพดานสองชั้น) มาก่อนจะถึงศูนย์แน่นอน — นี่คือคำตอบของเกณฑ์ §8 ข้อ 2 โดยตรง

### 6. Auth ของ endpoint

**แก้จาก v1:** เส้นแบ่งหลักไม่ใช่ "เห็นรายละเอียดแค่ไหน" แต่คือ **"ใครมีสิทธิ์ทำให้เกิด outbound call"** — v1 ปล่อยให้ทุก request ที่ไม่ auth ยิง provider จริง ซึ่งแปลว่าคนนอกยิงรัว ๆ แล้วกินโควตาที่ probe ปกป้องอยู่ได้ (กับดัก §6 ข้อ 2 เป๊ะ ต่างแค่คนกินไม่ใช่เรา)

- **shape ที่ไม่ auth** — เสิร์ฟ**สถานะล่าสุดที่เก็บไว้ใน DB เท่านั้น** (คำสถานะ 1 คำ + เวลาที่ตรวจล่าสุด) **ห้าม trigger probe สดเด็ดขาด** ⇒ ยิงรัว ๆ ได้แค่ query DB ของเราเอง ไม่เกิด outbound call แม้แต่ครั้งเดียว
- **shape ที่ auth** (shared-secret header, env ใหม่ 1 ตัว) — เห็นรายละเอียดเต็ม และเป็นทางเดียวที่ทำให้เกิด probe สด · ผู้ใช้จริงคือ GitHub Actions
- **กันแม้ secret หลุด** — live probe มี minimum interval (เช่น 1 ครั้ง/5 นาที) เรียกถี่กว่านั้นได้ค่าที่เก็บไว้แทน ⇒ เพดาน outbound call ต่อวันคงที่ ไม่ขึ้นกับจำนวนผู้เรียก ⇒ ตัวเลข 96/วัน ใน (ก) ข้างบนเป็นเพดานจริง ไม่ใช่ค่าประมาณ
- **ไม่ใช้ QStash signature เป็น auth** — circular ตามที่ §6 ข้อ 6 เตือน (endpoint ต้องตอบได้แม้ QStash ตายสนิท)

### 7. กัน alert fatigue

**เพิ่มใน v2:** สถานะต้องมี **STALE** ด้วย (ไม่มีผลตรวจใหม่เกิน N รอบที่คาดไว้) เพราะ transition-only + cron ที่ข้ามรอบ = ไม่มีผล = ไม่มี transition = เงียบ (ดูข้อ 10) · STALE เป็นสถานะจริงที่คำนวณจากอายุของผลตรวจล่าสุด ⇒ `OK → STALE` เป็น transition ที่ยิง alert ได้ตามกฎเดิม **โดยไม่ต้องเลิกกฎ transition-only**

แจ้งเฉพาะตอน**เปลี่ยนสถานะ** (transition) ไม่ใช่ทุกครั้งที่ poll — เก็บสถานะล่าสุดไว้ 1 ค่า (DB แถวเดียวก็พอ) เทียบกับผลรอบนี้ ถ้าเหมือนเดิมไม่ส่งอะไร ส่งเฉพาะ OK→DEGRADED, DEGRADED→FAIL, และ FAIL→OK (recovery ก็ต้องแจ้ง ไม่งั้นจะไม่รู้ว่าจบปัญหาแล้วหรือยัง) กฎเดียวนี้ตัด noise ส่วนใหญ่ทิ้งได้เพราะสถานะปกติควรอยู่นิ่งเป็นส่วนใหญ่ของเวลา

### 8. เส้นแบ่งกับ Sentry / Better Stack / Checkly

**Sentry (error tracking)** ตอบโจทย์นี้ไม่ได้โดยธรรมชาติ — ปัญหาทั้งหมดใน §3 คือ error ที่ถูก*กลืนโดยเจตนา* (fail-soft ที่ถูกต้อง) Sentry เห็นเฉพาะสิ่งที่ throw ออกมาไม่ถูกจับ ถ้าจะให้ Sentry เห็นก็ต้องเพิ่มจุด capture ที่ catch block เอง ซึ่งพอทำถึงขั้นนั้นก็เขียนลง DB ของตัวเองได้เลยโดยไม่ต้องเพิ่ม vendor **Checkly / Better Stack (synthetic monitoring)** ตรงกับ pattern ที่ต้องการที่สุด (external pinger + alert) แต่เป็น vendor ใหม่ที่ต้องเรียนรู้และผูก account — สิ่งที่มันให้ (dashboard, escalation policy, status page) เกินความจำเป็นของทีมคนเดียวไม่มี on-call ในขณะที่ GitHub Actions + Slack webhook ทำ pattern เดียวกันได้ที่ $0 ด้วยของที่มีอยู่แล้ว **ข้อสรุปสำหรับขอบเขตกว้าง (ระบบ monitoring หลัก): ไม่ใช้วันนี้** — ไม่ใช่เพราะไม่เหมาะ แต่เพราะสิ่งที่มันให้เกินสิ่งที่ทีมขนาดนี้ใช้ได้จริง ถ้ามีลูกค้าจริง + on-call rotation เมื่อไหร่ ควรกลับมาพิจารณาใหม่

**แก้จาก v1 — ขอบเขตแคบต้องตัดสินแยก:** มีงานหนึ่งที่ GitHub Actions ทำแทนตัวเองไม่ได้**เชิงตรรกะ** คือ "เฝ้าว่า P2 ยังรันอยู่ไหม" (ดูข้อ 10) ⇒ สำหรับขอบเขตนี้ **รับ external pinger ฟรี 1 ตัว** ที่มีหน้าที่เดียว: ดึง status shape ที่ไม่ auth ทุก X นาที แล้วเตือนถ้า `lastCheckAt` เก่ากว่าเพดาน · เหตุผลที่ตัดสินต่างจากขอบเขตกว้าง: มันไม่ได้เอา dashboard / escalation policy / status page มาด้วย ไม่มี check ชุดที่สองให้ดูแล (มันอ่าน field เดียวกับที่ P2 เขียนอยู่แล้ว) และไม่กลายเป็นแหล่งความจริงที่สอง · ต้นทุน: free tier $0 · ตั้งครั้งเดียว ~15 นาที · **สิ่งที่ต้องยอมรับ: dependency ภายนอกเพิ่ม 1 ตัว** ถ้าตัดสินว่าไม่รับ third party เลย ⇒ ต้องเขียนตรง ๆ ว่าเคส "P2 หยุดถาวร" **ไม่ถูกครอบ** ไม่มีทางฟรีอื่นที่ปิดได้จริง

### 9. Multi-tenancy

Readiness เป็น global โดยธรรมชาติ (provider connectivity, quota) จึงต้อง**ไม่เดินผ่าน tenant-scoped query pipeline** ตาม §4 ข้อ 6 — endpoint ต้องอยู่นอกเส้นทาง resolve tenant จาก subdomain (proxy ที่ redirect ทุก path บน host ที่ไม่ใช่ tenant ตามที่ phase-38 §8.3 อธิบายไว้ ต้อง special-case path นี้ให้ผ่านโดยไม่ redirect และไม่ต้อง resolve tenant) heartbeat ระดับ per-tenant (สำหรับ §3 ข้อ 4) เก็บ tenantId เป็น attribute ของข้อมูล operational ไม่ใช่ tenant-owned data

**แก้จาก v1:** การไม่ผ่าน helper ที่บังคับ tenant scope คือการ**ขอยกเว้นกฎข้อ 1 ของโปรเจกต์** (cross-tenant leak = บั๊กร้ายแรงที่สุด) v1 ผ่านไปด้วยเหตุผลประโยคเดียว ซึ่งไม่พอ · carve-out ต้องแคบที่สุดเท่าที่ยังใช้งานได้ และล้อมด้วย 3 ข้อบังคับ:

1. response ที่**ไม่ auth** ต้องไม่มี tenant identifier ใด ๆ เลย — ไม่มีชื่อ ไม่มี slug **ไม่มีจำนวน tenant** ไม่มี "tenant ไหนถูก sweep ทิ้ง" · เหลือแค่คำสถานะ + เวลาที่ตรวจล่าสุด (prod นี้เป็น portfolio สาธารณะที่มีคนเปิดจริง "จำนวน tenant ที่ sweep ไม่ถึง" คือข้อมูลที่ไม่ควรเปิด)
2. carve-out ครอบเฉพาะ**ตาราง operational (heartbeat / event) เท่านั้น** · ห้ามแตะตารางธุรกิจใด ๆ · เป็น read path เดียว เรียกได้จากเส้นทาง ops เท่านั้น · ไม่มี write path
3. path นี้**ไม่รับ tenantId จาก client เลยแม้แต่รูปแบบเดียว** (ไม่มี query param ไม่มี body) — คืนมุมมองภายในทั้งชุดให้ผู้เรียกที่ auth แล้วเท่านั้น

เหตุผลว่าทำไมถึงปลอดภัย: กฎเดิมมีไว้กัน "ผู้ใช้ของ tenant A เห็นข้อมูลของ tenant B" ซึ่งเกิดได้ 2 ทาง — รับ tenantId จาก client, หรือ query ที่ลืม scope · ข้อ 3 ตัดทางแรกทิ้งที่ระดับ interface (ไม่มี input ให้ปลอม) ข้อ 2 ตัดทางที่สองด้วยการจำกัดว่าแตะได้แค่ตารางที่ไม่มีข้อมูลธุรกิจของ tenant อยู่เลย และข้อ 1 ตัดผู้เรียกที่ไม่ auth ออกจากสมการทั้งหมด

### 10. ใครรู้ว่า P2 เองยังไม่ตาย

**เขียนใหม่ทั้งข้อใน v2.** คำถามนี้มี 2 ช่วงเวลา แต่เป็น**รูเดียวกัน**: "ข้ามรอบชั่วคราว" กับ "หยุดถาวร" ต่างกันแค่ความยาวของช่วงที่ไม่มีผลตรวจใหม่ ⇒ ตัวชี้วัดเดียวคือ **อายุของผลตรวจล่าสุด (`lastCheckAt`)** ไม่ใช่สองตัวชี้วัด · ทุกครั้งที่ P2 รันสำเร็จให้เขียน `lastCheckAt` ⇒ ใครก็ตามที่อ่าน field นี้ตรวจได้ทั้งสองช่วงด้วยเกณฑ์เดียว

ผู้อ่าน field นี้มี 2 ชั้น และตั้งใจให้ **ซ้อนทับกัน ไม่ใช่ต่อกัน**:

- **ชั้นใน (in-band, $0)** — รอบถัดไปที่รันจริงคำนวณ gap จากรอบก่อน ถ้าเกิน N รอบ ⇒ emit event + alert ทันที ให้ความละเอียดถึงระดับ "ขาดไปกี่รอบ" · ⚠️ **ยอมรับตรง ๆ ว่านี่คือ circular ชั้นใหม่** (GitHub Actions ตรวจ GitHub Actions) จึงครอบ "หยุดถาวร" **ไม่ได้เชิงตรรกะ** เพราะกลไกที่จะตรวจคือกลไกที่หยุดไปแล้ว
- **ชั้นนอก (external pinger ฟรี, ดูข้อ 8)** — ดึง status shape ที่ไม่ auth ทุก X นาที เตือนเมื่อ `lastCheckAt` เก่ากว่าเพดาน ⇒ ครอบทุกช่วงที่ยาวกว่าเพดานนั้น **ไม่ว่า GitHub Actions จะรันหรือไม่** — รวมถึง 60-day auto-disable ซึ่งมีอาการเหมือน "หยุดถาวร" ทุกประการ

**รอยต่ออยู่ตรงไหน และใครเฝ้า:** ตั้งค่าให้ทับกันโดยตั้งใจ — cron 15 นาที · ชั้นในเตือนเมื่อ gap ≥ 2 รอบ (30 นาที) · ชั้นนอกเตือนเมื่อ `lastCheckAt` เก่ากว่า 45–60 นาที ⇒ ช่วง 30–60 นาทีมี**สองชั้นเฝ้าพร้อมกัน** และทุกช่วงที่ยาวกว่า 60 นาทีมีชั้นนอกเฝ้าเสมอแม้ชั้นในตายไปแล้ว ⇒ ไม่มีช่วงเวลาที่ไม่มีใครรับผิดชอบ

เคส workflow crash (คำตอบเดิมของ v1) ยังใช้ได้ — GitHub แจ้ง collaborators เอง — แต่เป็นเคสที่ง่ายที่สุด ไม่ใช่เคสอันตราย · **คำว่า "ทางบรรเทาเดียวที่ทำได้ฟรีคือเช็คลิสต์รายเดือน" ใน v1 ไม่จริง และถูกตัดออกแล้ว** — เช็คลิสต์คนเป็น docs-as-gate ซึ่ง §7 ของ brief ปฏิเสธไปแล้ว

## 5. ทดสอบดีไซน์นี้เองกับเกณฑ์ §8

### ข้อ 1 (หลัก) — รันกับสภาพ §2.3 แล้วต้องไม่ PASS

สภาพ §2.3: env ทุกตัวที่รู้จักครบและถูกต้อง แต่ `QSTASH_URL` ไม่มี → SDK ตกไปใช้ default endpoint (EU) แต่บัญชีอยู่ US → probe ของ A เรียก `GET /v2/schedules` (หรือ endpoint read-only เดียวกัน) ด้วย client ตัวเดียวกับที่โค้ด production ใช้จริง (ไม่ประกอบ URL เองแยกต่างหาก — ต้องใช้ code path เดียวกับที่ publish ใช้ ไม่งั้นตรวจคนละอินสแตนซ์) → ได้ `404 user not found in this region (eu-central-1)` เป๊ะตามที่เกิดจริง → **ผลคือ FAIL ไม่ใช่ PASS** เพราะ probe ไม่เคยเช็คว่า "ตัวแปรมีค่าไหม" เลย มันเช็คว่า "เรียก provider นี้แล้วสำเร็จไหม" ซึ่งเป็นคนละคำถามกับที่ §7 ปฏิเสธไปแล้ว

**วิธี reproduce สภาพ §2.3 มาทดสอบจริง (ไม่ใช่แค่เจตนา):** ไม่ต้องรอ incident ใหม่ — ใช้ Vercel **Preview environment** ซึ่งตาม phase-38 §8.1 ใช้ QStash account/token ชุดเดียวกับ Production อยู่แล้ว

🔴 **prerequisite ที่ v1 ตกไป — ต้องทำก่อน ไม่งั้น rehearsal จะผ่านทุกครั้งโดยไม่ได้ทดสอบอะไรเลย:** ตาม phase-38 §8.3 `*.vercel.app` ทุก host ตอบ `302` ทุก path เพราะ `src/proxy.ts` จับ host ที่ไม่ใช่ tenant แล้ว redirect ทิ้ง (ระบุไว้ว่าเป็นข้อจำกัดถาวรของโปรเจกต์) ⇒ ถ้าไม่ special-case path ของ probe ให้ผ่านก่อน การยิง probe จะโดน redirect และถ้า client ตาม redirect จะได้ `200` จากหน้า marketing แล้วอ่านผิดว่า OK

1. **(prerequisite)** special-case path ของ probe ใน `src/proxy.ts` ให้ผ่านโดยไม่ redirect และไม่ต้อง resolve tenant
2. ไปที่ Vercel env ของ **Preview scope** เอา `QSTASH_URL` ออก (ไม่แตะ Production)
3. trigger deploy ของ Preview
4. ยิง probe endpoint ไปที่ URL ของ Preview deployment นั้น **โดยไม่ให้ client ตาม redirect**
5. **เกณฑ์ตัดสินต้องเป็นเนื้อ response ที่ระบุตัวตนได้** (marker ของ probe + identity ของ deployment ตาม §3 ข้อ 1ก) + สถานะ `FAIL` พร้อม error signature เดียวกับ §2.1 (`not found in this region (eu-central-1)`) · ⛔ **ห้ามใช้ status code เป็นหลักฐาน** (กฎเดียวกับที่ `201` เคยดูเหมือนผ่านทั้งที่ระบบตายสนิท)
6. ถ้าออกมาเป็น `OK` หรืออ่าน marker ไม่ได้ = **ดีไซน์นี้ผิด ต้องแก้ก่อนใช้จริง**
7. ตั้ง `QSTASH_URL` กลับคืน Preview แล้ว redeploy อีกครั้ง ไม่ปล่อย Preview ค้างอยู่ในสภาพพัง

ทั้งหมดนี้ทำได้ที่ $0 ใช้เวลา <5 นาที ไม่กระทบ Production traffic เลย เพราะเป็น scope Preview ล้วน — เป็น rehearsal ที่ทำซ้ำได้ทุกครั้งที่แก้ดีไซน์ ไม่ใช่แค่ทดสอบครั้งเดียวตอนส่งมอบ

### ข้อ 2 — โควตาเหลือ 0.1% ต้องไม่ PASS

ผ่าน — และต้องผ่านด้วย**เคส 1,152/วัน** ด้วย ไม่ใช่แค่เคสเหลือ 0.1%: counter นับที่ inbound delivery attempt ⇒ เคส sweep พังต่อเนื่องอ่านได้ 1,152 = **115.2% → FAIL** (v1 อ่านได้ 288 = 28.8% = OK ซึ่งเป็น false-PASS) · เคสเหลือ 0.1% (ใช้ไป 99.9%) ตก DEGRADED ตั้งแต่ 80% แล้ว · threshold สองชั้นตั้งจากตัวเลขจริงใน phase-38 §10.3 ไม่ใช่เดา: การใช้งานปกติ 288 (28.8%) + probe 96 (9.6%) = 384 (38.4%) ⇒ 80% ห่างจากการใช้งานปกติพอที่จะไม่ noisy และต่ำพอให้เหลือเวลาตอบสนอง

### ข้อ 3 — QStash ตายทั้งบริการต้องยังส่งเสียงได้

ผ่าน — ตอบไว้แล้วใน §3 ข้อ 3 ด้านบน (scheduler = GitHub Actions ไม่ใช่ QStash)

## 7. ไม่ซ้ำ §7 — เช็คสั้น ๆ

ไม่มีข้อไหนใน §7 ที่เห็นว่าถูกปฏิเสธเพราะเข้าใจผิด — เห็นด้วยกับเหตุผลเดิมทั้ง 9 ข้อ ดีไซน์นี้เลี่ยงแต่ละข้อโดยตรง: ไม่เช็คค่า env (เรียก provider จริงเสมอ) · ไม่อ่าน env จาก Vercel มาเทียบ (ไม่แตะ Vercel API เลย) · ไม่มี NEXT_PUBLIC_* ใน endpoint นี้ · ไม่ผูกกับ CI (เรียก URL ของ deployment จริงที่ live ไม่ใช่ container ตอน build) · ไม่ผูกกับ package.json build (ไม่ใช่ build-time gate) · ไม่ใช้ docs เป็น gate (เป็น loop อัตโนมัติที่รันจริงทุกรอบ) · ไม่มี escape hatch แบบคำแนะนำในเอกสาร · ค่าเริ่มต้นเมื่อไม่พบ heartbeat คือ FAIL เสมอ ไม่ใช่ PASS (กัน fallback ที่เขียวปลอม)

## 8. สิ่งที่ดีไซน์นี้ยังไม่ครอบ

- ไม่แก้ root cause ของ §3 ข้อ 3 (near-breach polling window แคบ) — ต้องเปลี่ยนเป็น per-ticket scheduling ตามที่ phase-38 §5.1.1 ระบุไว้แล้วว่าเป็นงานออกแบบแยก
- ไม่แก้ root cause ของ §3 ข้อ 4 (sweep ไม่มี checkpoint) — ต้องเพิ่ม resume logic ให้ sweep เอง เป็นงาน engineering แยก
- **quota:** counter นับหลัง verify จึงมองไม่เห็น attempt ที่ QStash ส่งมาแต่ signature ไม่ผ่าน (เช่น key ไม่ตรง) — ชดเชยด้วย counter ตัวที่สองที่บังคับ FAIL แต่**ตัวเลข headroom ในช่วงนั้นไม่แม่น**
- **สมมติฐานที่ยังไม่มีใคร verify:** read/list call ของ QStash นับโควตาหรือไม่ — free tier ไม่มี quota API ให้ตรวจ จึง budget เคสแย่สุดไว้แทน (384/วัน = 38.4%)
- **Supabase realtime key:** probe พิสูจน์แค่ PEM parse ได้ + KID มีอยู่ **ไม่ได้พิสูจน์ว่า Supabase ยอมรับ token** (§2.6)
- **ชื่อ Vercel system env สำหรับ deployment identity ยังต้อง confirm** กับเอกสาร Vercel ก่อน implement — เอกสารนี้ไม่เดาชื่อมาใส่
- **ช่วง "หยุดถาวร" ของ P2 ครอบได้ก็ต่อเมื่อยอมรับ external pinger** — ถ้าตัดสินไม่รับ third party ช่วงนี้**ไม่ถูกครอบ** และ in-band ช่วยไม่ได้เชิงตรรกะ
- ไม่ครอบ Postmark/SendGrid เพราะยังไม่ตัดสินใจเลือก provider — เพิ่มได้ทันทีด้วย pattern เดียวกันเมื่อตัดสินแล้ว
- ไม่ครอบ traffic-triggered check — prod วันนี้ไม่มี traffic จริงพอเป็นสัญญาณ
