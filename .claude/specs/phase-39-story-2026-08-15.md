## 3. การไล่ — **หลักฐานถูกถอน 3 รอบ**

ส่วนนี้คือหัวใจของเรื่อง ไม่ใช่ส่วนประกอบ **ทุกรอบที่ถอน คือรอบที่เรา "รู้แล้ว" ไปก่อนที่จะรู้จริง**

### รอบที่ 1 — ข้อสรุปที่พิสูจน์ตัวเอง (tautology)

ข้อสรุปแรกคือ *"cron มาสาย"* หลักฐานคือ **ผู้เฝ้าบอกว่าตัวเองค้าง**

แต่เกณฑ์ที่ผู้เฝ้าใช้ตัดสินว่า "ค้าง" **คำนวณมาจากคาบที่เราประกาศไว้ในไฟล์ workflow เอง**
⇒ ถ้าคาบที่ประกาศผิด ผู้เฝ้าจะบอกว่าตัวเองค้าง**เสมอ** ไม่ว่าความจริงเป็นอย่างไร
⇒ **หลักฐานกับข้อสรุปเป็นสิ่งเดียวกัน** — มันพิสูจน์ได้แค่ว่า *ตัวเลขสองตัวในไฟล์ไม่ตรงกัน*
ซึ่งเป็นเรื่องที่รู้อยู่แล้ว **ถอน**

### รอบที่ 2 — เศษที่คิดว่ารอด

รอบถัดมาพยายามกู้บางส่วนของตารางเดิมไว้ ด้วยเหตุผลว่า *"ส่วนนี้ไม่ได้อาศัยสมมติฐานที่ล้มไป"*

ตรวจซ้ำแล้วพบว่า **ทั้งตารางตั้งอยู่บนสมมติฐานเดียวกันหมด**
คือความเชื่อว่า GitHub ยิงตามกริด `:00/:15/:30/:45` แล้วแต่ละใบ "ถูกหน่วง" ออกไป
พอสมมติฐานนั้นตาย **ทุกแถวตายพร้อมกัน** ไม่มีเศษไหนรอด **ถอนทั้งตาราง**

> 🔑 บทเรียนของรอบนี้: เวลาสมมติฐานร่วมล้ม อย่าหาว่า *"อะไรยังรอด"*
> ให้ถามว่า *"อะไรที่ไม่ได้อาศัยมันเลย"* — สองคำถามนี้ให้คำตอบไม่เหมือนกัน

### รอบที่ 3 — reviewer อ่านข้อมูลของตัวเองผิด

รอบสุดท้าย มีข้อโต้แย้งว่า histogram ของนาทีที่ run เกิด **ดูกระจายสม่ำเสมอ** ⇒ ไม่มี pattern

ผิดสองชั้น:
1. **"ก้าวของนาที" มีสามนิยาม** (circular / forward / linear) ที่ให้ตัวเลขต่างกันมาก
   และ **baseline ของแต่ละนิยามไม่เท่ากัน** — การเทียบข้ามนิยามให้คำตอบที่ผิดแน่นอน
2. **ตัวอย่างไม่เป็นอิสระต่อกัน** (run ที่ติดกันมีนาทีใกล้กันมากกว่าการสุ่มอย่างชัดเจน)
   ⇒ เครื่องมือใด ๆ ที่สมมติความอิสระ **ใช้ไม่ได้ รวมถึงการดูด้วยตา**

⇒ วิธีปิดช่องนี้ถาวร: **เขียนนิยามลงเป็นโค้ด** (`analyze.mjs`) แทนที่จะอธิบายด้วยคำพูด
ทุกวันนี้ถ้าเถียงกันว่า *"median แบบไหน"* คำตอบอยู่ในสคริปต์ ไม่ใช่ในความจำของใคร

## 4. สาเหตุจริง + การวัด 89 run

หยุดเถียงกันแล้วไป **วัด** — `gh run list` ดึงประวัติ run จริง 89 ใบ (หน้าต่าง 109.5 ชม.)

| วัดอะไร | ผล |
| --- | --- |
| อัตราที่ run เกิดจริง | **89/439 = 20.3%** ของช่องที่ `*/15` สั่ง |
| คาบจริง (median) | **65.3 นาที** — ช้ากว่าที่ประกาศ ~4.3 เท่า |
| `createdAt` ตกบนกริด `:00/:15/:30/:45` | **4/89** — **ต่ำกว่า**ค่าที่คาดจากการสุ่มล้วน (5.93) |
| gap < 30 นาที ใน 88 ช่วง | **0 ครั้ง** (ถ้าดรอปแบบสุ่มที่ p=0.203 ควรเจอ ~18) |
| ระยะเวลา run ทั้งใบ | 29–59 วินาที ⇒ **ไม่มีคิว ไม่มีการหน่วง** |

⇒ **สมมติฐานเดิมทั้งสองข้อตกทั้งคู่** — ไม่ใช่ "ช่องถูกดรอป" และไม่ใช่ "ทุกช่องถูกหน่วง"
GitHub **ไม่ได้ทำตาม `*/15` เลยสำหรับ repo นี้** · `cron:` ของเราเป็นแค่ **คำขอ**

⇒ **สาเหตุของเหตุการณ์:** เกณฑ์ "ค้าง" ของผู้เฝ้า = `900s × 3` = 45 นาที
ซึ่ง **ต่ำกว่าคาบจริง (65 นาที) เสมอ** ⇒ ทุกครั้งที่ผู้เฝ้ามาทำงาน มันเห็นว่าตัวเองเต้นครั้งล่าสุด
นานเกินเกณฑ์ ⇒ **ตัดสินตัวเองว่าค้าง แล้วรายงานออกไปว่า "ระบบพัง"**

> 🔑 **ธีมกลาง ครั้งที่ 1:** เกณฑ์ถูกคำนวณจาก **ตัวเลขที่เราเขียนไว้ในไฟล์**
> ไม่ใช่จาก **คาบที่ระบบเดินจริง** — และไม่มีใครเคยวัดคาบจริงเลยตลอดเฟส

## 5. การแก้ — แยก "ผู้เฝ้าช้า" ออกจาก "ระบบพัง" + ประกาศคาบที่ได้จริง

### (ก) แยกสองเรื่องที่เคยใช้คำเดียวกัน

เดิม heartbeat ที่ค้าง ⇒ `FAIL` ⇒ `503` **ไม่ว่าจะเป็นกลไกไหน**
แต่มันมีสองความหมายที่ต่างกันสิ้นเชิงปนอยู่:

| ค้างที่กลไกไหน | ความหมายจริง | ควรเป็นอะไร |
| --- | --- | --- |
| `watched` (งานพื้นหลังที่ถูกเฝ้า) | **ระบบพังจริง** | `FAIL` · `503` |
| `watcher` (ตัวผู้เฝ้าเอง) | **จังหวะของผู้เฝ้าเอง** — ผลตรวจรอบนี้ยังสด ทุกอย่างวัดได้ปกติ | `WATCHER_LATE` · `200` |

จึงเพิ่ม verdict ใหม่ `WATCHER_LATE` และแยกบทบาทเป็น **field ในโครงสร้างข้อมูล**
(`{ intervalSeconds, role }`) — ⛔ **ไม่ใช่การยกเว้นตามชื่อ** (`if (m === "readiness-probe")`)
เพราะการยกเว้นตามชื่อคือที่ที่ภายหลังใช้ซ่อนของจริง

⚠️ และ **ไม่ใช้คำว่า `STALE` ซ้ำ** ทั้งที่ง่ายกว่า — เพราะ `STALE` ถูกใช้ไปแล้วกับ
*"snapshot เก่า"* และ `status` ถูกเสิร์ฟใน **shape สาธารณะ** ⇒ ใช้คำเดียวแทนสองเหตุการณ์
= คนนอกจะแยกสองเรื่องนี้ไม่ออก **ตลอดกาล**

### (ข) ประกาศคาบที่วัดได้จริง

`CRON_INTERVAL_MINUTES` 15 → **60** · `cron: "*/15"` → **`"0 * * * *"`**

ก่อนแตะ ตรวจสามข้อจากไฟล์สด เพื่อกันไม่ให้นี่กลายเป็น *"ขยายเกณฑ์ให้ผู้เฝ้าเงียบ"*:
1. heartbeat ของ watcher ถูกอ่านเฉพาะตอน probe รัน ⇒ **ตรวจ "ผู้เฝ้าหยุดสนิท" ไม่ได้โดยโครงสร้าง**
   อยู่แล้ว — ไม่ได้เสียความสามารถอะไรไป
2. `readiness-cadence.test.ts` มี assertion อยู่ก่อนแล้วว่า heartbeat ต้องดัง **ทีหลัง**
   in-band gap check ⇒ **โค้ดประกาศเองว่า `detectGap()` คือตัวตรวจหลัก**
3. เกณฑ์ของ `sla-sweep` **ไม่ถูกกระทบ**

⇒ **การประกาศคาบให้ตรงกับที่วัดได้ = การพูดความจริง ไม่ใช่การซ่อนปัญหา**

⛔ **สิ่งที่ตั้งใจไม่ทำ:** ไม่แตะ `gapped` เพื่อลดเสียง · Discord ยังดังตาม transition เหมือนเดิม
`WATCHER_LATE` ที่ตอบ `200` **ไม่ได้แปลว่าเงียบ** — คนที่อ่าน body ยังเห็นคำว่า `WATCHER_LATE` ชัดเจน

## 6. ปิดด้วย: **เขียนคาดการณ์ก่อนวัด แล้ววัดจริงเพื่อตรวจว่าเดาถูกหรือผิด**

เฟสนี้พลาดเพราะ *ประกาศผลโดยไม่วัด* มาแล้วหลายรอบ ⇒ รอบสุดท้ายเลย**บังคับตัวเอง**:
เขียนตัวเลขที่คาดว่าจะได้ **ลงใน PR body ก่อน merge** แล้ววัดจริงหลังจากนั้น

ผลออกมาเป็น **ถูก 1 (เชิงกลไก) · ยังตัดสินไม่ได้ 3**:

| # | เขียนไว้ก่อนวัด | วัดได้จริง | ตัดสิน |
| --- | --- | --- | --- |
| 1 | `detectGap` ยิง **9/88 = 10.2%** | **0/10** — `P = 0.9¹⁰ = 0.34` ถ้าอัตราเก่ายังจริง | ⚪ **ยังตัดสินไม่ได้** |
| 2 | scheduled run **ส่วนใหญ่ success** | **11/11 = 100% success** | ✅ ถูก — **เชิงกลไก ไม่ใช่คำทำนายที่มีความเสี่ยง** |
| 3 | margin ถึงเกณฑ์ stale **~23 นาที** | **87.2 นาที** | ⚪ **ยังตัดสินไม่ได้** |
| 4 | จะยังเห็น `WATCHER_LATE` **เป็นครั้งคราว** | 0/10 | ⚪ **ยังตัดสินไม่ได้** |

ข้อ 2 ผ่านแบบ **ไม่มีความเสี่ยง** — เกณฑ์ขยับ 45 → 180 นาที ในขณะที่ max gap อยู่แถว 90–160 นาที
⇒ `success` เกิดแน่นอนโดยไม่ต้องเดา ⇒ **ไม่ใช่หลักฐานว่าวิธีทำนายของเราดี**
และ **ข้อ 1 · 3 · 4 ไม่ใช่สามข้อสังเกตอิสระ** — ทั้งสามคือ **หางบนของการแจกแจงเดียวกัน เขียนคนละแบบ**
⇒ นับเป็น "ผิด 2 ข้อ" คือการนับการวัดอันเดียวซ้ำ

**แล้วการวัดครั้งนี้ให้อะไร** — คาดการณ์ข้อ 1 กับ 3 คำนวณด้วยวิธีเดียวกัน: เอาเกณฑ์ใหม่ไปทาบกับ
**การกระจายของ gap ชุดเก่า** ⇒ วิธีนั้นวางอยู่บน **สมมติฐานที่ไม่เคยถูกเขียนออกมา** คือ
*"การกระจายของ gap ไม่ขึ้นกับคาบที่เราประกาศ"*

หน้าต่างครึ่งวัน **ชี้สวนกับสมมติฐานนั้น** (mean 74.7 → 63.7 · max 156.9 → 92.8 ·
อัตราส่งมอบต่อช่องที่ประกาศ 20.3% → 100%) **แต่ยังไม่ถึงระดับที่ปฏิเสธได้**
— Mann-Whitney: `z = 1.30` · `p ≈ 0.19` ⇒ ต่างกันอย่างไม่มีนัยสำคัญ

> 🔑 **ธีมกลาง ครั้งสุดท้าย:** สิ่งที่การวัดครั้งนี้ให้จริง ๆ ไม่ใช่คำตอบว่าเดาถูกหรือผิด
> แต่คือ **การเปิดโปงสมมติฐานที่ซ่อนอยู่ในวิธีทำนายของเราเอง** — เราเอา **พฤติกรรมที่วัดได้
> ตอนประกาศค่าหนึ่ง** ไปทำนาย **พฤติกรรมตอนประกาศอีกค่าหนึ่ง** โดยไม่เคยเขียนสมมติฐานนั้นออกมา
> ⇒ **มีค่ากว่าคำตัดสินถูก/ผิด** เพราะใช้ได้กับการทำนายครั้งถัดไปด้วย

⛔ **ค่าคาดการณ์เดิมไม่ถูกแก้ย้อนหลัง** — เปลี่ยนได้แค่ **คำตัดสิน** ไม่ใช่ **คำทำนาย**
ถ้าแก้คำทำนาย การเขียนไว้ก่อนก็ไม่มีคุณค่าอะไรเลย

> 🔴 **และนี่คือบรรทัดที่เฟสนี้เกือบพลาดเป็นครั้งสุดท้าย:**
> **การประกาศว่าตัวเองเดาผิดโดยที่หลักฐานยังไม่พอ = การอ้างเกินหลักฐานเหมือนกัน
> แค่อ้างไปทางที่ฟังดูถ่อมตัว**
> ฉบับแรกของหัวข้อนี้เขียนว่า *"ผิด 2 ข้อ"* ทั้งที่ย่อหน้าถัดไปห่างกัน 6 บรรทัด บอกเองว่า
> n เล็กเกินกว่าจะสรุปอะไรได้ ⇒ **เอกสารขัดกันเองในหน้าเดียว** — ความถ่อมตัวที่ไม่มีหลักฐานรองรับ
> ก็ยังเป็นการเอา *สิ่งที่อยากให้เป็นจริง* มาแทน *สิ่งที่วัดได้* อยู่ดี

⚠️ **ขอบเขตที่ต้องพูดพร้อมกันเสมอ:** หน้าต่างวัดซ้ำมีแค่ **10.61 ชม. · 11 run · 10 gap**
⇒ ทุกตัวเลขข้างบนเป็น **ขอบเขตบนของสิ่งที่ยืนยันได้ในครึ่งวัน** ไม่ใช่อัตราระยะยาว
⛔ ห้ามอ่านว่า *"ประกาศรายชั่วโมงแล้ว GitHub ใจดีขึ้น"* — ไม่มี control และ n เล็กเกินไป
สิ่งที่ยืนยันได้มีข้อเดียว: **ในหน้าต่างนี้ ไม่มี run ที่ควรเกิดแล้วหายไป**

## 7. สิ่งที่ยังไม่จบ และ **ทำไมถึงเลือกไม่ทำ**

ปิดเฟสที่ **18/21 แถว** ⛔ ไม่ไล่ปิดให้ครบ — ทั้งสามแถวเป็น **ของค้างที่รู้ตัว ไม่ใช่ของที่ลืม**

| ค้างอะไร | ทำไมถึงเลือกไม่ทำ |
| --- | --- |
| **แถว A** — รัน workflow ซ้อมหนึ่งครั้ง | prod live แล้ว และ `ReadinessState` **ไม่มี environment scope** ⇒ การซ้อมเขียนทับสถานะที่ endpoint สาธารณะเสิร์ฟได้ ⇒ ราคาคือ **เสี่ยงกับ prod เพื่อเก็บหลักฐานของสิ่งที่ตัวสคริปต์ผ่านไปแล้ว** |
| **แถว I-b** — job ต้องแดงเมื่อ save ล้ม | ต้อง**จงใจ**ทำให้ save ล้ม = การทดลองที่ยังไม่มีแบบ · เป็น **งานออกแบบ ไม่ใช่งานตรวจ** |
| **แถว C** — external pinger ชั้นนอก | 🔑 ดูด้านล่าง |
| **ทำไม GitHub ถึง throttle repo นี้** | ตอบไม่ได้ · ปิดได้แค่ *"ไม่มีอะไรฝั่งเราที่แก้ด้วย cron expression ได้"* |
| **ผู้เฝ้าจับ probe ที่ตายจริงได้ช้า ~1 ชม.** | เป็น **การยอมรับข้อจำกัด** ไม่ใช่ข้อสรุปจากหลักฐาน ⇒ ทบทวนได้โดยไม่ต้องรอหลักฐานใหม่ |
| **เกณฑ์ผูกกับค่าที่ GitHub เปลี่ยนได้เงียบ ๆ** | แก้ไม่ได้ด้วยโค้ด — ทำได้แค่ **วัดซ้ำเป็นระยะ** |

### 🔑 แถว C คือบทเรียนที่ควรจำที่สุดของเฟสนี้

เกณฑ์ของแถว C เขียนไว้ว่า *"pinger แจ้งเตือนถึงปลายทางจริง"*
ถ้าตั้ง pinger วันนี้ **เกณฑ์นั้นจะผ่านภายในนาทีแรก** — เพราะ endpoint ประกาศ `STALE` + `503`
เป็นเวลาส่วนใหญ่ของวันอยู่แล้ว ⇒ pinger **ต้อง**ดัง ⇒ ติ๊กช่องได้ทันที

แต่ **เหตุผลที่แถว C มีอยู่** คือ *"ต้องมีชั้นนอกที่ดังเมื่อระบบพังจริง"*
สิ่งที่จะได้จริงคือชั้นนอกที่ดัง **~24 ครั้ง/วันเพราะจังหวะของผู้เฝ้าเอง**

> ⇒ **เงื่อนไขที่เขียนไว้ผ่าน แต่เหตุผลที่เงื่อนไขมีอยู่ไม่ผ่าน**
> ⇒ **การไม่ปิดแถว C คือการปฏิเสธหลักฐานปลอม ไม่ใช่การยอมแพ้**

และนี่คือ **ธีมกลางในรูปแบบที่บริสุทธิ์ที่สุด** — *ถ้อยคำของเกณฑ์ในไฟล์* กับ *พฤติกรรมที่เกณฑ์
ตั้งใจจะวัด* เป็นคนละสิ่งกัน และ gate จะไม่มีวันบอกเราเองว่าสองสิ่งนี้แยกจากกันแล้ว

## 8. สิ่งที่เอาไปใช้กับงานอื่นได้

1. **ค่าคงที่ที่บรรยายโลกภายนอก คือสมมติฐาน ไม่ใช่ข้อเท็จจริง** — `CRON_INTERVAL_MINUTES` บอกแค่ว่า
   *เราขออะไร* ไม่ได้บอกว่า *ได้อะไรกลับมา* · ค่าแบบนี้ต้องมีวันหมดอายุและต้องวัดซ้ำ
2. **ผู้เฝ้าที่ใช้ค่าที่ตัวเองประกาศเป็นเกณฑ์ตัดสินตัวเอง = ข้อสรุปที่พิสูจน์ตัวเอง**
   ⇒ ผู้ตรวจต้องไม่ใช่ชิ้นส่วนเดียวกับผู้ถูกตรวจ (กฎเดียวกับที่ใช้ปิดแถว I-a ด้วย REST API)
3. **หนึ่งคำ = หนึ่งความหมาย โดยเฉพาะในสัญญาสาธารณะ** — `STALE` ที่แทนสองเหตุการณ์
   ทำให้คนนอกแยกไม่ออกตลอดกาล และแก้ทีหลังแพงกว่าแก้ตอนนี้มาก
4. **เขียนคาดการณ์ก่อนวัด** — มันทำให้ *"เดาผิด"* กลายเป็นข้อมูล แทนที่จะหายไปเงียบ ๆ
   ในการเล่าเรื่องย้อนหลังที่ทุกอย่างฟังดูเหมือนวางแผนไว้แล้ว
5. **นิยามที่ถกเถียงได้ ให้เขียนเป็นโค้ดที่รันซ้ำได้** ไม่ใช่เขียนเป็นคำอธิบาย
