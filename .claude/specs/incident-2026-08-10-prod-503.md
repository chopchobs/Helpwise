## 4. 🔑 ผู้ต้องสงสัยอันดับ 1 — **`readiness-probe` ทำให้ตัวเอง `FAIL`**

> **หลักฐานเชิงเวลาเข้ากันครบทั้ง 6 จุด ไม่มีจุดไหนขัด** — แต่ **ยังไม่ใช่การพิสูจน์** (ดู §5)

### กลไก (ตรวจจากโค้ด ไม่ใช่เดา)

1. `MECHANISMS["readiness-probe"] = CRON_INTERVAL_MINUTES * 60` = **900s** (`src/lib/heartbeat.ts:52`)
2. เกณฑ์ stale = `expectedIntervalSeconds × STALE_TOLERANCE_FACTOR` = 900 × 3 = **2700s = 45 นาที**
   (`src/lib/heartbeat.ts:159`)
3. `readMechanismHeartbeats()` ถูกอ่าน **ก่อน** `recordHeartbeat("readiness-probe")` ในรอบเดียวกัน
   **โดยตั้งใจ** (`src/lib/readiness.ts:409` อ่าน · `:418` เขียน)
   ⇒ **`age` ที่วัดได้ = ระยะห่างระหว่าง cron สองรอบจริง ๆ**
4. stale ⇒ `readHeartbeats()` คืน `status: "error"` (`src/lib/heartbeat.ts:177-183`)
   ⇒ `rollUpStatus()` เห็น component error ⇒ **`FAIL`** (`src/lib/readiness.ts:387` · `:392-394`)

### 🔴 ความย้อนแย้งที่เขียนอยู่ในโค้ดเอง — `heartbeat.ts:40-48`

คอมเมนต์เหนือ `"readiness-probe"` เล่าเรื่อง §G ข้อ 13 ไว้ครบ **และการวินิจฉัยตอนนั้นก็ถูกทุกคำ**:

> *"เกณฑ์ stale (300×3 = 900s) **เท่ากับคาบจริง (900s) พอดี ⇒ margin = 0**
> ⇒ cron มาสายนิดเดียว = `stale` ⇒ `FAIL` · มาตรงเวลา = `OK` ⇒ **flap ไม่รู้จบ**"*

**แล้วเราแก้ด้วยการทำให้ค่าสองตัวผูกกันเป็นแหล่งเดียว** (§H-11) ⇒ margin 1× → 3×
✅ **การแก้นั้นถูกต้องกับปัญหาที่วัดไว้** — แต่มัน **ยืนอยู่บนสมมติฐานที่ไม่มีใครวัด**:

| ค่าที่ **วัดแล้ว** ตอนนั้น | ค่าที่ **สมมติ** ตอนนั้น |
| --- | --- |
| `cron:` ในไฟล์ = `*/15` | **cron เดินทุก 15 นาทีจริง** |

⇒ สมมติฐานฝั่งขวา **ผิด** (ของจริง ~2 ชม. — §G ข้อ 17) ⇒ **การแก้พังตามไปด้วย**
⇒ 🔴 **และผลลัพธ์แย่กว่าเดิม:** เดิม margin 0 ⇒ **flap** (สลับไปมา = ยังมีรอบ `OK` ให้เห็นว่าระบบยังดี)
   ตอนนี้เกณฑ์ 45 นาที **ต่ำกว่าคาบจริงเกือบ 3 เท่า** ⇒ **`FAIL` แทบถาวร**

> 🔑 **บทเรียนที่ต้องยกออกมาให้พ้นจาก incident นี้:**
> **"การแก้ที่ยืนบนสมมติฐานที่ไม่มีใครวัด จะพังเงียบกว่าบั๊กเดิม"**
> · บั๊กเดิม (flap) **ดังจนน่ารำคาญ** ⇒ ถูกจับได้ภายในวันเดียว
> · การแก้ที่พัง (`FAIL` ถาวร) **ดังสม่ำเสมอจนกลายเป็นเสียงพื้นหลัง** ⇒ ผ่านไป 7 ชั่วโมงกว่าจะมีคนไล่
> ⇒ §H-11 มีสามสนาม (`MECHANISMS` · `CRON_INTERVAL_MINUTES` · `cron:` ใน yml) และ **ผูกครบทั้งสาม
>   ด้วย import + test** — สิ่งที่ไม่มีใครผูกคือ **สนามที่สี่: cron เดินจริงบ่อยแค่ไหน**
>   ซึ่ง **ไม่ใช่ค่าในไฟล์ ⇒ ผูกด้วย static check ไม่ได้เลย** (= §G ข้อ 18 อีกรูปหนึ่ง)

> 🔑 **ถ้าข้อนี้จริง incident นี้ไม่ใช่ "prod พัง" แต่คือ "ผู้เฝ้าวัดตัวเองด้วยเกณฑ์ที่ตัวเองทำไม่ได้"**
> — ซึ่งเป็น **§G ข้อ 13 กลับมาอีกครั้งในรูปที่รุนแรงกว่า**: ครั้งก่อนเกณฑ์ = คาบพอดี ⇒ **flap**
> ครั้งนี้เกณฑ์ (45 นาที) **ต่ำกว่าคาบจริง (~2 ชม.) เกือบ 3 เท่า** ⇒ **`FAIL` แทบถาวร**
> ⇒ §H-11 แก้ margin จาก 1× เป็น 3× **แต่ยังตั้งอยู่บนสมมติฐานว่า cron เดินทุก 15 นาที**
>   ⇒ เมื่อสมมติฐานนั้นพัง การแก้ก็พังตาม

## 8. ผลต่อ Phase 39 (แยกให้ขาด อย่าให้สองเรื่องปนกัน)

- ✅ **ไม่กระทบความถูกต้องของแถวใดเลย** — แถว 12/15/16 เก็บจากเหตุการณ์จริงทั้งหมด
- ✅ **incident ทำให้หลักฐานแถว 15 คมขึ้น** — `prev=FAIL → verdict=OK` เป็น transition ข้ามทริกเกอร์ของจริง
- 🔴 **แต่ถ้าผู้ต้องสงสัยอันดับ 1 ถูก แปลว่า P2 ส่งสัญญาณ `FAIL` 7 ชม. 40 นาที เรื่องตัวมันเอง**
  ⇒ **ไม่ใช่ false positive ทางเทคนิค** (heartbeat ค้างจริง) **แต่เป็นสัญญาณที่ชี้ไปที่ผู้เฝ้า ไม่ใช่ที่ระบบ**
  ⇒ และ **ไม่มีใครอ่านออกจากตัวข้อความ** (§5) ⇒ ต้นทุนของ alert ที่ไม่บอกสาเหตุ **จ่ายไปแล้วเต็ม ๆ**
- 🔴 **แถว C (external pinger) เปลี่ยนสถานะจาก "แถวที่เหลือ" เป็น "แถวที่ incident นี้อธิบายว่าทำไมต้องมี"**
  — ชั้นนอกที่อยู่คนละ failure domain จะบอกได้ว่า *"เว็บยังตอบ 200 อยู่"* ขณะที่ชั้นในบอกว่า `FAIL`
  ⇒ **ความขัดแย้งระหว่างสองชั้นคือข้อมูลวินิจฉัย** ที่วันนี้เราไม่มี
  ⚠️ **แต่ตั้งตอนนี้ไม่ได้** — `SNAPSHOT_STALE_AFTER_SECONDS = 1800` + คาบจริง ~2 ชม.
  ⇒ endpoint สาธารณะ `STALE`+`503` **69–79% ของเวลา** ⇒ pinger **flap ~24 ครั้ง/วัน ตั้งแต่วันแรก**
  ⇒ **§G ข้อ 17 บล็อกแถว C อยู่** (เขียนเป็นเงื่อนไขในตารางหลักฐานแล้ว) ⇒ ลำดับคือ **cron ก่อน C**

### 🔑 สิ่งที่ incident นี้เปิดเผยเรื่องสถาปัตยกรรมของผู้เฝ้า

`readiness` ถูกขับด้วย **GitHub Actions** ส่วน `sla-sweep` ถูกขับด้วย **QStash**
ในวันเดียวกัน: QStash ยิงตรงเป๊ะ **12 รอบติด (09:35 → 10:30)** · GitHub Actions ห่าง **96–141 นาที**

เหตุผลเดิมของการเลือก GitHub Actions (*"ผู้เฝ้าต้องอยู่นอกระบบที่ถูกเฝ้า"* — §H-5) **ยังยืนอยู่**:
QStash เป็น component ที่ถูกเฝ้าจริง (`readiness.ts` `probeQStashReadOnly`) ⇒ ถ้า probe ถูกขับด้วย QStash
**QStash ตาย ⇒ probe ไม่รัน ⇒ ไม่มีใครบอกว่า QStash ตาย** = fail-silent แบบเดียวกับ Phase 38

> 🔑 **แต่เหตุผลนั้นไม่ครบ และนี่คือประโยคที่ควรอยู่ในไฟล์นี้ตรง ๆ:**
> **เราไม่ได้เลือก "ข้างนอก" กับ "ข้างใน" — เราเลือก "อิสระแต่ไม่ตรงเวลา" กับ "ตรงเวลาแต่ไม่อิสระ"
> โดยไม่รู้ว่ากำลังเลือกอะไร**
>
> ราคาสองอย่างของฝั่ง GitHub Actions **ไม่เคยถูกวัดตอนตัดสิน**: (1) ความตรงเวลา — วัดแล้ววันนี้ สาย 8 เท่า
> (2) **60-day auto-disable** ซึ่งเขียนอยู่ในหัว `readiness.yml` เองว่าตัวเฝ้าหายเงียบได้

> ⛔ **ยังไม่เสนอให้ย้าย** · และห้ามตัดสินก่อนปิด §7 ข้อ 2 (ถ้าสาเหตุคือความแออัดของช่อง การย้าย
