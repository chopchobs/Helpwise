## 1. ยิงที่ไหน

```
GET https://gethelpwise.xyz/api/health/readiness
```

- **ไม่ต้องใส่ header ใด ๆ** — ใช้ shape ที่ไม่ auth
- ⛔ **ห้ามใส่ `READINESS_PROBE_TOKEN`** ลงในบริการภายนอก · shape ที่ auth เป็นทางเดียวที่ทำให้เกิด
  outbound call จริง ⇒ ให้ token กับ pinger = ยกสิทธิ์กดโควตาให้บริการภายนอกถือไว้
- ⛔ **ห้ามยิงที่ `*.vercel.app`** — Deployment Protection ตอบ `302` ⇒ อ่านผลผิดทุกรอบ (erratum §F)

**ทุกกี่นาที:** 10–15 นาที (ตรงกับ free tier ของบริการส่วนใหญ่) — ความถี่ไม่สำคัญเท่า threshold ด้านล่าง
shape นี้ไม่ยิง outbound call และมี memo 10 วินาทีเป็นเพดาน read path ⇒ ยิงถี่ก็ไม่กินทรัพยากร (erratum §H-2)

## 2. เกณฑ์เตือน — **30 นาที** (ตัดสินแล้ว 2026-08-08)

ใช้ **threshold เดียวกับชั้นใน** โดยตั้งใจ — pinger เตือนเมื่อ body มี `"status":"STALE"`
(endpoint ตัดสิน STALE เองที่ 30 นาที ผ่าน `SNAPSHOT_STALE_AFTER_SECONDS`)

> 🔑 **คุณค่าของชั้นนอกคือ "อยู่คนละ failure domain กับ GitHub Actions" ไม่ใช่ threshold ที่ต่างกัน**
> ถ้า GitHub Actions ตาย/ถูก disable/ถูก throttle ทั้งชั้นใน (cron) และ in-band gap check
> หายไปพร้อมกัน เพราะทั้งคู่**อยู่ในบ้านหลังเดียวกัน** · pinger อยู่นอกบ้าน ⇒ มันคือชั้นเดียว
> ที่ยังพูดได้เมื่อ GitHub เงียบ · **นั่นคือเหตุผลที่มันมีอยู่ ไม่ใช่เพราะมันรอนานกว่า**

### เสียอะไร / ไม่เสียอะไร

| | |
| --- | --- |
| ✅ **ไม่เสีย** — เคสหลักที่ชั้นนี้ปิด (**cron ไม่รันเลย** · 60-day auto-disable · Actions ล่ม) | ยังถูกครอบเต็มที่ **30 นาที** ซึ่ง **เร็วกว่าแผนเดิม (45–60 นาที) ด้วยซ้ำ** |
| ✅ **ไม่เสีย** — alert fatigue | transition-only ทำให้แต่ละ transition ยิงครั้งเดียวอยู่แล้ว ⇒ ได้สองข้อความจากสองชั้น **ครั้งเดียว** ไม่ใช่เสียงรัว |
| ⚠️ **เสียจริง** — **การเตือนแบบไล่ระดับ** | แผนเดิม: ชั้นในดังก่อน ถ้าเงียบแล้วชั้นนอกดังตามทีหลัง ⇒ อ่านได้ว่า *"ชั้นในเงียบทั้งที่ควรดัง"* · ของจริง: ดังพร้อมกัน ⇒ **แยกไม่ออกจากข้อความเดียวว่าชั้นในทำงานหรือไม่** ต้องไปดูที่ Actions เอง |

⇒ ที่เสียคือ **ข้อมูลวินิจฉัยหนึ่งชิ้น** ไม่ใช่ความสามารถในการตรวจจับ

## 3. ⛔ ต้องอ่าน "เนื้อ response" ไม่ใช่ status code

กฎเดียวกับลำดับ 5 (erratum §B(ค)) — `302` จาก Deployment Protection, `200` จากหน้า SSO,
error page ของ CDN ล้วนมี "response" ครบถ้วนโดยที่แอปเราไม่เคยถูกเรียก

**เกณฑ์ขั้นต่ำที่ pinger ต้องทำได้: keyword match บน body** (ทุกเจ้าที่ใช้ได้ฟรีทำได้)

| ตั้งค่าใน pinger | ความหมาย |
| --- | --- |
| body **ต้องมี** `helpwise.readiness.v1` | ไม่มี = ไม่ได้คุยกับโค้ดเรา = `INCONCLUSIVE` ⇒ **ต้องเตือน** |
| body **ต้องไม่มี** `"status":"STALE"` | มี = ผลตรวจเก่าเกิน 30 นาที |
| body **ต้องไม่มี** `"status":"FAIL"` | มี = ระบบพัง |

รูปร่าง response ที่ shape ไม่ auth คืน (ยืนยันจากโค้ดจริง — 5 key เท่านั้น ไม่มีข้อมูล tenant/infra):

```json
{ "data": {
    "marker": "helpwise.readiness.v1",
    "status": "OK",
    "lastCheckAt": "2026-08-08T12:00:00.000Z",
    "ageSeconds": 42,
    "staleAfterSeconds": 1800
  }, "error": null }
```

## 4. ทางที่ **ตกไปแล้ว** — ห้ามรื้อกลับมา

| ทาง | สถานะ | เหตุผล |
| --- | --- | --- |
| **เพิ่ม `?staleAfter=<วินาที>` ให้ผู้เรียกตั้ง threshold เอง** | ⛔ **ตกด้วยเหตุผลเชิงหลักการ** | เป็นการให้ **ผู้เรียกที่ไม่ auth ควบคุมเกณฑ์ที่ใช้ตัดสินสถานะ** · endpoint นี้ออกแบบบนหลัก *"ไม่รับ input จาก client เลยแม้แต่รูปแบบเดียว"* (v2 §9 ข้อ 3) · **clamp แล้วก็ยังเป็น input ที่มีผลต่อคำพิพากษา** = ตระกูลเดียวกับ tenant spoofing แค่เบากว่า |
| **บังคับเลือก pinger ที่ assert JSON/numeric ได้** | ⛔ ตก | จำกัดตัวเลือกผู้ให้บริการเพื่อประโยชน์เล็กมาก (ได้แค่ข้อมูลวินิจฉัยหนึ่งชิ้นในตาราง §2) |

## 5. เช็คลิสต์ตั้งค่า + **เงื่อนไขปิดลำดับ 6**

> 🔴 **ลำดับ 6 ปิดไม่ได้ก่อน merge — เป็นข้อเท็จจริงเชิงโครงสร้าง ไม่ใช่ความล่าช้า** *(บันทึก 2026-08-09)*
>
> `/api/health/readiness` **ยังไม่อยู่บน prod** (verify: `git show main:src/app/api/health/readiness/route.ts` → ไม่มีไฟล์)
> ⇒ ผลที่ตามมาสามข้อ ต้องรู้ล่วงหน้า ไม่งั้นจะอ่านผิดทุกข้อ:
>
> 1. **monitor จะแดงตั้งแต่วันแรก** — keyword `helpwise.readiness.v1` ไม่มีทางเจอเพราะ endpoint ยังไม่มีบน prod
>    ⇒ **นี่คือสิ่งที่คาดไว้ ไม่ใช่บั๊ก และไม่ใช่หลักฐานว่า pinger ทำงาน** (แดงเพราะ 404 ก็แดงเหมือนกัน)
> 2. **วิธี A ใช้ไม่ได้ตอนนี้** — cron ยังไม่อยู่บน default branch ⇒ **ไม่เคยรันเลย** ⇒ "ปิด workflow แล้วรอ STALE"
>    ไม่มีความหมาย (ไม่มีอะไรให้ปิด และไม่มี `lastCheckAt` ให้เก่า)
> 3. **วิธี B ทำได้วันนี้เลย** — เพราะยิงที่ `/api/health` ซึ่ง**มีอยู่บน prod แล้วจริง**
>
> **⇒ แบ่งงานลำดับ 6 เป็นสองช่วง:**
>
> | ช่วง | ทำอะไรได้ |
> | --- | --- |
> | **ก่อน merge (ทำได้เลย)** | เลือกบริการ · ตั้ง monitor · ตั้ง keyword · ตั้งปลายทางแจ้งเตือนคนละช่องกับลำดับ 5 · **พิสูจน์ด้วยวิธี B** |
> | **หลัง merge (ค่อยทำ)** | ยืนยันว่า monitor กลับเขียวเมื่อ endpoint ขึ้น prod จริง · **พิสูจน์ด้วยวิธี A** |
>
> ⚠️ ถ้าปิดเฟสด้วย **B อย่างเดียว** ⇒ **ต้องบันทึกใน §G ว่าเคส `STALE` จริงยังไม่เคยถูกพิสูจน์ end-to-end**
> (B พิสูจน์แค่ว่า *keyword rule + ช่องทางแจ้งเตือน* ทำงาน — ไม่ได้พิสูจน์ว่าเคสที่ชั้นนี้มีอยู่เพื่อจับ ถูกจับจริง)

- [ ] เลือกบริการ pinger ฟรีที่ทำ **keyword match บน body** ได้ (ข้อ 3)
- [ ] ตั้ง monitor: `GET https://gethelpwise.xyz/api/health/readiness` ทุก 10–15 นาที · **ไม่มี header**
- [ ] keyword **ต้องมี**: `helpwise.readiness.v1`
- [ ] keyword **ต้องไม่มี**: `"status":"STALE"` และ `"status":"FAIL"`

### 🔴 เงื่อนไขปิด — ทั้งสองข้อนี้เป็น gate ไม่ใช่คำแนะนำ

- [ ] **ปลายทางแจ้งเตือนต้องเป็นคนละช่องกับ Slack ของลำดับ 5** (อีเมลก็ได้)
      เหตุผล: ถ้าใช้ Slack webhook เดียวกันแล้ว integration นั้นตาย **ทั้งสองชั้นเงียบพร้อมกัน**
      ⇒ ชั้นนอกที่ตั้งใจให้อยู่คนละ failure domain จะกลับมาอยู่ domain เดียวกันที่ปลายทาง
      (หลักการเดียวกับ erratum §H-5: ผู้เฝ้าต้องไม่ใช้ชิ้นส่วนเดียวกับผู้ถูกเฝ้า)

- [ ] **พิสูจน์ว่า pinger ดังจริง ก่อนปิดเฟส** — `CLAUDE.md` § Post-merge gate:
      *"feature ที่ออกแบบให้ fail-soft ต้องมี assertion ยืนยัน happy path บน prod เสมอ"*
      pinger ที่ตั้งแล้วไม่เคยพิสูจน์ว่าดังได้ = fail-soft ที่ไม่มีใครเห็น = สิ่งที่ทั้งเฟสนี้แก้อยู่

      **วิธีพิสูจน์ (เลือกอย่างใดอย่างหนึ่ง — ทั้งคู่ไม่แตะ production data):**

      **วิธี A — ทำให้ STALE จริง (พิสูจน์ทั้งเส้น)**
      1. ปิด scheduled workflow ชั่วคราว: GitHub → Actions → *Readiness (P2)* → `⋯` → **Disable workflow**
      2. รอ > 30 นาที (ไม่มี live probe ⇒ `lastCheckAt` เก่า ⇒ endpoint ตอบ `status: "STALE"`)
      3. ✅ ผ่านเมื่อ **pinger ส่งแจ้งเตือนมาถึงปลายทางจริง**
      4. เปิด workflow กลับ → กด **Run workflow** ครั้งหนึ่งเพื่อให้ `lastCheckAt` สดทันที
      5. ✅ ยืนยันว่า pinger กลับเป็นเขียว
      ⚠️ ระหว่างขั้นนี้ P2 ไม่มีชั้นในเฝ้าอยู่ — ทำตอนที่รับความเสี่ยงได้ และอย่าลืมขั้นที่ 4

      **วิธี B — ทดสอบ keyword ของ pinger เอง (เร็วกว่า ครอบน้อยกว่า)**
      1. ชี้ monitor ไปที่ URL ที่ไม่มี marker ชั่วคราว (เช่น `https://gethelpwise.xyz/api/health`)
      2. ✅ ผ่านเมื่อ pinger แจ้งเตือน (เพราะ keyword `helpwise.readiness.v1` หายไป)
      3. ชี้กลับ URL เดิม → ยืนยันกลับเป็นเขียว
      ⚠️ **พิสูจน์แค่ว่า keyword rule + ช่องทางแจ้งเตือนทำงาน** ไม่ได้พิสูจน์ว่าเคส STALE จริงถูกจับ
