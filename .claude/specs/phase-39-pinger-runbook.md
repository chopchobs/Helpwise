## 1. ยิงที่ไหน

```
GET https://gethelpwise.xyz/api/health/readiness
```

- **ไม่ต้องใส่ header ใด ๆ** — ใช้ shape ที่ไม่ auth
- ⛔ **ห้ามใส่ `READINESS_PROBE_TOKEN`** ลงในบริการภายนอก · shape ที่ auth เป็นทางเดียวที่ทำให้เกิด
  outbound call จริง ⇒ ให้ token กับ pinger = ยกสิทธิ์กดโควตาให้บริการภายนอกถือไว้
- ⛔ **ห้ามยิงที่ `*.vercel.app`** — Deployment Protection ตอบ `302` ⇒ อ่านผลผิดทุกรอบ (erratum §F)

**ทุกกี่นาที:** 10–15 นาที (ตรงกับ free tier ของบริการส่วนใหญ่) — ความถี่ไม่สำคัญเท่า threshold ด้านล่าง
shape นี้ไม่ยิง outbound call และมี memo 10 วินาทีเป็นเพดาน read path ⇒ ยิงถี่ก็ไม่กินทรัพยากร (erratum §H-2)

## 2. เกณฑ์เตือน — **45–60 นาที** (ตั้งใจให้ทับกับชั้นใน)

| ชั้น | ใคร | threshold |
| --- | --- | --- |
| ใน | endpoint ตัดสินเอง (`SNAPSHOT_STALE_AFTER_SECONDS`) | **30 นาที** → `status: "STALE"` |
| นอก | pinger ตัวนี้ | **45–60 นาที** |

ช่องว่าง 15–30 นาทีคือ**เจตนา** (v2 §3 ข้อ 10): ชั้นในมีโอกาสส่งเสียงก่อน ⇒ ถ้าชั้นนอกดัง แปลว่า
**ชั้นในเงียบทั้งที่ควรดัง** ซึ่งเป็นข้อมูลคนละชิ้นกับ "ระบบพัง" — ไม่ใช่การเตือนซ้ำ

---

## 3. ⛔ ต้องอ่าน "เนื้อ response" ไม่ใช่ status code

กฎเดียวกับลำดับ 5 (erratum §B(ค)) — `302` จาก Deployment Protection, `200` จากหน้า SSO,
error page ของ CDN ล้วนมี "response" ครบถ้วนโดยที่แอปเราไม่เคยถูกเรียก

**เกณฑ์ขั้นต่ำที่ pinger ต้องทำได้: keyword match บน body**

| ตั้งค่าใน pinger | ความหมาย |
| --- | --- |
| body **ต้องมี** `helpwise.readiness.v1` | ไม่มี = ไม่ได้คุยกับโค้ดเรา = `INCONCLUSIVE` ⇒ **ต้องเตือน** |
| body **ต้องไม่มี** `"status":"STALE"` | มี = ผลตรวจเก่าเกิน 30 นาที |
| body **ต้องไม่มี** `"status":"FAIL"` | มี = ระบบพัง |

รูปร่าง response ที่ shape ไม่ auth คืน (ยืนยันจากโค้ดจริง — 5 key เท่านั้น ไม่มีข้อมูล tenant/infra):

```json
{ "data": {
    "marker": "helpwise.readiness.v1",
    "status": "OK",
    "lastCheckAt": "2026-08-08T12:00:00.000Z",
    "ageSeconds": 42,
    "staleAfterSeconds": 1800
  }, "error": null }
```

## 4. 🔴 ข้อจำกัดที่ต้องตัดสินใจก่อนเลือกบริการ

**`lastCheckAt` / `ageSeconds` มีอยู่ในเนื้อ response จริง — แต่ pinger ฟรีส่วนใหญ่
"เปรียบเทียบตัวเลข" ไม่ได้** ทำได้แค่ *keyword มี/ไม่มี* กับ *status code*

⇒ ในทางปฏิบัติ pinger จะจับได้ที่ threshold **30 นาที** (ผ่าน keyword `"status":"STALE"`)
**ไม่ใช่ 45–60 นาทีตามที่ดีไซน์ตั้งใจ** ⇒ ช่องว่างระหว่างสองชั้นหายไป และชั้นนอกกลายเป็นเสียงซ้ำของชั้นใน

**สองทางเลือก — ยังไม่ตัดสิน รอ Dev บอกว่าใช้บริการไหนก่อน:**

| ทาง | ทำอะไร | ราคา |
| --- | --- | --- |
| **A. เลือก pinger ที่มี JSON/numeric assertion** (เช่น บริการที่ตั้ง "JSON path `data.ageSeconds` > 2700" ได้) | ไม่ต้องแก้โค้ด · ได้ threshold 45–60 นาทีตามดีไซน์เป๊ะ | ฟีเจอร์นี้มักอยู่ใน tier ที่เสียเงินของหลายเจ้า — ต้องเช็คก่อน |
| **B. ให้ endpoint รับ `?staleAfter=<วินาที>` แล้วคำนวณ STALE ตามค่านั้น** | pinger ฟรีที่ keyword match ก็ได้ threshold 45–60 นาที | เพิ่ม input จากคนนอกบน endpoint สาธารณะ ⇒ **ต้อง clamp ช่วง** (เช่น 1800–7200) และ **ห้ามให้ค่าที่ส่งมามีผลต่ออะไรนอกจากการตัดสิน STALE ของ response นั้น** · ต้องมี test ค้ำ clamp |

**ถ้าเลือก C (ไม่ทำอะไร):** ยอมรับว่าชั้นนอกดังที่ 30 นาทีเท่าชั้นใน ⇒ **ยังครอบเคส "cron ไม่รันเลย" ได้อยู่**
(ซึ่งคือหน้าที่หลักของชั้นนี้) แค่เสียคุณสมบัติ "แยกแยะว่าชั้นในเงียบทั้งที่ควรดัง"
— **ยอมรับได้ ถ้าบันทึกไว้** ห้ามลืมแล้วเข้าใจว่าได้ครบตามดีไซน์
