## §B. E-1 — 🔴 ข้ออ้างที่ v2 รับมาจาก incident §8.3 ผิด (ตรวจโค้ดยืนยันแล้ว)

### หลักฐานจากโค้ด (ตรวจแล้ว ไม่ใช่การอนุมาน)

- `grep -n "redirect" src/proxy.ts next.config.ts` ให้ผลลัพธ์เดียวคือ **คอมเมนต์** ที่ `src/proxy.ts:11` ซึ่งเขียนว่า *"ไม่รองรับ request rewrite/redirect แบบ edge granularity (ไม่มี NextResponse.rewrite)"*
  ⇒ **ไม่มี `NextResponse.redirect` อยู่ในโค้ดเลยสักบรรทัด** และ `next.config.ts` ก็ไม่มี redirect config
- พฤติกรรมจริงของ host ที่ไม่ใช่ `{slug}.gethelpwise.xyz`: `slug = null` → `nextWithoutTenantHeaders()` → **ผ่านไปเฉย ๆ ไม่ redirect**
- `src/proxy.ts:69-85` = `SKIP_TENANT_PATH_PREFIXES` ซึ่ง **มี `"/api/health"` อยู่แล้ว (บรรทัด 84)** และ **ไม่มี `/api/ops/`**
- เงื่อนไข match ที่ `src/proxy.ts:207-209`: `pathname === p || pathname.startsWith(p.endsWith("/") ? p : p + "/")`

### (ก) การ attribute `302` ไปที่ `src/proxy.ts` ผิด — และแก้ที่ไหนบ้าง

ประโยคใน `phase-38-qstash-region-incident-2026-08-06.md` **§8.3 (บรรทัด ~281–285)** ที่ว่า *"`*.vercel.app` ทุก host ตอบ `302` ทุก path เพราะ `src/proxy.ts` จับ host ที่ไม่ใช่ tenant แล้ว redirect ทิ้ง"* **ไม่จริง** — โค้ดไม่มี redirect ให้ทำแบบนั้นได้เลย

**v2 รับข้ออ้างนี้มาใช้ต่อ 2 จุด และต้องแก้ทั้งสองจุด:**

| จุดใน v2 | ข้อความเดิม | สถานะหลัง erratum |
| --- | --- | --- |
| **v2 §5 ข้อ 1** (บรรทัด ~205 ย่อหน้า "prerequisite ที่ v1 ตกไป") | "…ตอบ `302` ทุก path เพราะ `src/proxy.ts` … redirect ทิ้ง" | **ผิด — ถูกแทนที่ด้วย §B(ค) ของ erratum นี้** |
| **v2 §3 ข้อ 9** (บรรทัด ~163) | "proxy ที่ redirect ทุก path บน host ที่ไม่ใช่ tenant … ต้อง special-case path นี้ให้ผ่านโดยไม่ redirect" | **ผิด — ไม่มี redirect ให้ special-case** · ข้อกำหนดที่ยังคงอยู่คือ "endpoint ต้องไม่เดินผ่าน tenant-scoped pipeline" ซึ่งได้มาฟรีจากการที่ path อยู่ใน `SKIP_TENANT_PATH_PREFIXES` แล้ว (`src/proxy.ts:84` + เงื่อนไขบรรทัด 207-209) |

**สาเหตุจริงของ `302`:** **Vercel Deployment Protection** ที่บังคับ SSO บน `*.vercel.app`
> ⚠️ **ยังไม่มีใครตรวจค่าจริงของ Deployment Protection บนโปรเจกต์นี้** — ข้อนี้เป็น **สมมติฐานจนกว่า Dev จะ confirm ใน Vercel Project Settings** ห้ามเขียน/อ้างเป็นข้อเท็จจริงในเอกสารหรือใน commit message

**ข้อสังเกตเดิมยังคงอยู่ทั้งข้อ:** *"เทียบ artifact ข้าม host (production alias ↔ deployment URL) ทำไม่ได้"* — เปลี่ยนแค่**เหตุผล** จาก "proxy redirect" เป็น "Deployment Protection (สมมติฐาน)" · ผลต่อการออกแบบ gate เหมือนเดิมทุกประการ แต่**ทางแก้ต่างกันสิ้นเชิง**: proxy แก้ที่โค้ดของเรา ส่วน Deployment Protection แก้ที่ Vercel setting/bypass token — ถ้าไม่แก้บันทึกไว้ คนถัดไปจะไปแก้โค้ดที่ไม่ใช่ต้นเหตุ

### (ข) แทนที่ v2 §6 ลำดับ 1 และแก้ v2 §5 prerequisite ข้อ 1

งานจริง**ไม่ใช่** "แก้ proxy ไม่ให้ redirect" (ไม่มีอะไรให้แก้) แต่คือ **path ของ probe ต้องอยู่ใน `SKIP_TENANT_PATH_PREFIXES`**

**การตัดสิน: ใช้ path `/api/health/readiness`** — ไม่ใช่ `/api/ops/readiness` ที่ v2 §2 ทางเลือก A เขียนไว้

เหตุผลครบ 3 ข้อ:

1. **ไม่ต้องแก้ `src/proxy.ts` เลยสักบรรทัด** — `"/api/health"` อยู่ในลิสต์แล้ว (บรรทัด 84) และเงื่อนไข prefix match ที่บรรทัด 207-209 (`p + "/"`) ครอบ `/api/health/readiness` อยู่แล้วโดยอัตโนมัติ
2. **`src/proxy.ts` เป็นชั้น tenant isolation ซึ่งเป็นกฎสูงสุดของโปรเจกต์** — ไม่แตะเลยย่อมปลอดภัยกว่าแตะ · การเพิ่ม prefix ใหม่เข้าลิสต์คือการเพิ่มพื้นที่ที่ข้าม tenant resolution ซึ่งต้องรีวิวระดับ security ทุกครั้ง งานนี้ไม่ต้องจ่ายราคานั้น
3. **เป็น path ที่ brief §5 เสนอไว้ตั้งแต่แรกอยู่แล้ว** — brief §5 (P2) เขียนว่า *"ข้อเสนอตั้งต้นคือ `GET /api/health/readiness` แต่ไม่ผูกมัดว่าต้องเป็นรูปนี้"* ⇒ กลับมาที่ข้อเสนอตั้งต้นคือทางที่มีเหตุผลรองรับมากที่สุด ไม่ใช่การประนีประนอม

**ผลตามมาที่ต้องเขียนให้ชัด:**

- **v2 §6 ลำดับ 1 หายไปทั้งข้อ** — เหลือเพียงการ**ยืนยัน**ว่า path ถูกครอบจริง (ดู §E ลำดับ 1) ไม่ใช่งานแก้โค้ด
- **แถว "special-case probe path ใน `src/proxy.ts` + identity ของ deployment ใน response · ~1 ชม." ในตารางต้นทุน v2 §5 ข้อ 5 ถูกลบออก** — ส่วน "identity ของ deployment ใน response" ย้ายไปรวมกับแถว probe endpoint (ดู §D)

**ราคาที่จ่าย (เขียนตรง ๆ):** ชื่อ path สื่อความหมายแคบลง — `health` สื่อว่า "ยังมีชีวิต" ขณะที่ของจริงคือ readiness ระดับ ops (headroom, heartbeat, deployment identity) ซึ่ง `ops` สื่อได้ตรงกว่า · **ยอมรับได้** เพราะราคานี้เป็นเรื่องการตั้งชื่อ ส่วนสิ่งที่ได้กลับมาคือการไม่แตะชั้น tenant isolation

### (ค) prerequisite ตัวจริงของ rehearsal (แทนที่ v2 §5 ข้อ 1)

**prerequisite ตัวจริงคือ: Deployment Protection ของ Preview จะขวางการยิง probe เข้าไปที่ `*.vercel.app`**

✅ **confirm แล้ว 2026-08-08 (Dev)** — Vercel Authentication = ON โหมด "Standard Protection" · หลักฐานการวัดครบชุดอยู่ที่ **§G ข้อ 5** (ไม่ลอกมาซ้ำที่นี่)

**ล็อกที่ทาง A — Protection Bypass token** (ส่ง `x-vercel-protection-bypass` เป็น header หรือ query param ไปกับ request ที่ยิง probe · ตั้งเป็น system env `VERCEL_AUTOMATION_BYPASS_SECRET`)
เหตุผล: มีให้ใช้จริงบน plan ปัจจุบัน (confirm แล้ว) · ไม่แตะ setting ของโปรเจกต์ · ไม่มีหน้าต่างเวลาที่ Preview เปิดสาธารณะ · ทำซ้ำได้ทุกครั้งโดยไม่ต้องมีคนไปกดอะไร (ตรงกับเจตนา "rehearsal ที่ทำซ้ำได้" ใน v2 §5)

⛔ **ทาง B (ปิด Protection ชั่วคราวแล้วเปิดคืน) ถูกตัดออกแล้ว ห้ามรื้อกลับมา** — เป็น escape hatch ที่พึ่งคนจำไปเปิดคืน ซึ่ง brief §7 ปฏิเสธไว้ตรง ๆ ("คนลืม revert = เสีย gate ถาวรแบบเงียบ") และไม่มีเหตุให้ใช้แล้วเพราะทาง A ใช้ได้จริง

→ เพิ่มเข้าเช็คลิสต์ **§F** แล้ว

#### กฎแยกผลลัพธ์ — `INCONCLUSIVE` (เพิ่มเข้า v2 §5 ข้อ 5–6)

v2 §5 ข้อ 5 ตั้งกฎไว้แล้วว่า **"⛔ ห้ามใช้ status code เป็นหลักฐาน"** และเกณฑ์ตัดสินต้องเป็น **เนื้อ response ที่ระบุตัวตนได้ (marker ของ probe + deployment identity)** — erratum นี้เติมกลไกที่ v2 ยังไม่ได้เขียน:

- **ไม่พบ probe marker ในเนื้อ response ⇒ ผลลัพธ์คือ `INCONCLUSIVE`**
  **ห้ามนับเป็น `FAIL` และห้ามนับเป็น `PASS`** — ไม่ว่า status code จะเป็น `200`, `302`, `401` หรืออะไรก็ตาม (นี่คือกรณีที่ Deployment Protection ตอบแทนแอปเรา: response มีอยู่ แต่ไม่ได้มาจากโค้ดของเรา)
- **ครึ่งหลังที่ห้ามตกหล่น: `INCONCLUSIVE` ต้องส่งเสียงดังเท่า `FAIL`** — เข้า transition rule เดียวกัน ยิง Slack ช่องเดียวกัน ไม่มีการ "ข้ามไปก่อน" ต่างกันแค่**ข้อความ**:
  - `FAIL` = **ระบบพัง** ไปดูว่าอะไรพัง
  - `INCONCLUSIVE` = **วัดไม่ได้** ต้องมีคนไปดูว่าทำไมวัดไม่ได้
- **ขอบเขตของกฎนี้: ทุกจุดที่อ่านผล probe ไม่ใช่แค่ rehearsal** *(ตัดสินโดยรีวิว 2026-08-08 — ไม่เหลือให้ตัดสินตอน implement)*
  **probe รอบ cron ปกติที่อ่าน marker ไม่ได้ = `INCONCLUSIVE` ด้วยกฎเดียวกับ rehearsal** เหตุผลเหมือนกันเป๊ะ: *response มีอยู่ แต่ไม่ได้มาจากโค้ดของเรา = **วัดไม่ได้** ไม่ใช่ **ระบบพัง*** ⇒ ดังเท่า `FAIL` ต่างกันแค่ข้อความ ⇒ **ไม่มีอะไรต้องตัดสินเพิ่มตอน implement ลำดับ 5**
- **เหตุผลที่ต้องเขียนเป็นกลไก ไม่ใช่คำอธิบาย:** ถ้า `INCONCLUSIVE` เงียบกว่า `FAIL` มันจะกลายเป็น **"สถานะที่สามที่ไม่มีใครได้ยิน"** ซึ่งคือรูเดิมที่ Phase 39 ทั้งเฟสกำลังรักษาอยู่ (brief §3: *"เราตีความ 'ไม่มี error' ว่า 'ปกติ'"*) และซ้ำกับกฎที่ v2 ตั้งไว้เองใน **§3 ข้อ 1ก-3** ว่า *"timeout = สัญญาณ ไม่ใช่การข้าม"* — `INCONCLUSIVE` คือ timeout ในรูปแบบอื่น กฎเดียวกันต้องใช้บังคับ

## §C. E-2 — 🔴 counter ตัวที่สองเปิดให้คนนอกตรึงระบบเป็น FAIL (แทนที่ v2 §3 ข้อ 2 ข-2)

### ปัญหา (verify แล้ว)

v2 **§3 ข้อ 2 (ข-2)** กำหนดว่า counter "inbound ที่ verify ไม่ผ่าน" มีค่ามากกว่าศูนย์ต่อเนื่อง = **FAIL ทันที** + **ห้ามสถานะรวมเป็น OK**

ข้อเท็จจริงที่ตรวจแล้ว:

- `src/proxy.ts:81` มี `"/api/jobs/"` อยู่ใน `SKIP_TENANT_PATH_PREFIXES` (คอมเมนต์บรรทัด 79-80 ระบุเองว่า *"route handler verify QStash signature เอง"*)
- worker ทั้ง 3 ตัว — `src/app/api/jobs/send-email/route.ts`, `src/app/api/jobs/sla-sweep/route.ts`, `src/app/api/jobs/webhook-deliver/route.ts` — เรียก `verifyQStashSignature()` เองที่ route
- ⇒ **path เหล่านี้เข้าถึงได้สาธารณะ** และ prod นี้เป็น **portfolio ที่เปิดจริงมีคนเข้า** (brief §1)

⇒ **ใครก็ได้ POST ขยะเข้าไปตรึงสถานะเป็น FAIL ถาวร = ทำลายช่องเตือนทั้งช่อง** ซึ่งคือความเสียหายที่ v2 **ยกมาเป็นเหตุผลของตัวเองใน §3 ข้อ 2 (ข-1)** ว่าทำไมไม่นับก่อน verify (*"เปิดให้ใครก็ได้ POST เข้ามาดันตัวเลขทะลุ threshold → alert ปลอมรัว ๆ → alert fatigue … ความเสียหายนั้นทำลายระบบเตือนทั้งระบบ"*)
⇒ **v2 ขัดกันเองในหน้าเดียว** — ปฏิเสธ pattern นี้ใน ข-1 แล้วสร้างมันขึ้นมาเองใน ข-2

### กฎใหม่ (ใช้แทน ข-2 ทั้งข้อ)

แยก attempt ที่ verify ไม่ผ่านออกเป็น **สองคลาสก่อน** แล้วค่อยตัดสิน:

| คลาส | นิยาม | ความหมาย | ผลต่อสถานะ |
| --- | --- | --- | --- |
| **(1) signed-but-invalid** | request ที่**มี header ลายเซ็นของ QStash** แต่ verify ไม่ผ่าน | สัญญาณจริง — ครอบเคส "signing key ไม่ตรง" | เข้าเกณฑ์ FAIL แบบมีเงื่อนไข (ดูล่าง) |
| **(2) unsigned** | request ที่**ไม่มี header นั้นเลย** | ขยะจากภายนอก — QStash ไม่เคยส่งแบบนี้ | ❌ **ห้ามทำให้เป็น FAIL** · ไปทาง **rate-based → DEGRADED** เมื่ออัตราต่อชั่วโมงเกิน threshold ที่ตั้งไว้ (เป็นข้อมูล ไม่ใช่คำพิพากษา) |

**เงื่อนไขเพิ่มของคลาส (1) — corroboration ก่อน FAIL:**
คลาส (1) ยัง forge ได้ (ใครก็ใส่ header ชื่อนั้นแล้วส่งค่ามั่วได้) ⇒ **`FAIL` ต้องมีหลักฐานสองด้านพร้อมกัน**:

- คลาส (1) > 0 ต่อเนื่อง **และ** **heartbeat ของ mechanism ที่เกี่ยวข้องค้างเกินหน้าต่างที่คาด** (ชั้น B ตาม v2 §3 ข้อ 2 ข-3) ⇒ **FAIL**
- คลาส (1) > 0 ต่อเนื่อง **แต่ heartbeat ยังสด** ⇒ **DEGRADED** ("มีคนยิง signature ปลอมเข้ามา แต่ delivery จริงยังผ่าน") — ต้องมีคนไปดู ไม่ใช่ประกาศว่าระบบพัง
- ยังคงกฎเดิมของ v2 ข-2 ไว้ 1 ข้อ: **ตลอดช่วงที่คลาส (1) ไม่เป็นศูนย์ ตัวเลขโควตาต้องถูก mark ว่า "ต่ำกว่าความจริง"** และ **สถานะรวมห้ามเป็น `OK`** (เป็น DEGRADED เป็นอย่างต่ำ)

### กฎใหม่จับ "signing key rotate แล้วไม่ตรง" ได้อย่างไร

**จับได้ — และนี่คือกลไก:** QStash แนบ header ลายเซ็นมาทุก attempt เสมอ (ทั้ง delivery แรกและ retry) ⇒ เมื่อ key ที่ Vercel ไม่ตรงกับที่ QStash เซ็น attempt ทุกตัวจะตกเข้า **คลาส (1)** ไม่ใช่คลาส (2) · และเพราะ verify ไม่ผ่าน worker จะไม่ทำงาน ⇒ **heartbeat ของ mechanism นั้นค้างแน่นอน** ⇒ เงื่อนไข corroboration ครบทั้งสองด้าน ⇒ **FAIL**
กลับกัน คนนอกที่ยิง forged header ทำให้ heartbeat ค้างไม่ได้ (worker จริงยังรับ delivery จริงอยู่) ⇒ ตรึงเป็น FAIL ไม่ได้ **นี่คือจุดที่เงื่อนไข corroboration ทำงาน ไม่ใช่แค่ลด noise**

**สิ่งที่ยังจับไม่ได้ (ลง §G):** ช่วงที่ key ไม่ตรง **แต่ยังไม่มี message ถูก publish เลย** (เช่นนอกเวลาที่ sweep รัน) ⇒ ไม่มีทั้ง attempt และ heartbeat gap ⇒ เงียบจนกว่าจะมี traffic รอบถัดไป · หน้าต่างนี้ยาวเท่าคาบของ mechanism ที่ถี่ที่สุด

### ข้อบังคับสามข้อที่ต้องติดมากับกฎนี้

1. **ชื่อ header จริงห้ามเดา** — เอกสารนี้**ไม่เขียนชื่อ header ลงไป** ตามกฎเดียวกับที่ v2 §8 ตั้งไว้กับชื่อ Vercel system env
   ⇒ **ตอน implement ต้อง confirm ชื่อ header จากโค้ด verify ที่ใช้อยู่จริง คือบรรทัดที่อ่าน header ใน `verifyQStashSignature()` ที่ `src/lib/queue.ts` (~บรรทัด 163, ในฟังก์ชันที่เริ่มบรรทัด 139)** — โค้ดตัวนั้นคือ source of truth เดียว ไม่ใช่เอกสารของผู้ให้บริการและไม่ใช่เอกสารฉบับนี้
   ⚠️ ถ้า SDK เปลี่ยนชื่อ header ในอนาคต การจำแนกคลาสจะเพี้ยนเงียบ ๆ (ทุกอย่างกลายเป็นคลาส 2) ⇒ ต้องอ่านจากที่เดียวกับที่ verify อ่าน
2. **counter คลาส (2) เป็น write ที่คนนอกกระตุ้นได้ ⇒ ต้องเป็น write ที่ bounded**
   - **aggregate/bucket เท่านั้น** — increment แถวเดียวต่อ (mechanism, คลาส, ช่วงเวลา) **ห้าม insert 1 แถวต่อ 1 request**
   - **มีเพดานต่อ bucket** — เกินเพดานแล้ว counter saturate (หยุดเขียนเพิ่ม บันทึกว่า "≥ เพดาน") ⇒ จำนวน write ต่อวันมีขอบบนคงที่ ไม่ขึ้นกับจำนวน request ที่คนนอกยิง
   - เหตุผล: ถ้าไม่ทำ ช่องเตือนไม่พัง **แต่ DB โดนแทน** — ย้ายความเสียหายเฉย ๆ ไม่ได้แก้
3. **การจำแนกคลาสต้องอ่าน header เอง ห้ามอนุมานจากค่า return ของ `verifyQStashSignature()`**
   *(เพิ่มโดยรีวิว 2026-08-08 · ตรวจโค้ดแล้ว)*
   - ฟังก์ชันนั้นคืน `{ valid: false }` **เหมือนกันหมดทั้งสามกรณี**: ไม่มี header · header มีแต่ signature ผิด · **signing key ฝั่งเราไม่ได้ตั้งเลย** (สาขา early-return ตอน key ขาดใน production **ตัดจบก่อนจะอ่าน header ด้วยซ้ำ**)
   - ⇒ ถ้าจำแนกจาก `valid === false` **ทุกอย่างกองรวมเป็นก้อนเดียว กฎ §C ใช้ไม่ได้ทั้งข้อแบบเงียบ ๆ**
   - ⇒ ต้อง**อ่าน header ตรง ๆ ที่จุดนับ** หรือ**ให้ verify คืน `reason` เพิ่ม**
   - ⇒ เคส **"signing key ฝั่งเราไม่ได้ตั้ง" ต้องตกเป็นคลาส (1)** เพราะ QStash แนบ header มาเสมอ ⇒ **corroboration กับ heartbeat ยังทำงานถูกต้อง**

### แก้ v2 §5 ข้อ 2 + ตาราง v2 §3 ข้อ 2 (ก) — ตัวเลขโควตา

**สิ่งที่ v2 เขียนผิด:** v2 §5 ข้อ 2 และตารางใน §3 ข้อ 2 (ก) เอา `probe 96/วัน` มาบวกกับ `sla-sweep 288/วัน` เป็น **384** แล้วใช้ 384 เป็นฐานอธิบาย threshold 80% — **แต่ counter ที่ v2 §3 ข้อ 2 (ข) ย้ายไปนับที่ inbound delivery attempt มองไม่เห็น probe เลย**

- probe 96/วัน เป็น **read-only outbound call** ที่เราเป็นคนยิงออกไป ไม่เคยวิ่งกลับเข้า endpoint ของเรา ⇒ **คนละระบบบัญชีกับ counter** ⇒ **เอามาบวกเป็น 384 ที่ counter อ่านได้ไม่ได้**
- **ค่าที่ counter อ่านได้จริงในสภาพปกติคือ 288 (28.8%)**
- **threshold 80%/100% ยังใช้ได้ แต่เหตุผลต้องเขียนใหม่ให้ถูก:** 80% (= 800 attempt/วัน) ห่างจากฐานปกติที่ counter อ่านได้ (288) เกือบ 3 เท่า ⇒ ไม่ noisy · และต่ำกว่าเพดาน 1,000 พอที่จะเหลือเวลาตอบสนอง · เคส 1,152/วัน ยังอ่านได้ 115.2% ⇒ **FAIL** เหมือนเดิม (ข้อสรุปของ v2 §5 ข้อ 2 ไม่เปลี่ยน เปลี่ยนแค่ที่มาของตัวเลข)

**เศษที่ v2 ไม่ได้เขียน และต้องเขียน — blind spot เชิงโครงสร้าง:**
สมมติฐานที่ยังไม่มีใคร verify (v2 §3 ข้อ 2 ก + §8) คือ *"read/list call ไม่กินโควตา"* · **ถ้าสมมติฐานนี้ผิดจริง:**

- โควตาที่ถูกใช้จริง = **384/วัน** แต่ **counter อ่านได้ 288**
- ⇒ **headroom ที่อ่านได้สูงกว่าความจริง ~9.6 percentage point เสมอ โดยโครงสร้าง** — ไม่ใช่ error ที่หายไปเอง
- ⇒ ตอนที่ counter แสดง 80% (DEGRADED) ของจริงคือ ~89.6% · ตอน counter แสดง 100% (FAIL) ของจริงคือ ~109.6%
- นี่ไม่ใช่แค่เรื่อง "คนละระบบบัญชี" แต่เป็น **blind spot ที่ต้องเขียนลง §G คู่กับสมมติฐานเดิม** — ไม่งั้นแถวโควตากลายเป็นแถวเขียวปลอมแบบที่ v2 เตือนตัวเองไว้ใน §2.6/§7

**ผูกกับ min-interval (ข้อบังคับ ไม่ใช่คำแนะนำ):**
blind spot 9.6% นี้ **bounded ก็ต่อเมื่อ min-interval ของ live probe ที่ v2 §3 ข้อ 6 กำหนดไว้ถูก implement จริง** — เพราะ min-interval คือสิ่งเดียวที่ทำให้ outbound call ต่อวันคงที่ ไม่ขึ้นกับจำนวนผู้เรียก (v2 §3 ข้อ 6 เขียนไว้เองว่า *"ตัวเลข 96/วัน เป็นเพดานจริง ไม่ใช่ค่าประมาณ"*)
⇒ **ถ้า min-interval หลุดตอน implement blind spot จะไม่ bounded อีกต่อไป** — คนนอกที่ยิง shape ที่ auth ได้ (หรือ workflow ที่รันซ้อน) จะดันโควตาที่มองไม่เห็นขึ้นได้ไม่จำกัด
⇒ **min-interval เป็นเงื่อนไขของความถูกต้องของตัวเลขโควตา ไม่ใช่แค่มาตรการกัน DoS** — ต้องเขียนกำกับไว้ที่โค้ดและใน §G

### H-1. snapshot store = **Redis** ไม่ใช่ตารางใน DB

**เบี่ยงจาก:** v2 §3 ข้อ 7 ("DB แถวเดียวก็พอ")
**ทำที่:** ลำดับ 2 — `src/lib/readiness.ts`

**เหตุผล (สามข้อ ไม่ใช่ความสะดวก):**

1. ตาราง heartbeat/`lastCheckAt` เป็น **ลำดับ 4** ⇒ สร้าง migration ที่ลำดับ 2 = ลาก **post-merge migration gate** (`CLAUDE.md` § Post-merge gate) เข้ามาก่อนเวลา ทั้งที่ยังไม่มีอะไรให้ verify บน prod
2. Redis เป็น shared store ที่ serverless instance ทุกตัวเห็นตรงกัน ซึ่งเป็น**เงื่อนไขที่ min-interval ต้องการอยู่แล้ว** ⇒ ไม่ได้เพิ่ม dependency ใหม่
3. `readSnapshot()` / `writeSnapshot()` ถูกเขียนเป็น **seam** ตั้งใจให้ลำดับ 4 ย้ายไปตารางจริงโดยไม่แตะตรรกะสถานะ

**ผลที่ตามมาที่ต้องเขียนตรง ๆ (ไม่ใช่ซ่อนใน `catch`):**

> 🔴 **สถานะของ P2 ไปอาศัยอยู่ใน dependency ที่ P2 เฝ้าเอง**
> Redis เป็นทั้ง "สิ่งที่ถูกตรวจ" และ "ที่เก็บผลการตรวจ" ⇒ Redis ล่ม = P2 เสียทั้งการวัดและความจำพร้อมกัน

โค้ดจัดการเคสนี้แล้ว และนี่คือสัญญาที่ห้ามเปลี่ยนโดยไม่แก้เอกสารนี้:

| เหตุการณ์ | สถานะที่ต้องได้ | เหตุผล |
| --- | --- | --- |
| อ่าน snapshot ไม่ได้ (Redis error) | **`FAIL`** | Redis ล่มคือ **ระบบพังจริง** ไม่ใช่ "วัดไม่ได้" |
| ไม่มี snapshot เลย (ยังไม่เคยวัด) | **`STALE`** | วัดไม่ได้ ≠ ระบบพัง — แต่ดังเท่ากันตาม §B(ค) |
| จองคิว live probe ไม่ได้เพราะ Redis พัง | **`FAIL` + ห้ามยิง live probe** | ไม่มี min-interval = เพดานโควตาหาย (§D) |

**ย้ายแล้วในลำดับ 4** ⇒ ตารางสัญญาข้างบนยังใช้ได้ทุกแถว เปลี่ยนแค่ว่า "อ่าน snapshot ไม่ได้" หมายถึงอ่าน **Postgres** ไม่ได้ ส่วน "จองคิวไม่ได้" ยังหมายถึง Redis เหมือนเดิม

### ⚠️ ความเสี่ยงสามข้อที่ต้องตัดสินพร้อมแบบ (อย่าให้หายไป)

**1. 🔴 `concurrency` — มีโอกาส deadlock ถ้าออกแบบพลาด**

`concurrency: readiness` ตอนนี้อยู่ **ระดับ workflow** ⇒ ครอบทุก run ของไฟล์นี้
⇒ run ของ `dispatch` กับ run ที่ถูก dispatch **แย่ง slot เดียวกัน**

> ⛔ **ถ้า `dispatch` รอผลของ run ที่มันสั่ง = deadlock ทันที** (ตัวที่ถือ slot รอตัวที่ยังเข้าคิว)

**ขนาดจริงของความเสี่ยง (รีวิว 2026-08-09):** `gh workflow run` **ไม่รอผลโดยค่าเริ่มต้นอยู่แล้ว**
⇒ ของจริงที่จะเกิดคือ **รอคิวไม่กี่วินาที ไม่ใช่ deadlock** — deadlock เกิดได้เฉพาะเมื่อมีคน**เพิ่มการรอเข้าไปเอง**

🔑 **⇒ ทำให้ deadlock เป็นไปไม่ได้ *เชิงโครงสร้าง* ไม่ใช่เพราะเราระวัง — กฎ 2 ชั้นซ้อน:**

| ชั้น | กฎ | ทำไมเป็นโครงสร้างไม่ใช่ข้อตกลง |
| --- | --- | --- |
| **ก** | **`dispatch` ห้ามรอผลเด็ดขาด** — ⛔ ห้าม `--watch` · ⛔ ห้าม poll จนกว่า run จะจบ | ถ้าไม่มีการรอ ก็ไม่มีวงจรรอคอยให้เกิด deadlock ตั้งแต่แรก |
| **ข** | **job `dispatch` อยู่ concurrency group แยกจาก `readiness`** (เช่น `readiness-dispatch`) | ต่อให้ชั้น ก พลาด สอง run ก็**ไม่แย่ง slot เดียวกัน** ⇒ ไม่มีคิวให้ติด |

⇒ **สองชั้นนี้อิสระต่อกัน** — ชั้น ก กันที่ "ไม่มีการรอ" · ชั้น ข กันที่ "ไม่มีทรัพยากรร่วมให้แย่ง"
⛔ **ห้ามตัดชั้นใดชั้นหนึ่งออกด้วยเหตุผลว่า "อีกชั้นก็พอแล้ว"**

> ✅ เจตนาเดิมของ `concurrency` (*"กัน cron ชนกับ post-deploy ตอนเขียน state"*) **ยังได้ครบ**
> เพราะตัวที่เขียน state คือ job `check` เท่านั้น — และ `check` ยังอยู่ในกลุ่ม `readiness` เหมือนเดิม

**2. latency ที่เพิ่ม ~1–2 นาที — ✅ ไม่กระทบ `IDENTITY_POLL_TIMEOUT_MS`**

timeout 5 นาที **นับจากตอนที่ poll เริ่ม** ไม่ได้นับจากเวลา deploy
⇒ ความล่าช้าจากการ dispatch **ไม่กินโควตาเวลาของ poll เลย** — และในทางปฏิบัติ **ช่วยด้วยซ้ำ**
(alias มีเวลาสลับมากขึ้นก่อนเริ่มถาม) · ราคาจริงคือ **เวลารวมตั้งแต่ deploy ถึงคำตัดสินยาวขึ้น ~1–2 นาที**
ซึ่งเล็กมากเทียบกับคาบ 15 นาทีของทั้งระบบ

**3. 🟠 โค้ดที่ถูก checkout เปลี่ยนเวอร์ชัน — ต้องบันทึกไว้**

ปัจจุบัน run ของ `deployment_status` checkout ที่ **sha ของ deployment**
หลังเปลี่ยน run ที่ถูก dispatch จะ checkout ที่ **HEAD ของ default branch**
⇒ **โค้ดของ *ตัวตรวจ* อาจไม่ใช่เวอร์ชันเดียวกับ sha ที่กำลังตรวจ**
· ปกติเหมือนกัน (deploy production มาจาก main) · ต่างกันเฉพาะช่วงที่มี commit ใหม่คั่นกลาง
· ✅ **ความถูกต้องไม่เสีย** เพราะ `expected_sha` ถูกส่งผ่าน input ⇒ ยังเทียบกับ sha ที่ deploy จริง

> 📌 **พูดให้ตรงกว่านั้น (รีวิว 2026-08-09):** ถ้า `main` ขยับไปแล้วระหว่างนั้น
> **โค้ดของ *ผู้ตรวจ* จะใหม่กว่าโค้ดที่ *ถูกตรวจ***
> ⇒ ✅ **ยอมรับได้ และสอดคล้องกับหลักการของเฟสนี้** — *ผู้เฝ้าไม่ใช่ผู้ถูกเฝ้า* (§H-5)
>   ไม่มีเหตุผลใดที่ตัวตรวจต้องเป็นเวอร์ชันเดียวกับสิ่งที่มันตรวจ
> ⇒ ⚠️ **แต่ต้องบันทึกไว้** — คนถัดไปที่เห็น run ของ post-deploy checkout คนละ sha กับ deployment
>   จะสงสัยว่าเป็นบั๊ก · **บรรทัดนี้มีไว้ตอบคำถามนั้นล่วงหน้า**

**4. 🔴 จุดล้มเหลวใหม่ที่ assertion ยัง *ไม่* ครอบ — ต้องพูดตรง ๆ**

`gh workflow run` สำเร็จ (exit 0) **แต่ run ปลายทางไม่เคยเริ่ม** ⇒ เงียบสนิท
⇒ **นี่คือรูปทรงเดียวกับที่เรากำลังแก้ ย้ายที่อยู่ไปอีกจุด** — ห้ามเขียนให้ดูสมบูรณ์กว่าที่เป็น

**ทางบรรเทา (อนุมัติแล้ว 2026-08-09):** ให้ `dispatch` **ยืนยันว่ามี run ถูก *สร้าง* จริง** —
`gh run list --workflow readiness.yml --event workflow_dispatch` แล้วเช็คว่ามี run ที่เกิด**หลัง**เวลาที่สั่ง

> 🔴 **ต้องเป็น poll แบบ *มีเพดาน* (2–3 ครั้ง) เท่านั้น — ห้ามรอจนกว่า run จะจบ**
> ไม่งั้นมันจะ **ชนกับกฎชั้น ก ของข้อ 1 ที่เพิ่งตั้งไปเอง** (ห้ามรอผล) ⇒ สร้าง deadlock ด้วยมือ
> ตรงที่เพิ่งประกาศว่าทำให้เป็นไปไม่ได้
>
> 🔑 **เส้นแบ่งที่ต้องชัด: ยืนยันว่า run *ถูกสร้าง* ≠ รอว่า run *ทำงานเสร็จ***
> อย่างแรกจบภายในไม่กี่วินาทีและไม่พึ่งผลของ run · อย่างหลังคือการรอที่ชั้น ก ห้าม
· ตาข่ายชั้นสองที่มีอยู่แล้ว: **cron รอบถัดไป (≤ 15 นาที) จะเห็นสถานะจริงอยู่ดี** ⇒ ความเงียบมีเพดานเวลา

### วิธีที่เลือก: **verify ผ่าน REST API** (Dev เสนอ — เห็นด้วย และมีเหตุผลเพิ่ม)

```yaml
- name: Verify state was actually saved   # ⇐ effect ไม่ใช่เจตนา
  if: always()
  env:
    GH_TOKEN: ${{ github.token }}
  run: |
    key="readiness-state-${{ github.run_id }}"
    for i in 1 2 3; do
      n=$(gh api "/repos/${{ github.repository }}/actions/caches?key=$key" --jq '.total_count')
      [ "$n" -ge 1 ] && exit 0
      sleep 5
    done
    echo "::error::cache entry '$key' ไม่มีอยู่จริงหลังสเต็ป save — ความจำของผู้เฝ้าไม่ถูกบันทึก"
    exit 1
```

> 🔑 **เหตุผลที่ API ดีกว่าการใช้ `actions/cache/restore` + `fail-on-cache-miss` (ที่ผมเสนอไว้ตอนแรก):**
> **ผู้ตรวจไม่ควรเป็นชิ้นส่วนเดียวกับผู้ถูกตรวจ** — ถ้า verify ด้วย action ตัวเดียวกับที่เพิ่ง no-op เงียบ

> ⇒ **นี่คือหลักการเดียวกับ §H-5 ย้ายมาใช้กับการ verify** ไม่ใช่กฎใหม่

**กรอบที่ถูกต้องของชั้นนอก (แก้ความเข้าใจเดิม):**

> 🔑 คุณค่าของชั้นนอกคือ **อยู่คนละ failure domain กับ GitHub Actions** — **ไม่ใช่ threshold ที่ต่างกัน**
> cron (ชั้นใน) กับ in-band gap check อยู่ในบ้านหลังเดียวกัน ⇒ GitHub ตาย/disable/throttle
> ทั้งคู่หายพร้อมกัน · pinger อยู่นอกบ้าน ⇒ เป็นชั้นเดียวที่ยังพูดได้ตอนนั้น

| | |
| --- | --- |
| ✅ ไม่เสีย — เคสหลัก (**cron ไม่รันเลย** · 60-day auto-disable · Actions ล่ม) | ครอบเต็มที่ 30 นาที — **เร็วกว่าแผนเดิม** |
| ✅ ไม่เสีย — alert fatigue | transition-only ยิงครั้งเดียวต่อ transition ⇒ ได้สองข้อความ **ครั้งเดียว** ไม่ใช่เสียงรัว |
| ⚠️ **เสียจริง** | **การเตือนแบบไล่ระดับ** — เดิมชั้นในดังก่อน ชั้นนอกดังตามทีหลัง ⇒ อ่านได้ว่า *"ชั้นในเงียบทั้งที่ควรดัง"* · ของจริงดังพร้อมกัน ⇒ แยกไม่ออกจากข้อความ ต้องไปดูที่ Actions เอง (ลง §G ข้อ 8) |

**⛔ ทางที่ตกแล้ว ห้ามรื้อ:** เพิ่ม `?staleAfter=<วินาที>` ให้ผู้เรียกตั้งเกณฑ์เอง
— เป็นการให้ **ผู้เรียกที่ไม่ auth ควบคุมเกณฑ์ที่ใช้ตัดสินสถานะ** ขัดหลัก *"ไม่รับ input จาก client
เลยแม้แต่รูปแบบเดียว"* (v2 §9 ข้อ 3) · **clamp แล้วก็ยังเป็น input ที่มีผลต่อคำพิพากษา**
= ตระกูลเดียวกับ tenant spoofing แค่เบากว่า
**⛔ ตกด้วย:** บังคับเลือก pinger ที่ assert JSON/numeric ได้ — จำกัดตัวเลือกผู้ให้บริการเพื่อประโยชน์เล็กมาก
