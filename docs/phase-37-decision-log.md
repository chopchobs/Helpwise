## บทที่ 3 — รอบที่เถียงกันแล้วผมเป็นฝ่ายผิด

ผมเสนอว่า A จะพังเพราะ demo-login เรียก:

```ts
const passwordValid = await verifyPassword(DEMO_PASSWORD, user.passwordHash);
```

agent2 มี hash สุ่ม → `verifyPassword` ไม่ผ่าน → 503

Claude Code สวนกลับ 2 จุด และถูกทั้งคู่:

1. **ผมเขียนเหมือนว่า "เจอ 503 มาแล้ว"** ทั้งที่ไม่มีใครรัน ไม่มี log — มันเป็นแค่คำทำนาย
   → มันจึงไปไล่หาสาเหตุของอาการที่ไม่มีอยู่จริง เสียเวลาไปหนึ่งรอบ
2. **demo-login ไม่เคยแตะ agent2 เลย** ในโค้ดปัจจุบัน — ผมพูดถึงโค้ดหลัง implement แต่เขียนไม่ชัด

> **บทเรียน:** เขียน "ผมทำนายว่า X" ให้ต่างจาก "ผมสังเกตเห็น X"
> ถ้าเขียนปนกัน คนอ่าน (หรือ agent) จะไปแก้ปัญหาที่ไม่มีอยู่

จากนั้นมี 2 ทางออก:

- **(i)** persona branch ข้าม `verifyPassword` — เพราะ `DEMO_PASSWORD` อยู่ใน repo อยู่แล้ว ไม่ใช่ด่านจริง
- **(ii)** ให้ agent2 ใช้ public password เดียวกัน — flow เดิมไม่เปลี่ยน

ตอนแรกผมเชียร์ (ii) แล้ว **กลับข้างเพราะประโยคที่ Claude Code เขียนเอง**:

> ให้ agent2 ใช้ `demoPasswordHash` = เพิ่ม account ที่ login ได้ด้วย password สาธารณะ
> จาก 1 → 2 ต่อ tenant **ผ่าน `/api/auth/agent/login` ปกติ**

นั่นคือการขยาย surface จริง ส่วน (i) ทำให้ agent2 ออก session ได้ทางเดียวคือ demo route บน demo tenant เท่านั้น
**(i) แคบกว่า** — และไม่ต้องเขียน prod DB เลย

ที่น่าสนใจ: รอบถัดมา Claude Code ยอมรับเองว่า *"ข้อโต้แย้งเดิมของผมข้อหนึ่งอ่อนกว่าที่มันฟังดู"*
แล้วหาข้อโต้แย้งใหม่ที่คมกว่าเดิมมาแทน 4 ข้อ

## บทที่ 4 — คำถามเดียวที่เปลี่ยนคำตอบทั้งหมด

ข้อโต้แย้งข้อแรกของมันคือคำถาม ไม่ใช่ข้อโต้แย้ง:

> **persona=2 มีไว้ทำอะไร?**
> ถ้าเป็นแค่ smoke ครั้งเดียวของ Dev → login ด้วย member จริงอีกคนก็จบ **ด้วยโค้ด 0 บรรทัด**
> ทั้ง (i) และ (ii) จะกลายเป็น over-engineering ทันที

คำตอบคือ: **visitor-facing ถาวร** ไม่ใช่ one-off

พอตอบข้อนี้ ทุกอย่างหลังจากนั้นเปลี่ยนหมด — และมันยังทำให้เห็นสิ่งที่ตกไป:
**ถ้า visitor-facing ต้องมี UI ให้กดถึง** persona ที่ไม่มีทางกดถึงเท่ากับไม่มี

> **บทเรียน:** requirement ที่ไม่ได้พูด ไม่ใช่ requirement ที่ไม่มี
> agent ที่ถาม "อันนี้มีไว้ทำอะไร" ก่อนเขียนโค้ด มีค่ากว่า agent ที่เขียนเร็ว

## บทที่ 6 — Bug class ที่กลับมารอบที่ 2

พอสั่งว่า "ลิงก์ที่ copy ต้องพาไปถึง ticket ใบเดิม" → URL กลายเป็น
`/demo?persona=secondary&next=/tickets/<id>`

`next` = **input จาก client ที่ควบคุมปลายทาง redirect** = open-redirect

และมันคือ bug class เดียวกับ **Story 1** ที่เคยเจอมาแล้ว:

> ปุ่ม "Try live demo" hardcode `https://acme.{ROOT_DOMAIN}/demo` ทุก host
> → visitor บน `globex.` โดนส่งเข้า workspace ของ acme
> แก้ด้วย `resolveDemoUrl()` ที่ resolve จาก Host จริง — บน subdomain คืน relative `/demo`
> ซึ่งกัน open-redirect **by construction** เพราะ relative path ออกนอก origin ไม่ได้

รอบนี้กันตั้งแต่ออกแบบ: relative path เท่านั้น · ต้อง match `/tickets/<id>` · reject `//`, `http://`, `https://`, `\`, มี host · ไม่ผ่าน → fallback `/dashboard` เงียบ ๆ

> **บทเรียน:** bug class สำคัญกว่า bug
> เจอครั้งแรก = แก้ได้ · เจอครั้งที่สองในโปรเจกต์เดียวกัน = **ยังไม่ได้เรียนรู้จริง จนกว่าจะกันไว้ตั้งแต่ออกแบบ**

เลือก **B** ด้วยเหตุผลที่ Claude Code เคยใช้ค้านผมเองเมื่อ 3 รอบก่อน:

## บทที่ 9 — พิสูจน์ว่าเทสจับบั๊กได้ ไม่ใช่แค่เทสเขียว

แทนที่จะรันเทสใหม่แล้วบอกว่าผ่าน มันทำแบบนี้:

```
โค้ดเก่า + เทสใหม่  →  7 failed | 16 passed   ← repro ยืนยันว่าบั๊กมีจริง
โค้ดใหม่ + เทสใหม่  →  23 passed
```

**เทสที่ไม่เคยเห็นสีแดง คือเทสที่ยังไม่รู้ว่าตัวเองจับอะไรได้**

## บทที่ 10 — พิสูจน์ที่ระดับ artifact ไม่ใช่ระดับ source

กฎที่ตั้งไว้: `DEMO_PASSWORD` ห้ามติด client bundle

วิธีพิสูจน์แบบอ่อน: grep source ว่าไม่มี import ผิด → พิสูจน์ได้แค่ **เจตนา**
วิธีพิสูจน์แบบจริง: `grep .next/static/` หลัง build → **bundler เท่านั้นที่บอกความจริง**

แล้วต่อยอดเป็น CI step — แต่ก่อนเชื่อว่ามันใช้ได้ ต้องพิสูจน์ว่ามัน **แดงเป็น**:

จงใจ import `DEMO_PASSWORD` เข้า client component จริง → build → scan

```
✗ พบ server-only value ใน client bundle (9 จุด)   EXIT: 1
```

**9 จุด — จาก import ผิดจุดเดียว** เพราะ re-export ลากทั้งโมดูลเข้า client graph
นี่คือเหตุผลที่ artifact-level scan จำเป็นจริง ไม่ใช่แค่ระเบียบ

> **บทเรียน:** gate ที่ไม่เคยเห็นสีแดง ไม่ต่างจากไม่มี gate
> "CI เขียว" อาจแปลว่า "ไม่มีปัญหา" หรือ "grep หาผิด path" — สองอันนี้หน้าตาเหมือนกัน

## บทที่ 11 — Audit prod ก่อนเปิดใช้จริง

`POST {"persona":"secondary"}` เปล่า ๆ ได้ session AGENT ทันที (เดิมยังต้องรู้ว่าต้องส่ง password)
→ ทุกอย่างใน acme/globex กลายเป็น **public โดยสมบูรณ์**

จึงต้องยืนยันก่อนว่าไม่มีของจริงหลงอยู่ ด้วย SQL read-only ชุดเดียว:

| ตรวจ | ผล |
|---|---|
| persona 4 ตัวมีจริง (User + TenantMember role=AGENT active) | ✅ OK ทั้ง 4 |
| User นอก persona | 1 แถว — `owner@acme.test` (OWNER) |
| Contact นอก seed | ไม่มี |
| Ticket นอกช่วง seed | ไม่มี |
| ApiKey / WebhookEndpoint / Attachment | 0 / 0 / 0 ทั้ง 2 tenant |
| ticketCounter vs max ticketNumber | ตรงพอดีทั้งคู่ |

จุดที่ agent คิดเพิ่มเอง (ไม่ได้สั่ง) คือแถว **ApiKey / WebhookEndpoint / Attachment** —
เพราะใน tenant ที่ public สมบูรณ์ ของที่อันตรายกว่าข้อความใน ticket คือ **credential** กับ **egress**

`owner@acme.test` ไม่มีอยู่ในโค้ดเลย (grep ทั้ง repo) = สร้างมือผ่าน signup เมื่อ 2026-05-31
→ ไม่ใช่ช่องโหว่ (visitor เข้าไม่ถึง) แต่เป็น standing risk ที่ re-seed ลบให้ไม่ได้

## สรุป: บทเรียนที่เอาไปใช้ต่อได้

1. **เอกสารที่ไม่ได้เขียนจากโค้ด จะผิดเงียบ ๆ** และถูกส่งต่อไปเรื่อย ๆ
2. **fail-soft ทำให้ "พัง" กับ "ปิดอยู่" หน้าตาเหมือนกัน** — ต้อง preflight แยกให้ออกก่อนเสมอ
3. **แยก "ผมทำนายว่า" ออกจาก "ผมสังเกตเห็น"** ไม่งั้นคนอื่นจะไปแก้ปัญหาที่ไม่มีอยู่
4. **requirement เปลี่ยนคำตอบทั้งหมด** — ถามว่า "มีไว้ทำอะไร" ก่อนเถียงเรื่องวิธีทำ
5. **bug class สำคัญกว่า bug** — เจอครั้งที่ 2 ในโปรเจกต์เดียวกันแปลว่ายังไม่ได้เรียนรู้จริง
6. **การจำแนกตัวตนอยู่ฝั่ง server เสมอ** — อย่าให้ client เทียบ list เอง
7. **อย่าเชื่อรายงานของงานที่ยังไม่ถึงเส้นชัย**
8. **เทสที่ไม่เคยเห็นแดง = ยังไม่รู้ว่าจับอะไรได้**
9. **พิสูจน์ที่ artifact ไม่ใช่ที่ source** — bundler เท่านั้นที่บอกความจริง
10. **ทางเลือกที่ดีทางวิศวกรรม ≠ ทางเลือกที่ดีที่สุด** ถ้าไม่รู้ว่าแก้ให้ใคร
